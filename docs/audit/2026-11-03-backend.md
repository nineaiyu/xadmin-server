## 三、问题清单（按严重级别）

> 说明：**未发现「阻断」与「高」级问题**。以下按 中 / 低 分组；每条标注

### 中级（3 项）

#### M-1 异步导入/导出任务未开 `acks_late`，worker 崩溃后记录可能永久停在 RUNNING

- **位置**：`system/tasks/__init__.py:186-187`（`async_export_data_task` 未声明 `acks_late`）、
  `system/tasks/__init__.py:249-250`（`async_import_data_task` 同）；对照
  `task/webhook_tasks.py:101` 与 `common/tasks.py:58,94`（邮件/投递任务**显式** `acks_late=True`）。
- **现象**：导入/导出任务在 heavy worker 执行中（worker OOM、宿主重启、30min 硬超时杀进程）时，
  消息已 ack、任务丢失，`ImportRecord` / `ExportRecord` 停在 `RUNNING`（`task/services/_import.py:108-109`、
  `task/services/_export.py:189-193`），直到保留期清理任务删除记录（导入 30 天 / 导出 7 天，
  `system/tasks/__init__.py:100-110`）。全仓 grep 无「stale RUNNING 重派/回收」机制。
- **成因**：任务幂等守卫其实**已经存在**（终态直接跳过：`task/services/_import.py:99-102`、
  `_export.py:179-181`），但任务声明没有像邮件任务那样补 `acks_late=True`——项目其它任务
  （邮件、Webhook）已认识到该差异并显式声明，此处属于遗漏而非设计取舍。
- **影响**：下载中心出现「永远进行中」的记录，用户无从区分是排队还是已死；协作式取消也失效。
- **修复建议**：两个任务补 `acks_late=True`（终态守卫已具备，重投安全）；可选：加一个周期任务
  把超过 N 小时仍 RUNNING 的记录标 FAILURE 或重新入队（与 `auto_clean_import_record_job` 同风格）。
- **状态**：已证实（代码路径 + 配置对照 + grep 无重派机制；崩溃场景未实际演练）。

#### M-2 Webhook 重试链完全依赖 Celery countdown 消息存活，无兜底重派

- **位置**：`task/webhook_tasks.py:161-166`（失败后仅 `next_retry_at` 落库 + countdown 派发下一轮）、
  `task/webhook_tasks.py:192`；`task/models/webhook.py:55`（`next_retry_at` 字段）；
  `docker-compose.yml:104-109`（Redis 仅 `requirepass` + 端口，无 AOF 追加持久化声明）。
- **现象**：失败重试不是「扫描 `next_retry_at` 到期行」而是依赖上一轮任务派发的 countdown 消息；
  broker（Redis）重启/丢消息时，`failed` 状态的投递将无人认领（人工 retry 是唯一出口，
  `task/views/webhook.py`）。全仓 grep 确认没有周期任务扫描 `next_retry_at`。
- **成因**：`celery 层 max_retries=0，由业务表跟踪`（`common/celery/retry.py:10` 注释声明的设计），
  但「业务表跟踪」只用于展示/审计，没有形成闭环调度。
- **影响**：开放平台事件投递在 Redis 故障后静默停摆；订阅方只能靠人工发现。
- **修复建议**：新增周期任务（如每 5 分钟）扫描 `status=failed AND next_retry_at<=now` 的行经
  `dispatch_deliver_webhook` 重派（代际号机制已天然防重复投递，`webhook_tasks.py:101-129`）；
  或给 compose Redis 显式配置 AOF。注意与 M-1 同根：都属「消息队列可靠性兜底缺失」。
- **状态**：已证实（代码路径 + grep；Redis 实际持久化策略未在本机验证）。

#### M-3 分片上传 `complete` 在数据库事务 + 行锁内做全量文件合并 I/O

- **位置**：`file/utils/upload_chunk.py:257`（`@transaction.atomic def _complete_session`）→
  `:266`（`select_for_update` 锁会话行）→ `:298`（`_merge_and_store` 在事务内）→
  `:307-343`（逐分片读存储 → 写临时文件 → 计算 md5/SHA-256 → 落库）。
- **现象**：合并时长与文件体积成正比（GB 级 + 对象存储后端时可达分钟级），期间持有：
  ① PG 事务（阻碍 vacuum、占用 xmin）；② 会话行锁（阻塞同会话并发 abort/complete——这是有意串行化）；
  ③ 一个数据库连接。psycopg 池 `timeout=5s` 只约束取连接，不约束事务时长。
- **成因**：「与并发 complete/abort 互斥」的串行化需求被实现为「锁横跨全部 I/O」。
- **影响**：大文件高频上传场景下 heavy/web 线程的 DB 连接被长事务占用；对 PG 的 WAL/vacuum
  压力随上传体积线性增长。功能正确性不受影响（异常路径、指纹校验、清理都严密）。
- **修复建议**：两段式——先在短事务内 CAS 把会话置 `MERGING`（携带指纹快照），锁外做合并 I/O，
  再以短事务落 `COMPLETED`/`ABORTED`；`MERGING` 中断由既有的过期清理任务兜底
  （`auto_clean_upload_sessions`，`file/utils/upload_chunk.py:379-405`）。
- **状态**：已证实（代码路径；未实测大文件的锁持有时长）。

#### L-5 `cached_method` 进程内缓存无容量上限、无淘汰

- **位置**：`packages/xadmin-common/common/decorators/cache.py:316-341`。
- **说明**：docstring 已自认「只增不主动清理，不要用于大对象或高基数 key」，属已知设计；

- **影响**：二开误用于高基数 key 时进程内存只增不减。
- **建议**：给 `_cache` 加条目上限 + 简单 FIFO 淘汰，或迁移到 `L1_STORE` 同款实现。
- **状态**：已证实（设计自述 + 使用面 grep，当前调用点基数可控）。

#### L-6 compose Redis 未显式声明持久化策略，缓存/通道/broker 共用一实例

- **位置**：`docker-compose.yml:104-109`（仅 requirepass/port）；`server/settings/cache_channel.py:17-50`
  （default 缓存 + CHANNEL_LAYERS + celery broker 三个 Redis 逻辑库共用）。
- **说明**：缓存键按逻辑库隔离（DEFAULT_CACHE_ID / CHANNEL_LAYERS_CACHE_ID / CELERY_BROKER_CACHE_ID），
  语义正确；但 broker 库的消息存活依赖 Redis 持久化配置，与 M-1/M-2 叠加会放大任务丢失窗口
  （可接受性取决于业务对异步任务丢失的容忍度——项目已有大量「终态守卫 + 人工 retry」兜底）。
- **建议**：生产 compose 显式 `--appendonly yes`（或独立 broker 实例）；文档注明当前 RPO。
- **状态**：部分证实（compose 配置已证实；Redis 实际重启丢消息窗口未实测）。

### 观察项（不构成缺陷，供演进参考）

1. **`MagicCacheData` 等锁排队上限 65s**（`common/core/decorators/cache.py:89`：`blocking_timeout=placeholder_ttl+5`）：
   计算方挂死时等待方最多排队 65s 才回源/报错——有界且注释了理由，但高并发下会形成请求堆积波，
   建议监控 `miss` 指标。
2. **批量导入整包一个外层事务**（`task/services/_import.py:198`）：为支持「失败率超限整体回滚」的
   语义把全部行包进单事务——万行级导入是分钟级长事务（heavy 进程执行，无请求线程影响），
   与「超限中止」语义强绑定，属有意取舍；若未来导入量级上去可评估改「逐行独立提交 + 中止时补偿删除」。
3. **`background_task_view_set_job` 的分片汇总靠 `cache.len()==task_count`**（`common/tasks.py:280-302`）：
   分片结果若被 Redis 驱逐，汇总与通知会挂起至 24h TTL；代码注释已声明该兜底。
4. **`UserInfo.username` 保持全局唯一**（`identity/models/user.py:150-152`）：软删后用户名仍被占用，
   注释已说明这是 Django auth.E003 检查的约束，序列化器按 `all_objects` 给可读提示——已知权衡。
5. **`handle_db_connections` 每次调用打两行 INFO**（`common/base/decorators.py:24-27`）：仅用于 celery 任务路径，量级可控。

## 四、值得肯定的设计（抽样，均有代码依据）

1. **权限体系 fail-closed 全链路**：运行时按 `(path, method)` 解析、坏正则跳过不误伤
   （`common/core/url_inventory.py:48-96`）；权限缓存（24h）由信号在用户/角色/部门/菜单/M2M 全部
   变更面精准失效（`identity/signal_handler.py:72-149`、`system/signal_handler.py:41-141`），
   批量删除目录时级联后代也失效（`system/models/menu.py:159-178`）；PAT 双 header 的 scope
   回退解析带 60s 短缓存与降级直查（`common/core/permission.py:271-318`）。
2. **数据权限编译器 + 版本化缓存**：授权池按「全局版本号」失效（`common/core/filter.py:36-67`），
   缓存故障静默回落直查；无授权即 `none()`（fail-closed）；写侧载荷范围与读侧同源
   （`assert_within_data_scope`，`filter.py:207-230`）。
3. **缓存基建的占位保护**：`MagicCacheData` 修复了「异常被吞后把空结果缓存整个业务 TTL」的旧缺陷、
   占位/锁 TTL 与业务 TTL 解耦、锁上排队 + 双检（`common/decorators/cache.py:31-122`）；
   `MagicCacheResponse` 同范式单飞 + `no_cache` 旁路 + 4xx/5xx 不回写。
4. **配置三层缓存（L1→Redis→DB）**：缺行 no_row 短 TTL 标记防穿透、运维热改键 60s 短 TTL 自愈、
   L1 深拷贝防调用方污染（`common/core/config/base.py:110-194`）；Redis 冻结时 `IGNORE_EXCEPTIONS`
   降级读库不阻断请求（`server/settings/cache_channel.py:39-45`）。
5. **审批引擎并发设计**：实例行锁 + 任务级 CAS + 终态 CAS 三层防重复推进（
   `approval/services/approval_flow/engine.py:289-337`）；流程版本钉住（在途单不受改版影响）；
   运行期无候选节点 fail-closed 阻塞而非自动通过（`engine.py:58-93`）。
6. **出站 SSRF 防线**：协议白名单 + 全 IP 归属校验（link-local/元数据/隧道地址任何模式拒绝）+
   白名单放行 + **固定解析连接**消除 DNS rebinding 窗口（`common/utils/outbound.py:48-130`），
   Webhook/AI/MCP/通知全走同一出口。
7. **字段加密 v3**：HKDF 派生独立数据密钥 + AES-256-GCM（机密性+完整性），主密钥与 SECRET_KEY
   分离可轮换、读路径逐历史密钥回退（`common/base/crypto.py:62-181`）；JWT 签名密钥同样可分离。
8. **导入链路工程质量**：逐行 savepoint 部分成功、失败率超限整体回滚、失败行 xlsx 报告落库、
   自关联拓扑排序、thread-local 请求注入使 creator/审计同源（`task/services/_import.py:81-230`）；
   进度走缓存通道避免长事务内不可见。

10. **操作日志体系**：process_view 只标记、响应期单条 INSERT（结构性消除孤儿/半成品行，
    `common/core/oplog_recorder.py:161-185`）；请求体/响应体/变更 diff 三面递归脱敏 +

11. **数据集执行安全**：模型/字段/op/指标四层白名单保存与执行双侧校验、禁原生 SQL、
