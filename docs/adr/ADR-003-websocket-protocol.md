# ADR-003: WebSocket 消息协议保持自定义格式并补类型约束

- 状态：已接受（2026-09-04，P2 复审）
- 关联：半年规划 T1.6 / TD-08

## 背景

消息推送使用自定义 WS 协议 `{action, data, mid}`（`message/base.py`），前端 `src/utils/websocket` 对应解析。此前分析（XADMIN_FRAMEWORK_ANALYSIS.md §5.2.9）指出该协议无标准约束、action 字符串匹配缺乏类型安全。

## 备选方案

1. 迁移到标准协议（Socket.IO / WAMP / Mercure）；
2. 保持自定义格式，补充 Schema 与前后端类型约束。

## 决策

**方案 2**，理由：

1. 现有消息场景（聊天室、通知推送、任务日志流）消息类型有限且稳定，自定义协议运行良好，迁移收益低；
2. 引入 Socket.IO 类方案会带来客户端库、房间/命名空间语义、心跳重连参数与 channels-redis 层的适配成本，且增加一条长连接依赖链；
3. 真正的痛点是"契约无类型"而非"协议非标"——可用 Schema 化解决。

## 实施项（归入 P2，与 T2.3 元数据 Schema 同批）

- 后端：`message/` 定义 action 枚举与消息体 Pydantic/TypedDict 定义，收发两端校验；
- 前端：依据同一 Schema 生成 TS 类型，消除 `action` 字符串散落匹配；
- 协议版本字段：消息体增加可选 `v` 字段，为未来迁移留兼容口。

## 后果

- 正面：契约获得编译期/运行期双重保护，避免前后端协议漂移；保留技术选型自由；
- 负面：放弃了成熟协议自带的断线重连/房间管理生态（当前自实现已覆盖，未见缺口）。
