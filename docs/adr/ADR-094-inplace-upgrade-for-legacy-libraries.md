# ADR-094：四域切分前的旧库支持真·原地升级（立项）

- 日期：2026-10-16
- 状态：**已接受**（立项：主路线与分期已定，按批实施；方案与调研见 [plans/原地升级立项与方案-2026.10.md](../plans/原地升级立项与方案-2026.10.md)）

- 背景：5.0 的升级路径分两档——四域切分**之后**的 4.x 库走账本认领（原地，已交付）；
  切分**之前**的库（`system_userinfo` 等旧表名）只能「备份 → 清库重建 → 回灌」
  （[ADR-093](ADR-093-migration-consolidation-and-ledger-claim.md) §修订）。
  上一轮 4.2.5 → 5.0.1 端到端演练确认了这条路的代价：**二开用户实际损失面过大**——
  二开 app 的旧迁移引用必须人工改写（否则新库里装不上）、二开表的物理文件不搬、
  搬运面只有 12 个实体（审批 / 表单 / 数据集 / 报表 / 大屏 / 聊天 / 审计与登录日志 /
  任务记录 / PAT 与 API 应用 / webhook 均不在面内）、加密设置取值跨库不可解、
  且停机 + 人工 `DROP/CREATE` + 目录搬运未封装进安装器。
  同时调研发现一个此前被忽略的**使能条件**：`v4.1.0 ~ v4.2.5` 的历史 tag 全在仓库里，
  旧模型、旧迁移与旧列集可以权威还原，因此「表改名 + 补列 + 存量串重指」的映射表可机械生成、
  可校对、可守护——技术上前提已具备。

## 决策

### D1 立项做「结构对齐器」路线，而不是继续在回灌上打补丁

- 主路线：**同库结构对齐**——读活库与目标态，生成声明式 DDL/DML 计划（表改名 / 补列回填 /
  索引与序列修正 / `contenttypes` 与权限重指 / 存量字符串重指 / 账本重写），在单事务内执行。
  表改名由 PostgreSQL 保留约束、索引、序列与外键，**二开表的行、主键、外键与文件路径全部不动**。
- 不采用「把四轮重建回滚为正常迁移链」的方案（对全新安装影响大、历史链重建工作量大）；
  也不再把「无损回灌增强」当官方首选，它降级为逃生舱。

### D2 二开迁移图用「历史链兼容包」解决，而不是要求用户改代码

- 用历史 tag 把旧链还原为**只声明状态、不执行 DDL** 的迁移（节点名与原链一致），
  随 5.x 发布、只在升级路径生效：二开迁移的 `dependencies` 与 `to="system.userinfo"` 类引用零改动即可解析。
- 兜底：提供迁移改写工具（按登记表改写 `app_label` / `to=` / `dependencies` / 表名串，改写前打印 diff），
  适用于深度定制；处理结果必须写进升级报告。

### D3 判定 fail-closed，执行可预演、可退

- `upgrade_check` 增加「可原地升级 / 阻断原因」判定；结构画像命中不了已知家族、
  或检测到框架表被人工改动时**拒绝执行**，输出差异报告并给人工/回灌路径（不产生「半对齐」的库）。
- 执行前强制备份（复用 `ops/db_backup.sh`）；计划支持 dry-run 与断点续跑；失败回滚一律走备份恢复，
  不做反向迁移承诺。安装器接线为「判定 → 预演 → 交互确认 → 执行 → 复检」，既有 `SKIP_*` 逃生舱保留。

### D4 边界

- 不做零停机升级；不承诺任意定制库自动收敛；不动已发布历史链的组织方式（全新安装路径零变化）；
  PG 大版本数据目录迁移维持现有 `pg_dump` / `pg_restore` 做法，本项不升级为 `pg_upgrade`。

## 后果与边界

- 四域切分前的库将获得与切分后库同等的升级体验：保留主键 / UUID / 时间戳 / 媒体文件 /
  全部业务数据与二开表，升级从「停机 + 人工重建 + 有限回灌」变为「一条命令 + 分钟级停机」。
- 代价是新增长期维护面：结构差异目录（catalog）随版本演进需同步维护，且需要真实旧库样本回归。
- 全新安装与四域切分后的库行为、性能零变化（不修改 5.x 迁移链）。
- 回灌工具保留（逃生舱）：极端定制、结构漂移、跨大版本且无样本的库仍用它。

## 验证（分期验收）

- 第一批（可行性，**2026-10-17 已交付**）：由 `v4.2.5` tag 生成结构库（含旧账本）并产出表/列级
  差异报告，跑通「改名 + 补列」执行原型——实测改名 14 张 / 补列 30 列 / 由 `migrate` 新建 76 张 /
  阻断 0，执行后逐表行数、主键与 UUID 原样，外键随改名保留，复跑幂等（细节见方案 §八）。
  账本重写与权限重指归入第二批（它们是**记录与引用层**的重写，与结构改名解耦）。
  其余样本（4.1.x / 4.2.x 真实库）与二开样本 app 回归仍待补齐。
- 第二批（能力落地，**2026-10-17 已交付**）：结构补齐（缺失表 / 0002 外键列 / 模型级索引与约束 /
  自动 M2M 中间表 / 前置扩展白名单）+ `django_content_type` 重指 + 存量字符串重指（登记表驱动）+
  迁移账本重写（只动本仓库 app，三方记录留给常规 `migrate`）+ `align_full` 编排（预演 / 阻断即拒绝 /
  两段 schema editor / 执行后复检）；守护测试覆盖标签迁移、改写锚定、前置白名单完整性、
  结构与账本一致性、幂等、与全新安装的索引集合一致。`upgrade_check` 新判定与安装器接线归入第三批。
- 第三批（**2026-10-17 已交付**）：`upgrade_check` 新增 `legacy-inplace-capable` 判定（含 `--dsn` / `--tag`
  与只读预演小节）；`legacy_align --probe` 三态退出码供安装器判定，安装器新增
  `inplace_align_if_needed`（探询 → 预演 → 确认 → 执行，`SKIP_INPLACE_ALIGN` 逃生舱）；
  二开迁移引用改写工具 `legacy_rewrite_app_refs`（离线标签映射、改写 FK 目标与依赖、未映射不猜）；
  `v4.1.3` / `v4.2.3` / `v4.2.5` 三代样本**全部原地对齐通过**（结构完整 / 账本一致 / 数据与主键原样）。
  真实客户库与真实二开 app 的回归、安装器真机端到端演练归入第四批。
- 每组验收同时跑：`upgrade_check` = `up-to-date`、`sync_menu_permissions --dry-run` 缺口 0、
  旧密码登录成功、附件可下载、健康检查四项 `true`。

## 与既有 ADR 的关系

- [ADR-093](ADR-093-migration-consolidation-and-ledger-claim.md)：其「切分前库不在等价范围内」的
  结论与拒绝保护继续有效（认领仍只服务结构等价的库）；本 ADR 只为其补上**真正的结构对齐能力**，
  不修改合并链与认领口径。
- [ADR-058](ADR-058-system-migration-squash.md) / [ADR-084](ADR-084-migration-squash-2026h2.md)：
  四轮清库重建式整理的历史事实不变，不回滚。
