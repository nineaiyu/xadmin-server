# ADR-009：字段级脱敏的豁免口径与写入侧守护

- 状态：已接受
- 日期：2026-09-10
- 关联：N3 第三期 F3（脱敏能力）/ 第四期 F1（原文通道接线与规则运营化）

## 背景

字段级脱敏在输出侧统一生效（`BaseModelSerializer.to_representation` 钩子，列表/详情/导出同一链路）。但「统一掩码」与两类真实诉求冲突：

1. 内部链路（导出、预览、任务重放、超管操作）需要原文；
2. **编辑者需要看到原文才能修改**——若编辑弹窗只拿到列表里的掩码值，用户「看不见就改不动」，且会把掩码串原样提交回写（一旦落库即不可逆的原文损坏）。

## 决策

1. **豁免仅三类**（`_mask_exempt`）：超管、显式 `ignore_field_permission`、原文通道。其余请求（列表/详情/导出）一律按规则掩码。
2. **原文通道 = 显式 `?mask=false` 且对该请求地址有更新权限**（PUT/PATCH 任一命中）：
   - 为什么以「更新权限」为门槛而不是「读权限」：能改这条数据的人才需要原文；只读用户看到原文属越权读取，且列表/导出仍须掩码，故不放宽读权限；
   - **按请求地址判定，而非菜单主键**：同一 path 的 GET/PUT/PATCH 是三条主键互不相同的菜单，按主键比对时 GET 详情请求永远命中不了更新权限菜单 —— 通道恒关。该缺陷在前端未接线时不可见，第四期接线后由 E2E 暴露并修复（`user_can_update_menu(user, url)` 复用 `get_menu_pk` 地址口径）；
   - 放行的原文访问记审计（每请求一次，含 `user`/`path`/`model`），便于回溯「谁看了原文」。
3. **写入侧守护**（`to_internal_value`）：提交值等于「库内原文的掩码结果」时丢弃该字段并告警。原文通道与写守护是**互补**关系：
   - 通道解决「看得到」——只对具备更新权限的用户开放；
   - 守护解决「改不坏」——即便通道不可用（权限不足 / 请求失败 / 旧前端），掩码回写也不会污染库内原文。
   - 只做其一都会留下真实破坏路径：**只有通道**时，权限收紧后前端仍会回写掩码值；**只有守护**时，编辑者无法修改被掩码字段（真实改动会被静默丢弃）。
4. **不做**：按数据行差异化脱敏（如「自己的手机号不脱敏」）、前端本地脱敏渲染（两侧各算一遍必然漂移）、原文通道的字段级审计（只记「发生过访问」，不记「看了哪些字段」）。
5. **字段权限是独立链路**：脱敏豁免与字段权限白名单互不替代。非超管走详情接口时，其角色还需在**该详情菜单**上有字段白名单，否则响应被裁剪为空对象（表现为「接了通道也看不到原文」）。E2E 种子已覆盖该前提（`grant_field_permission` 同时授列表与详情 GET 菜单）。

## 后果

- 正面：编辑者不再被掩码卡住；掩码回写有服务端兜底；原文访问可审计。
- 负面/边界：原文通道以「更新权限」为门槛，粒度较粗（可更新该资源的用户能看到该记录全部被掩码字段的原文）；字段权限启用时需为详情菜单配置白名单，属部署配置前提。
- 演进：若需「谁看了哪些字段」的精确审计，需在操作日志侧扩展字段级记录（当前只记是否发生过原文访问）。
