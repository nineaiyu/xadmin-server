# ADR-067：在线建表（表单即建表）评估（P2.1 第二段）

- 日期：2026-09-27
- 状态：**已评估（结论：不投运行期 DDL；补齐缺口清单与触发条件）**——本 ADR 只做决策与登记，不产生代码改动；**后续更新（2026-09-27）**：登记项 B2（表单数据页）触发条件命中并已交付，实施口径见 [ADR-068](ADR-068-form-data-management.md)；**登记项 B1（数据集 JSON 路径列）随后交付**，见 [ADR-069](ADR-069-dataset-json-columns.md)（日期类型标注仍维持登记）
- 背景：§7 P2.1 的决策点是「是否对齐 jeecg Online？**若投，先做设计器增强再评估在线建表**」。设计器增强（拖拽 / 联动 / 版本化）已交付（[ADR-064](ADR-064-dform-designer-upgrade.md)），本文补第二段：在线建表（用户自定义实体 = 物理表）的评估结论。

## 现状证据（评估前的能力基线）

「表单数据能不能用起来」这件事，现状已具备三条路径：

| 能力 | 位置 | 说明 |
|---|---|---|
| 提交列表（含筛选） | `dataset/views/dform.py::DynamicFormSubmissionViewSet` + `SubmissionFilter` | 按表单 / 状态 / 提交人筛选，**行级数据权限**编译（非超管只在自己可见域内），`schema_version` 随行下发 |
| 动态列导出 | 同上的 `export-data`（`SubmissionExportSerializer`） | 固定列（提交号/表单/提交人/时间）+ **按表单 schema 展开的动态列**，导出范围跟随列表筛选 |
| 数据消费 | `Dataset.bound_model = dataset.dynamicformsubmission` | 数据集 → 明细/聚合/报表/大屏/看板全链路；字段权限、数据权限、CSV/xlsx 导出全部复用（种子有「示例-表单提交」数据集） |

缺口（同一基线下的两点不足）：

1. **数据集的列只能是模型字段**：`dataset/utils/dataset.py::build_queryset` 走 `queryset.values(*columns)`，`_check_numeric` / `numeric_columns_of` 走 `model._meta.get_field(field)`——表单字段值都在 `DynamicFormSubmission.data`（JSON）里，**JSON 路径列（如 `data.kind`）不被支持**（会以「字段不可用」400 拒绝）；字段权限（`FieldPermission`）也按模型字段名登记，JSON 路径没有登记位。
2. **缺管理端「按表单看数据」的页面**：现有页面只有「我的填报」（creator 隔离）与导出；管理员想「按字段筛选、翻页浏览某个表单的全部提交」需要走导出或数据集，路径不直观。

另有一处版本化带来的**既有行为**需要登记：`_export_dynamic_fields` 取的是当前 schema，提交时只存 `schema_version`（不存 schema 快照）——表单删字段后，历史提交里该字段的值仍在 `data` JSON 中，但不再出现在导出列里（回看/导出历史字段需要快照）。

## 方案对比

| 方案 | 形态 | 成本 | 风险 |
|---|---|---|---|
| **A 运行期 DDL** | 表单即物理表（jeecg Online 形态） | ≥ 3 个窗口：建表/改表/删表 DDL 与回滚、字段类型映射与变更算法（改类型/删字段的数据迁移）、迁移体系与仓储层冲突、PG/SQLite 方言差异 | 运行期 DDL 权限面、备份与恢复（新增表纳入备份与 PITR 口径）、数据权限编译器与字段权限需覆盖动态表、二开契约不稳定（表结构随用户操作漂移） |
| **B1 数据集支持 JSON 路径列** | `columns` 允许 `data.kind` 形态（含数值/日期类型标注） | 中：`values()` 路径解析 + 类型标注（数值聚合不能用模型字段判定）+ 字段权限映射（`data.*` 继承 `data` 的权限登记）+ 前端列选择器 | 与既有「列 = 模型字段」契约不兼容，需版本化列语义；历史数据集列不受影响（fail-closed 拒绝旧格式的安全面要守住） |
| **B2 表单数据页（管理端）** | 按表单渲染提交列表（动态列 + 筛选 + 导出），复用 RePlusPage 动态列 | 低：后端接口已具备（列表按 form 过滤 + export-data 动态列），纯前端页面级 | 需要新权限点（查看他人在某表单的提交）——现状靠数据权限收敛，产品口径要明确「谁能看」 |
| **B0 维持现状** | 文档说明「配置数据集 / 用导出」 | 0 | 管理员体验绕 |

## 决策

### D1 不投方案 A（运行期 DDL）

理由：收益（SQL 生态、外键、大数据量性能）在本系统的实际用法里不成立——表单填报的数据量级（演示与常见企业内部用量）远未到需要物理表优化的程度，而成本/风险面（DDL 权限、备份口径、数据权限编译器、迁移体系、二开契约）是长期负债。**重开条件**（任一命中）：① 出现「用户自定义实体」而非「表单填报」的诉求（自定义业务表 + 强关联/外键 + 百万级行数）；② 需要在表单数据上做跨表 JOIN 的报表诉求且数据集通道无法满足；③ 表单数据量级单表 > 500 万行且查询延迟进入 SLO 红线。

### D2 缺口按 B2 → B1 的顺序登记，触发条件命中再投

- **B2（表单数据页）**：优先级高（成本低、体验缺口最直观）。**触发条件**＝出现「管理员需要在页面上按字段筛选/浏览某个表单的全部提交」的真实诉求（当前以导出 + 数据集过渡）；实施时须同时定义「谁能看」的权限点与数据权限口径（默认沿用数据权限编译器，不新开旁路）。
- **B1（数据集 JSON 路径列）**：成本中等且改动列语义契约（`Dataset.columns` 从「模型字段名」扩展为「模型字段名 ∪ JSON 路径」），需与字段权限、数值判定、前端列选择器一并设计。**触发条件**＝出现「表单字段级别做报表/看板」的诉求（当前只能对 `data` 整列消费）。
- **历史字段可见性**（schema 快照或按版本解析导出列）：随 B2/B1 一并评估，或出现「改版后需回看/导出历史字段」诉求时单独投——**已交付（2026-09-27，ADR-070）**：按 `schema_history` 版本快照解析（详情按提交版本渲染、导出列合并历史字段并标注、管理端列表同口径），未采用「提交冗余存快照」方案。

### D3 现状路径保留并在文档中显性化

「表单数据 → 数据集 → 报表/大屏/看板/导出」与「提交列表导出（动态列）」两条路径继续作为标准用法；`README`/使用说明层补充「如何为某个表单配置数据集」的步骤（表单元数据与数据集列映射）。

## 验证

- 本 ADR 为评估类，无代码改动；结论依据的代码事实：`dataset/views/dform.py::DynamicFormSubmissionViewSet`（列表筛选 / `export-data` 动态列）、`dataset/utils/dataset.py::build_queryset|_check_numeric|numeric_columns_of`（列 = 模型字段 + 数值判定走 `_meta.get_field`）、`loadjson/dataset.json`（示例-表单提交数据集）。
- 缺口可用性复核：以「管理员要给某个表单做按字段筛选/导出」为场景走了一遍现状路径（数据集 + 导出），确认**可用但绕**，故登记而非立即投。

## 边界

- 不做表单数据的**跨表关联**（B1 的 JSON 路径仍是单表内取列，不引入 JOIN）；
- 不引入物化视图/汇总表（数据量触发后再评估）；
- 在线建表若将来重开（A），须先补「DDL 权限与审计、备份口径、数据权限编译器覆盖动态表」三份设计，不得以「先跑起来再补」的方式落地。
