# ADR-031：多租户 go/no-go 评估（结论：暂不做）

- 状态：已接受（评估结论：**no-go（暂不做）**，登记重开条件）
- 日期：2026-09-13
- 关联：年度开发计划 2026.10-2027.09 §四 2027-09；ADR-006/ADR-015（数据权限编译器与红线）；
  `common/core/data_scope.py`、`common/core/filter.py::get_filter_queryset`；
  年度回顾 `docs/plans/年度回顾-2026.10-2027.09.md`

## 背景

SaaS 化诉求（一套代码服务多个租户）需要决定：**在现有单租户架构上引入租户模型，还是继续
「一租户一实例」的部署形态**。评估口径：租户隔离强度、数据权限编译器适配成本、迁移与运维成本、
以及现有能力的复用度。

## 现状（事实基础）

1. **隔离边界已存在且是多层纵深**：数据权限编译器（`get_filter_queryset`，fail-closed）、
   字段级权限、菜单/URL 权限、部门树 + 角色、PAT/应用 scope、审计（`OperationLog`）；
   但它们全部是**「单租户内」的权限模型**——没有任何一层带租户维度；
2. **部署形态已是多实例友好**：`config.yml` 单文件配置 + sqlite/mysql/pg 三库可选 +
   `xadmin-installer`（docker compose）+ 备份/异地副本链路（ADR-013）；
3. 业务表**没有租户列**：`system.*`、`settings.*`、`notifications.*` 及演示模型都是全局表；
   数据权限授权（`DataPermission`）以部门/PK 清单表达，**没有租户作用域概念**。

## 决策：no-go（暂不做），理由

| 维度 | 评估 |
|------|------|
| 隔离强度 | 「一租户一实例」= **物理隔离**（库/配置/密钥/备份独立），强于任何行级 `tenant_id` 方案（后者任一查询漏加过滤即跨租户泄露） |
| 改造面 | 引入 `tenant_id` 需：全部业务表加列 + 唯一约束重写（如 `uniq_*_active` 加租户）+ 数据权限编译器加租户维度 + 认证/会话/JWT 带租户 + 迁移历史重放 + 种子按租户实例化；估算 **≥ 6 个窗口**且高风险窗口集中在权限链路 |
| 运维成本 | 单实例多租户省机器，但备份/恢复/升级的**爆炸半径**从「一个租户」扩大到「全部租户」；现有备份演练与异地副本按实例编排，无需重设计 |
| 收益 | 当前无可确认的「单实例服务多租户」商业诉求；一租户一实例的成本（compose 一套）已由 installer 摊薄 |
| 时机 | 数据权限编译器方兴未艾（本年度刚接入多处），此时叠加租户维度会把两个高风险改动耦合在一起 |

因此**登记为 no-go，按现有「一租户一实例」部署形态承载 SaaS 场景**；租户开通 = 实例编排
（installer + 独立库 + 独立密钥 + 独立备份域），与本项目既有运维链路一致。

## 重开条件（任一满足即重新评估）

1. 出现**明确**的「单实例服务多租户」诉求（如按租户计费的托管服务，实例数 > 50 且机器成本敏感）；
2. 需要**跨租户聚合**的产品能力（平台级运营看板/统一计费），一租户一实例无法提供；
3. 需要**租户自助开通**（分钟级、零运维介入）——此时评估方向是「实例编排自动化」而非行级多租户，
   优先在 `xadmin-installer` 上做（成本低一个量级）。

## 若将来真的要做（预研要点，供重开时直接落地）

- 隔离方案选 **schema-per-tenant**（Postgres schema / MySQL database）而非行级 `tenant_id`：
  复用现有迁移与 ORM 不变更模型，天然防漏过滤；
- 租户解析点收敛在认证链（JWT claim `tid` + 会话绑定），数据权限编译器**不改**；
- 平台侧表（租户注册表、计费）单独 schema + 单独权限面；
- 迁移/种子/备份按租户编排（`xadmin-installer` 已是这条路的起点）。
