# 验证码多形态增强方案：滑动 / 旋转 / 点选（2026-10）

> 状态：**已交付（2026-10-26）** ｜ 范围：`captcha` + `identity` + `settings`（server）、登录与通用组件（client）
> 诉求来源：现有图片字符验证码易被 OCR 绕过，需要补充交互式（行为式）验证码：滑动拼图、旋转回正、文字点选。
> 关键决策已与需求方确认（见 §〇 决策记录）；执行偏差与验证证据见 §十一。

## 〇、决策记录（2026-10-26 与需求方确认）

| 决策项 | 结论 |
|--------|------|
| 「滚动」题型语义 | **旋转回正**（拖杆把预转图片转正；i18n 词条与 vben 参照均现成，实现最顺） |
| 首批题型范围 | **三种全做**（slide / rotate / click，题型插件一次成型，三阶段约 6 天） |
| 交付后默认模式 | **保持图片验证码**（`CAPTCHA_MODE` 默认 `image`，升级零行为变化，管理员在设置页切换） |
| 触发策略 | **每次必验证**（维持现状语义；「连续失败 N 次后才弹」不在本期，见 §十.3） |
| 点选字符集（工程默认） | 常用 3500 汉字子集 + OFL 字体内置；`CAPTCHA_CLICK_CHARSET` 保留可切 ascii |
| Redis 故障语义（工程默认） | verify **fail-closed**（缓存不可用即拒绝，对齐「开关开即必须通过」） |

## 一、目标与非目标

**目标**

1. 在现有图片验证码之外新增三种**服务端校验**的交互式验证码：滑动拼图（slide）、旋转回正（rotate）、文字点选（click）；
2. 生成 / 校验能力以题型插件化组织，后续题型（拖拽点选、语序点选、PoW 无感）可插拔扩展；
3. 全部场景开关（登录 / 注册 / 重置密码 / 绑定邮箱 / 绑定手机 / 邀请接受）复用既有机制，图片与交互式可切换；
4. 前端复用已有 `ReSliderCaptcha` 基座，新增旋转 / 点选组件，登录页与验证码发送组件统一接入；
5. 答案永不出服务端，配套一次性 ticket、TTL、尝试上限、轨迹启发式与限流五层防护。

**非目标**

- 不做行为风控评分 / 免验证（risk-based）与设备指纹（预留扩展位，见 §十）；
- 不接任何商业打码 / 云验证码服务（离线私有化是本项目底线）；
- 不动短信 / 邮箱验证码链路（`auth_verify_code_*`）；不改既有图片验证码对外契约。

**术语对齐**（已确认）：「滑动」= 滑动拼图；「滚动」= 旋转回正（拖动滑杆把预旋转图片转正）；「点动」= 文字点选（按顺序点击图中文字）。

## 二、现状盘点（两仓事实）

### 2.1 后端（xadmin-server）

- **独立 `captcha` app**：`captcha/models.py` 的 `CaptchaStore`（DB 表，非 Redis）+ `captcha/utils.py` 的 `CaptchaAuth`（generate/valid，一次性原子消费）+ `captcha/services.py` 契约层（跨 app 只许导入 `CaptchaAuth`）+ `captcha/views.py`（PIL 渲染 PNG、410 Gone、每 IP 60/min 限流）+ `captcha/helpers.py` 题目生成器（算式 / 随机字符）+ `captcha/fonts/Vera.ttf`（字体随 app 内置的先例）。

- **E2E 现状**：`tests/settings_e2e.py` 直接关闭图片验证码（`SECURITY_LOGIN_CAPTCHA_ENABLED = False`），注释明言「图片验证码无法自动识别」。

### 2.2 前端（xadmin-client）

## 三、开源调研

### 3.1 项目对比

| 项目 | 语言 / License | 题型 | 校验模型 | 可借鉴点 |
|------|----------------|------|----------|----------|
| [AJ-Captcha](https://gitee.com/max911/captcha)（anji-plus） | Java / MIT | 滑动拼图 blockPuzzle、文字点选 clickWord | `POST /captcha/get` 返回底图 / 滑块图 base64 + token，答案存 Redis；`POST /captcha/check` 提交坐标（前端 AES 加密）→ 通过后 token 进入二次校验态，随登录表单提交再验一次 | **两段式协议 + 二次校验 ticket** 模型（本方案采用）；滑动容差 `slip-offset=5px`；同用户错误 N 次才弹码、5min 限 100 次 get 的防刷建议；**坑**：点选需 Linux 装中文字体 |
| [tianai-captcha](https://github.com/dromara/tianai-captcha)（dromara） | Java（另有 Go 版）/ MulanPSL-2.0 | 滑块 SLIDER、旋转 ROTATE、滑动还原 CONCAT、文字点选 WORD_IMAGE_CLICK、PoW | 生成器 / 校验器 / 资源管理器**可插拔**；缓存抽象（内存 / Redis 可换）；客户端上报 `ImageCaptchaTrack` 轨迹参与校验 | **题型插件化架构**（本方案采用）；底图规范 600×360、滑块模板 110×110、旋转图 200×200；默认容错 0.02（相对底图宽）；轨迹校验思路；官方 web SDK（vue/react 原生） |
| [go-captcha](https://github.com/wenlng/go-captcha) | Go / Apache-2.0 | 点选（文本 / 图形）、滑动（基本 / 拖拽）、旋转、拖拽点选 drag-dot | 生成主图 + 缩略图 + dot/块数据结构；配套 `go-captcha-service` 独立服务（存储 / TTL / 重试计数） | 点选双模式（字符 / 图形图标）与 drag-dot 题型定义；主图 / 提示图双图协议 |
| [ALTCHA](https://altcha.org) / [Cap](https://trycap.dev) | 多语言 / MIT | 工作量证明（PoW）无感验证 | 前端算力证明 + 服务端验签，无图片交互 | 远期「无感模式」候选（tianai 也已内置 POW 题型可参照），本期不做 |
| django-simple-captcha 等 Python 生态 | Python | 仅图片字符 | DB / 缓存 | **Python 侧无成熟的滑 / 旋 / 点选库** → 生成器需 Pillow 自研（算法均为公开几何操作：遮罩裁切、旋转、文字绘制，无专利与实现壁垒） |
| vben（本地参照 `vue-vben-admin`） | Vue3 / MIT | 滑条、旋转、拼图、点选四组件（`packages/effects/common-ui/src/components/captcha/`） | **全部纯前端自校验**（答案在浏览器内，脚本可直接绕过），点选组件仅收集坐标不判定 | **仅作交互参照**：拖杆手感、300ms 回弹复位、点选编号标记与 `{x,y,t}` 带时间戳采集；安全边界必须放服务端 |

### 3.2 调研结论（选型决策）

1. **后端自研 + 协议借鉴**：题型插件架构学 tianai（生成器 / 校验器可插拔），两段式协议与 ticket 学 AJ-Captcha 的二次校验模型；不新增任何运行时第三方依赖（Pillow 已在用）。
2. **存储走 Redis 缓存**（django-redis），挑战是 2 分钟生命周期的短命数据，与既有 `oauth_state` / passkey challenge 同类；既有 DB 版 `CaptchaStore` 仅为图片验证码保留，不动。
3. **不做前端坐标 AES 加密**（AJ-Captcha 有此层）：其价值主要是防传输篡改 / 明文重放，本方案以「一次性 ticket + 短 TTL + 服务端容差 + 轨迹校验」覆盖同类威胁且交互面更小；若评审要求，可在 verify 请求加 HMAC 签名位（`common/base/crypto.py` 已有基座），协议留扩展位。
4. **前端交互复用自有基座**：`ReSliderCaptcha` 已具备服务端判定模式与键盘可达；旋转 / 点选组件参照 vben 交互（MIT 可移植）+ 服务端图源改造；不引入第三方验证码前端包。

## 四、题型与交互设计

三题型统一交互框架：挑战弹层内含题目区 + 操作区（滑杆或点击区）+ 刷新按钮 + 结果反馈（成功态动画 / 失败抖动后自动换题）；同一挑战内最多尝试 3 次，超次或过期即作废换题。

| 题型 | 玩法 | 服务端生成 | 校验口径（默认值，均可配） |
|------|------|-----------|---------------------------|
| slide 滑动拼图 | 拖动滑块，把拼块横向拖入底图缺口 | 底图随机位置开拼图形状缺口（内阴影），拼块以**同尺寸透明画布 PNG** 返回（拼块绘在其真实 y 上，前端只需水平拖动，不泄漏 y 之外的任何信息） | 提交 `x`，`|x - 秘密x| ≤ 4px`（AJ 默认 5px / tianai 相对容差取严） |
| rotate 旋转回正 | 拖动滑杆，把预旋转的方形图转回正向 | 底图近方形裁切后随机预转 θ（避开 ±0°/±180° 平坦区） | 提交 `angle`，`|angle - θ| ≤ 4°` |
| click 文字点选 | 按提示条顺序依次点击底图中 3 个文字 | 底图上绘制 3 个常用汉字（随机字号 / 微旋转 / 干扰色，位置防重叠采样）；提示条单独渲染为**图片**（与 vben `hintImage`、AJ 点选一致，防 OCR 直接读出指令） | 提交有序 `points`，逐字命中半径 ≤ 20px 且顺序一致 |

**无障碍口径**：拼图 / 点选依赖指针操作，无法键盘完成；保留「切换为图片验证码」的显式入口（图片码 + 其音频链路 `captcha_audio` 即无障碍回退），在弹层头部提供切换按钮。键盘用户路径 = 切图片码，不另造键盘版拼图。

## 五、接口协议（契约先行，两段式 + 一次性 ticket）

### 5.1 能力发现（扩展既有端点）

`GET /api/identity/auth/capabilities` 各场景节点扩展：`captcha: true` 语义不变，新增 `captcha_types: ["slide","rotate","click"]`（mode=interactive 时后端从启用题型集返回；mode=image 时为空）。前端据此选择预渲染组件。

### 5.2 新端点（挂 `identity/urls.py` 的 `no_auth_url`，对齐登录端点匿名惯例）

```
POST /api/identity/auth/captcha/challenge     # 获取挑战
POST /api/identity/auth/captcha/verify        # 校验并换 ticket
```

**challenge 请求** `{type?: "slide"|"rotate"|"click", scene: string}`——`type` 缺省由服务端从启用集随机；`scene ∈ login|register|reset|bind_email|bind_phone|invite`。

**challenge 响应**（答案字段一律不出现）：

```jsonc
// slide
{ "challenge_id": "…", "type": "slide", "background": "<base64 png 320×180>",
  "piece": "<base64 png 320×180 透明画布>", "ttl": 120 }
// rotate
{ "challenge_id": "…", "type": "rotate", "background": "<base64 png 240×240 已预转>", "ttl": 120 }
// click
{ "challenge_id": "…", "type": "click", "background": "<base64 png 320×180>",
  "tip": "<base64 png 提示条>", "ttl": 120 }
```

**verify 请求** `{challenge_id, type, scene, answer, track?}`：

```jsonc
// answer 按题型：slide {"x": 187}；rotate {"angle": -42}；click {"points": [{"x":81,"y":64},{"x":…},{"x":…}]}
// track：拖动采样 [{x,y,t}…]（pointercmove 采样，≥2 点），click 为逐次点击的 {x,y,t}
```

**verify 响应**：成功 `{passed: true, ticket, expires_in: 120}`；可重试失败 `passed: false, attempts_left: n`（HTTP 200，不区分具体失败原因，防探测）；挑战未知 / 过期 / 已耗尽 → HTTP 400 + 错误码 `captcha_invalid` / `captcha_exhausted`（错误文案走 `_()` + zh 词条门禁）。

### 5.3 ticket 与业务消费

- verify 通过签发**一次性 ticket**（随机 ≥32 字节，服务端只存其哈希），TTL 120s，绑定 `scene`；
- 业务请求携带 `captcha_ticket`：`POST /api/identity/login/basic`、注册 / 重置 / 绑定（`ReSendVerifyCode` 的 `formatSendData`）、邀请接受等现有请求体新增该字段；
- 服务端在 `check_token_and_captcha` 同位置扩展：mode=interactive 时消费 ticket（`atomic_get_delete` 一次性），scene 不匹配即拒绝；
- **兼容**：`captcha_key + captcha_code` 字段与图片码链路原样保留；两套凭据二选一，按场景配置决定。

## 六、后端详细设计

### 6.1 模块结构（扩展既有 `captcha` app，参照 `mfa/backends/` 多后端布局）

```
captcha/
  backends/
    base.py        # ChallengeBackend 抽象（generate/verify/answer 校验）+ 注册表 + get_backend(type)
    slider.py      # 滑动拼图生成（Pillow jigsaw 遮罩模板 ×3~4 种）与校验
    rotate.py      # 旋转生成（近方形裁切 + 预转）与校验
    wordclick.py   # 文字点选生成（常用字采样绘制 + 提示条）与校验
    track.py       # 轨迹启发式校验（点数 / 时长 / 瞬移检测）
  serializers.py   # ChallengeIn / VerifyIn / ChallengeOut（DRF，extend_schema 供 OpenAPI）
  views.py         # 扩展：CaptchaChallengeView / CaptchaVerifyView（匿名 + 限流）
  cache.py         # 挑战 / 尝试计数 / ticket 存取（集中放键名与 TTL，见 §6.4）
  const.py         # CaptchaScene / CaptchaType 常量与场景映射
  services.py      # 契约层扩展导出 InteractiveCaptcha（challenge/verify/consume_ticket）
  resources/
    backgrounds/   # 底图包（CC0，≥12 张）+ 资源清单文件；程序化渐变 + 噪声图兜底
    fonts/         # 中文字体子集（常用 3500 字，OFL 许可，~1~2MB；app 内置先例 Vera.ttf）
identity/
  views/auth/captcha_challenge.py  # identity 侧薄视图（对齐 CaptchaAPIView 包 CaptchaAuth 的分层）
  utils/auth/captcha.py            # check_token_and_captcha 扩展 ticket 分支
```

行数红线：单文件 ≤ 500 行 / 单函数 ≤ 100 行，`slider.py` 的绘制逻辑注意拆分纯函数（对齐前端 geometry 拆分思路，便于表驱动测试）。

### 6.2 生成器要点（Pillow）

- **滑动**：缺口随机 `x ∈ [0.25w, 0.9w]`、`y ∈ [0.15h, 0.75h]`；拼图形状用预置 alpha 遮罩模板（圆角方块 + 上下凸钮，3~4 种轮换防形状指纹）；缺口绘制半透明深色内阴影，拼块叠加高光描边；全图加轻噪点 / 扫描线防模板匹配；输出底图（含缺口）与同尺寸透明画布拼块两张 PNG。
- **旋转**：从底图中心裁近方形，`rotate(θ, resample=BICUBIC)` 预转输出；θ ∈ [15°, 345°] 且距 0°/90°/180°/270° ≥ 15°（避免接近摆正角的歧义区）。
- **点选**：字符集取常用 3500 字表（配置 `CAPTCHA_CLICK_CHARSET` 可切 ascii），3 字去重、避混淆集（如「己已巳」）；泊松采样保证字间 / 边距 ≥ 48px；逐字随机字号 28~40、旋转 ±25°、颜色在底图对比度安全带内取值；提示条按用户点击顺序渲染同字号文字条。启动时字体缺失即 fail-fast（对齐本项目服务端 fail-fast 风格），不允许静默降级成英文点选。
- **尺寸**：默认底图 320×180 / 旋转 240×240（对齐登录卡片宽度），进 `settings_defaults` 可调。

### 6.3 校验与风控（五层）

1. **容差判定**：§四 表格口径，全部服务端；
2. **尝试上限**：每挑战 ≤ 3 次（Redis 计数），超次即删挑战；
3. **TTL**：挑战 120s、ticket 120s（均短于图片码的 `CAPTCHA_TIMEOUT=5min`——交互式应更短，可配）；
4. **轨迹启发式**（`track.py`，可关）：点数 ≥ 2（点选 ≥ 3）；总时长 ∈ [80ms, 60s]；
   相邻采样点位移速度 > 50px/ms 判「瞬移」（只拦坐标瞬移脚本，不误杀快速拖动 / 慢速点选）；
   不匹配即判败且**不返回具体原因**；
5. **限流与锁定**：challenge 每 IP 30/min、verify 每 IP 60/min（复用 `allow_by_ip` 固定窗口，与 `captcha/views.py` 现行 60/min 同范式）；verify 耗尽可联动 `LoginBlockUtil`（默认关闭，配置位预留）。

另：同 IP「未消费 ticket 数」≤ 3（防囤 ticket 后慢速重放）；verify 请求对 `challenge_id` 不可枚举（uuid4）。

**交付后补漏**

- **滑动拼图块不可见**：后端拼块画布原本按秘密 x 绘制整幅图，前端又按拼块尺寸缩放整幅
