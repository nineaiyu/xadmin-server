## 一、背景与定位

UI 一致性重构（批次一~五 + 复核）解决了「同类页面两种做法」「颜色/字号不跟主题」的问题，
得到的是**结构一致、主题正确**的基线；但观感层面仍存在三类空间：

1. **视觉资产缺位**：无统一空态/骨架组件（`el-empty` 裸用 35 个文件、`el-skeleton` 仅 1 处）、
   无卡片视觉体系（圆角/阴影/hover 微交互不统一）、图表观感朴素（直角柱、无渐变、tooltip 样式零散）；
2. **重页观感集中落后**：大屏 `display.vue` 是全站唯一大面积写死灰阶的自绘页（emoji 控制键、无缩放适配）；
   错误页/空白页氛围弱；聊天/AI 控制台面板层次单薄；
3. **收尾残留**：零散写死样式（`lay-panel` hover 色、`ReAnimateSelector` 边框色、`empty` 页背景）、
   同一语义多套图标（上传 3 套 / 更多 2 套）、页面过渡无差异化（`meta.transition` 零配置）。

框架与性能侧，基础设施（连接池 / pg_trgm 索引 / 缓存键审计 / N+1 防护 / k6 基线 / perf 基线）已就绪，
但存在**可实测的收益点**与**观测缺口**：Element Plus 仍占首屏闭包 44%（236 KB gzip）、
元数据 `_with_meta` 变体比普通变体慢 2.6×（k6: 203.8ms vs 78.3/81.5ms）、perf 基线仅覆盖 3 页、
未使用依赖残留（`vue-virtual-scroller`）。

二开体系（模块裁剪六层 / `generate_crud` / `generate_module` / cookbook / demo 官方示例 / 教程）已成体系，
但**缺一次「从零到可用」的端到端实战验证**：以真实业务诉求走完整链路，才能暴露生成器/脚手架/文档的最后一公里问题。

本计划的实施纪律沿用既有红线：**新功能 100% 携带测试**；契约改动先行；视觉改动必须过视觉基线 +
a11y + CLS 三道判据；性能改动必须有前后实测对比；不引入新依赖（除明确登记）。

### 3.2 框架与性能优化

| # | 项 | 现状 | 目标 | 判据 / 风险 |
|---|----|------|------|-------------|
| P1 | Element Plus 首屏体积 | 组件级按需注册（含逐组件样式，全量 CSS 已替代）；JS chunk 236 KB gzip（占闭包 44%）；CSS 322 KB 未压缩 | 低频组件（ColorPicker / Cascader / Splitter / Tour 等）**页面级引入**试点，从全局注册下沉；实测闭包降幅 | 收益须实测（目标 ≥8 KB gzip，否则回滚并登记）；`elementPlus.spec.ts` 用法扫描守护需同步口径；el-* 解析回归风险 |
| P2 | 元数据 `_with_meta` 性能 | k6 变体差 2.6×（203.8ms vs 78.3/81.5ms，同端点）；需剖析三项元数据的装配成本 | 剖析后优化（查询合并 / 序列化裁剪 / 缓存），k6 复测 | 元数据是核心契约（`metadata-protocol.md` + 契约守护），失败即回滚；只做不改语义的优化 |
| P3 | perf 基线扩页 | 3 页（login / welcome / system-user） | 增补监控页（echarts+轮询）/ 操作日志（长列表）/ 大屏（懒加载全屏图表），基线入库 | 采集口径与现有三页一致（TTFB/FCP/LCP/CLS + `cls_top`） |
| P4 | 未使用依赖清理 | `vue-virtual-scroller` 在 `package.json` 与 `build/optimize.ts` 预构建中残留，`src` 零使用 | 移除依赖与预构建项；同步 lockfile | 删除前全仓复核（含 `e2e/`、`scripts/`）；`pnpm audit` 保持 0 |
| P5 | 路由级预取（二次导航提速） | 无任何 `prefetch/preload`（仅 Vite modulepreload）；切换菜单等待目标 chunk | 侧栏/顶栏在**空闲时**预取高频目标页 chunk（`requestIdleCallback`，上限 3~5 个） | 不得争抢首屏带宽（空闲触发 + 上限）；不改变路由加载契约 |
| P6 | 评估项（先剖析后定） | 登录页 LCP 1320ms（显著高于其它页）；i18n chunk 55.9 KB（第二大 JS，zh 全量 eager） | 各自剖析并给出结论：能低风险优化则做，否则登记触发条件 | 登录链路（加密/限流/异步渲染）回归面大；i18n key 同步探测依赖 zh 全量，改造需先补替代机制 |

**P6 结论（2026-09-25，评估完成、不做改造）**：

- **登录页 LCP ≈1.2s 属 dev 链路基线**：`perf.e2e.ts` 跑的是 `pnpm dev`（未打包模块图 + 站点配置异步 + 登录表单异步渲染），生产链路已有 en 懒加载 / modulepreload / gzip 等主要杠杆；继续压 dev 基线收益不落到用户侧。→ 触发条件：**先落生产链路 perf 基线**（build + 静态服务，可复用 `scripts/csp-page-server.mjs` 形态）；LCP 持续 > 1.5s 或真实用户反馈登录慢时启动。
- **i18n chunk 55.9 KB**：已做 en 懒加载（约 −15 KB，首屏只带 zh）；zh-CN 是默认语言与源语言（`transformI18n` 同步 key 探测依赖），必须 eager。进一步收益只能裁剪**未静态引用词条**（zh 3008 条 vs 静态引用 2123 个，约 29%）——须先补「动态 key 审计」（`t()` 变量引用与后端下发键），属中风险改造。→ 触发条件：首屏闭包逼近预算上限，或词条体系重构窗口。
