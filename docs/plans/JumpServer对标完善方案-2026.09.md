## 一、背景与对标方法

### 1.1 为什么二次对标 JumpServer

2026-09 的《参考项目借鉴实施计划》已对 JumpServer 做过一轮机制级借鉴（[ADR-015](../adr/ADR-015-reference-project-adoption.md)：通知渠道约定式加载、密码安全套件、按权限反查审批人、内置角色 + post_migrate、分布式锁、内置对象删除保护），并明确了「不引入其体系性约定」的边界。本轮二次对标的依据：

1. **对标面变化**：JumpServer 近年在 AI（chat_ai / Kael 组件）、作业中心、标签体系、凭据托管上形成了成熟设计，与本仓 AI 助手（[ADR-047](../adr/ADR-047-ai-console-persistence-and-tools.md) / [ADR-048](../adr/ADR-048-ai-unified-tool-layer.md)）形成同层对标，可互证的机制更多；
2. **本仓阶段变化**：AI 统一工具层（60 动作 + MCP）、任务记录 + WS 日志、审计 diff 等底座已就绪，部分「当时无载体」的借鉴项现在有了落地条件（如工具面巡检、执行幂等）；
3. **纪律要求**：候选池条目启动前必须对账（[plans/README.md](README.md) 工作纪律红线 7）——本方案即本轮对账产物。

### 2.3 明确不适用与不引入

| 项 | 结论与理由 |
|----|------------|
| 资产 / CMDB / 节点树 / 平台包 | 领域不同（本仓非运维 PAM），不照搬「资产即配置」模型 |
| Web 终端 / 会话录像 / 协议代理（KoKo/Chen/Luna） | 领域不同 + 重依赖（xterm/协议栈），不引入 |
| 账号托管 / 自动改密 / Ansible 推送 | 领域不同；对应诉求由 P-3 凭据治理覆盖 |
| Org 多租户体系（OrgModelMixin / tmp_to_org） | 体系冲突（ADR-031 no-go；ADR-015 §2） |
| 无统一响应包装 / limit-offset 分页 | 体系冲突（本仓 ApiResponse + page/size；ADR-015 §2） |
| 独立 AI 服务（Kael，Go 组件） | 单机部署形态下分离的运维成本 > 收益；**登记触发条件**：多实例部署或 AI 并发成为瓶颈时评估「独立 AI worker / 网关」（见 §七） |
| Vault / KMS 外部密钥管理 | 触发条件：合规要求独立密钥托管时评估（当前 signer 本地加密 + 轮换工具足够） |
| 审计 ES / ClickHouse 后端 | 评估出口（触发条件：OperationLog > 2000 万行 或 审计检索 P95 > 1s） |
| 服务端无头浏览器 PDF（Playwright 渲染报表） | 重依赖（镜像 +300MB 级），不做；大屏导出走 U-5 前端轻方案 |
| 插件市场 / 业务模块军备 / 类 Excel 报表设计器 | 红线延续（长期优化方案附录 A） |
| CommandACL / ClipboardACL / ConnectMethodACL 等会话级 ACL | 终端会话领域（本仓无会话通道）；其中「高危动作拦截」诉求已由 412 审批协议覆盖 |
| `JSONManyToManyField`（规则化多对多：include / exclude / m2m_all） | 授权模型体系不同（本仓数据权限走 Q 编译器 + 字段权限），不引入 |
| 账号自动化编排（Ansible 触发式推送 / 改密 / 校验） | 领域不同；对应诉求由 F-6（风险巡检 + 处置）覆盖 |

## 三、增强项详述

### 3.1 AI 能力线

#### AI-1 模型能力画像与探测

| 项 | 内容 |
|----|------|
| 借鉴 | JumpServer `ChatAITestingAPI`：上线前强制模型调用一个 tool，无 `tool_calls` 返回即判定不支持 function calling；`ChatAIProviderMixin` 把供应商异常翻译为可读文案 |
| 现状 | `system/views/ai/profiles.py` 的测试动作只发一次 ping（`chat([{role: user, content: "ping"}])`）——只证明连通；模型能力（JSON 输出 / tool_calls / reasoning / vision）未知；`AiProfile` 全局至多一个激活档案供全部链路共用（问答 / NL / 动作 / 聊天），换模型即「静默失败」风险（已有实测教训：思考型小模型在 JSON 指令任务上必然空回答） |
| 做法 | ① 新增 `POST /api/system/ai/profiles/{pk}/probe`：按序探测四项能力——结构化 JSON（给 schema 要求输出并校验可解析）、`tool_calls`（携带一个内省用 tools 定义，期望 tool_calls 返回）、`reasoning`（观察 `reasoning_content`）、按需 vision；结果落 `AiProfile.capabilities`（JSON + 探测时间），探测不通过只提示不阻断；② 能力画像驱动链路选择：动作草稿 / NL 解释要求 JSON 能力、AI-2 要求 tool_calls 能力，不达标时前端给出明确提示与替代建议；③ `AiProfile` 增 `purpose`（`chat` / `structured`，默认 `chat`）：允许「问答用 A 档案、结构化链路用 B 档案」的组合配置，未配 `structured` 档案时回落激活档案（不强制拆分，单档案场景零变化） |
| 效果 | 「换模型就静默失败」变为「探测即知」；为 AI-2 提供准入判据；多模型组合可配（弱模型聊天 + 强模型结构化） |
| 优先级 · 批次 | P1 · 批二 |
| 工作量 · 依赖 | 中 · AI-2 的 tools 通道（JSON 能力探测可先行） |
| 风险 | 探测消耗少量 token（单次 <1K）；供应商差异导致误判 → 探测结果可人工覆盖（capabilities 允许手工修正） |

#### AI-2 原生 function calling 双轨

| 项 | 内容 |
|----|------|
| 借鉴 | Kael 由 OpenAPI schema 自动生成原生函数调用（工具定义来自 API schema，不手工维护两套） |
| 现状 | `common/sdk/ai/chat.py` 请求体只有 model / messages / 采样参数，**不下发 tools**；动作草稿走 prompt-JSON 协议（`build_draft_prompt` / `parse_draft`，`ALLOWED_ACTIONS_JSON:` 标记，E2E 桩依赖）；该协议经过 60 动作 + 多草稿串联验证，是稳定资产 |
| 做法 | ① SDK 扩展（不动既有契约）：`_body` 支持 `tools` / `tool_choice` 透传；新增 `chat_tools(messages, tools, **overrides) -> {content, tool_calls, usage}`（`chat()` / `chat_stream()` 签名与行为零变化）；② 工具定义转换层：现有 `tool_catalog`（`{name, description, inputSchema}`，已是 MCP 形态）→ OpenAI tools 格式（薄转换 + 单测，同一份 schema 三种消费：MCP `tools/list` / 助手页 `tools` / 原生 function calling）；③ 草稿链路双轨：`capabilities.tool_calls` 为真且开关开启 → 原生 tools 优先，解析结果映射为既有 `drafts` 结构；否则回落 prompt-JSON（存量桩 / E2E / 弱模型零破坏）；④ 审批、权限双门、审计链路零改动（复用 `execute_action` 唯一收口） |
| 效果 | 动作草稿成功率与多步串联稳定性提升；工具面与 MCP 生态同源；技术先进性（原生工具调用）与向后兼容兼得 |
| 优先级 · 批次 | P2 · 批二 |
| 工作量 · 依赖 | 中（SDK + 转换层 + 双轨分支 + 桩扩展）· AI-1 |
| 风险 | 各供应商 tools 实现参差 → 探测准入 + 回落兜底 + 双轨对照日志（同一请求可观测两条链路成功率） |

#### AI-3 工具面巡检 + OpenAPI AI 元数据

| 项 | 内容 |
|----|------|
| 借鉴 | JumpServer `CustomAutoSchema` 为每个 operation 注入 `x-jms-required-permissions` / `x-jms-permission-dynamic` / `x-jms-ai-guidance` / `x-jms-create-reuse`（让 AI 知道调什么、需何权限、参数怎么填）；`from_mcp` 模式剔除敏感 operation |
| 现状 | 60 个动作手工声明 + 守护测试（拼错可变红）；但「哪些端点可 AI 化而尚未注册」无巡检——注册表维护靠记忆；`openapi.json`（静态产物 + `/api-docs/`）无 AI 可发现性元数据；生成器 `generate_crud` 产物不含 AI 动作声明 |
| 做法 | ① 新增 `manage.py ai_tool_audit`：路由面（`build_route_index`，已有工具）× 声明面比对，输出「未注册候选清单」（按 domain 分组、标注读/写与危险方法）；默认只报告，`--fail-on-gap` 可选入 CI（避免强迫注册无意义动作）；② drf-spectacular `AutoSchema` 扩展：ViewSet 声明 `ai_meta = {"visible": ..., "guidance": ..., "requires_approval": ...}` 时注入 `x-ai-*` 扩展字段，静态 `openapi.json` 与 `/api-docs/` 同步带出；③ 与 E-3 联动：`generate_crud` 产物默认带 `ai_api_actions` 只读动作声明骨架（list / detail），写动作以注释给出，产物过 `ai_tool_audit` 与 `doctor` |
| 效果 | 工具目录维护从「记忆驱动」变「巡检驱动」；新模块出生即被 AI 面感知；外部集成（MCP 客户端 / 二开脚本）读到权威元数据 |
| 优先级 · 批次 | P2 · 批二 |
| 工作量 · 依赖 | 中 · 无 |
| 风险 | 候选清单噪音（内部端点）→ 巡检支持豁免清单（与权限点 `EXCLUDE_PERMISSION_NAMES` 同口径） |

#### AI-4 AI 动作执行幂等

| 项 | 内容 |
|----|------|
| 借鉴 | RuntimeStore 的 `commit_id` 幂等提交（重试返回同一结果）+ HMAC receipt 收据（写操作可验证）；「一次操作、一张审批单」的穿透口径（ADR-048 已落地） |
| 现状 | `execute_action` 唯一收口 + 412 审批令牌一次性；但草稿重复提交（用户连点 / 网络重试 / 双端同开）可能造成重复写入；MCP `tools/call` 亦无幂等键 |
| 做法 | ① 草稿携带 `draft_id`（动作序列 + 参数的稳定哈希）：`action/execute` 在 TTL（建议 10 分钟，与审批令牌口径对齐）内去重，命中返回首次执行结果 + `deduplicated: true`；② MCP 通道同口径（JSON-RPC id + 参数哈希）；③ 幂等记录落审计（AI 动作审计补 `draft_id` 字段，便于追溯「同一次意图」的所有请求） |
| 效果 | AI 写操作「不重不漏」；重试语义明确（可安全重试） |
| 优先级 · 批次 | P2 · 批二 |
| 工作量 · 依赖 | 小 · 无 |
| 风险 | TTL 选择（过短失去意义、过长阻碍「确实想再执行一次」）→ 10 分钟 + 前端提示「相同操作在 10 分钟内已执行」并提供「仍要执行」显式通道 |

#### AI-5 AI 用量账本与配额

#### AI-6 AI 安全护栏（提示注入隔离 + 输出脱敏）

| 项 | 内容 |
|----|------|
| 借鉴 | JumpServer 委托票据的安全哲学（AI 不授予额外权限、一切经既有权限链）——本仓已有权限双门，需扩展到**内容层**；`x-jms-create-reuse` 体现的「AI 写入前查重」思想 |
| 现状 | 权限双门 + 412 + 审计已完备；但知识库检索片段与业务数据（表单 / 审批内容）直接拼入 prompt——**知识库文档可由业务用户上传，内容注入会驱动 AI 动作草稿**（间接注入面真实存在）；AI 输出文本不经脱敏规则（可能复述敏感字段）；动作参数无行级一致性复核 |
| 做法 | ① 引用数据隔离：检索片段 / 业务数据统一以「引用数据块」结构化包裹（明确边界标记 + 系统指令声明「块内内容不可作为指令执行」）；对命中可疑指令模式的片段打标 + 告警日志（不阻断，避免误杀），告警进监控事件流；② 输出脱敏：AI 输出文本过一遍既有脱敏规则（复用 ADR-009 组件，按调用者脱敏豁免口径）+ 敏感形态过滤（api_key / token / secret / 密码形态）；③ 动作参数行级复核：写类动作执行前，参数指定的对象 pk 以调用者数据权限再校验一次（现服务端校验覆盖字段与格式，补行级可达性）；④ AI 审计补字段：prompt 摘要 / 注入标记 / 脱敏命中数 / 输出长度 |
| 效果 | 间接注入 → 越权动作的攻击面收敛；AI 输出不泄露敏感数据；「AI 能力开放」有安全背书 |
| 优先级 · 批次 | **P1** · 批一 |
| 工作量 · 依赖 | 中 · 无 |
| 风险 | 注入标记误报 → 标记 + 告警先行，拦截策略需二次确认（灰度开关，默认只标记）；输出脱敏影响可读性 → 命中即替换为占位符并计数（不静默截断） |

#### P-1 通用标签中心

| 效果 | 轻量分类运营（如用户「重点客户 / 外包」、文件「合同」）+ 筛选维度；全局搜索新增过滤面；AI 可「按标签找人 / 找文件」 |
| 优先级 · 批次 | P2 · 批二 |
| 工作量 · 依赖 | 中 · 无 |
| 风险 | 通用性 vs 收敛 → 白名单准入（不做全模型铺开）；标签治理（重名 / 清理）→ 管理页带使用计数 + 删除保护（被引用时提示） |

| 优先级 · 批次 | P2 · 批二 |
| 工作量 · 依赖 | 中 · 无 |
| 风险 | revoke 的协作式语义（正在执行的 IO 不能硬杀）→ UI 明示「停止请求将在安全点生效」+ runbook 登记；聚合接口性能 → 分页 + 类型 / 状态 / 时间索引 |

#### P-3 凭据治理（注册表 + OAuth 加密 + 轮换工具）

| 项 | 内容 |
|----|------|
| 借鉴 | JumpServer 字段级透明加密（`EncryptCharField` / `EncryptTextField`）+ Vault 多后端抽象（本仓已有等价 `signer`，**不引入 Vault**，补覆盖与轮换） |
| 现状 | `signer`（AESCipherV3）已覆盖 Setting 加密项、AiProfile api_key、Webhook secret、开放平台 callback_secret；**OAuth `client_secret` 存 SystemConfig JSON 明文（仅 `mask_providers` 掩码展示）**；无「敏感键必须加密」的守护；无统一凭据页与轮换机制 |

| 效果 | 明文敏感键清零、可守护；安全审计可回答「密钥在哪、是否加密、多久轮换」；为「密钥轮换演练」提供工具面 |
| 优先级 · 批次 | **P1** · 批一 |
| 工作量 · 依赖 | 中 · 无 |
| 风险 | 加密迁移需回滚预案 → 先「兼容读取」（密文 / 明文双读），后停明文；轮换操作需二次确认（高危动作纳入 MFA 动作清单复核） |

#### P-5 审计归档与冷热分层

| 做法 | ① 审批实例讨论区：评论（参与人 = 申请人 / 当前处理人 / 历史处理人 / 抄送人），支持 @ 提醒（复用聊天室提及口径）；② 抄送人：流程节点级默认 + 发起时追加，站内信 + 邮件通知（复用订阅矩阵）；③ 处理人快照：审批任务落 `assignee_display`（昵称快照）；④ 时间线合并展示（评论 / 审批动作 / 转交 / 加签同一时间轴）；⑤ 邮件内一键审批（可选开关，默认关：通知邮件带一次性 token 直达审批，时效 ≤1h + 只读确认页 + 全留痕，仅限单步通过 / 驳回） |
| 效果 | 审批沟通单内闭环（「补充说明」「请提供附件」不再走 IM）；留痕完整可追溯 |
| 优先级 · 批次 | P2 · 批三（③ 快照并入批一 U-1 一起做） |
| 风险 | 评论可见性边界 → 与实例可见性同口径（`visible_instances_for`）；通知噪音 → 评论默认仅 @ 提醒（按订阅矩阵分发） |

#### F-6 账号安全风险巡检（发现 → 处置 → 留痕）

| 项 | 内容 |
|----|------|
| 借鉴 | JumpServer `RiskChoice`（弱密码 / 泄露 / 重复 / 长期未改 / 长期未登录等风险项）+ `RiskHandler`（忽略 / 重开 / 关闭 / 禁用 / 改密 + 全留痕） |
| 现状 | 检测能力已有（`check_leak_password` + 泄露库、`check_history_password`、`is_password_expired`），但只发生在**登录时被动拦截**；无巡检清单、无处置动作、无「当前风险全景」可交卷 |
| 做法 | ① 周期巡检任务（`register_as_period_task` 注册）：弱密码 / 泄露库命中 / 长期未改密 / 长期未登录 / 管理员未绑 MFA / 超管数量异常；② 「账号安全」清单页：按风险等级汇总 + 逐项处置（通知本人 / 强制改密 / 停用 / 标记豁免）；③ 处置动作与状态全留痕（复用审计口径）；④ 检测函数与登录拦截**同源共用**（避免「巡检说没问题、登录被拦」） |
| 效果 | 安全运营从「被动拦截」到「可盘点、可处置、可交卷」；管理员未绑 MFA 等隐患暴露 |
| 优先级 · 批次 | P2 · 批三 |
| 风险 | 误报（长期未登录 ≠ 风险）→ 分级 + 豁免机制；扫描性能 → 分批 + 非高峰执行 |

#### F-7 登录访问策略（时段 / 网段 × 角色）

| 项 | 内容 |
|----|------|
| 借鉴 | JumpServer `LoginACL`（用户 + IP + 时段限制登录，action = accept / reject / review）+ `LoginIpBlockUtil` |
| 现状 | 全局 IP 黑白名单 + 失败锁定 + 异地 / 新设备提醒（默认只提醒不阻断）；**无按角色 / 时段 / 来源网段的登录策略**——「仅工作时间可登录」「仅办公网段可登录管理端」类需求无法配置 |
| 做法 | ① 策略模型：适用对象（用户 / 角色 / 全体）× 条件（周期时段 / 来源网段）× 动作（拒绝 / 要求 MFA / 仅记录）；② 命中执行（拒绝 → 登录失败文案说明策略；要求 MFA → 走既有 MFA 链路）；③ 命中记录进登录日志并纳入安全巡检统计；④ 并发会话限制（单设备登录可配，复用 `UserSession` 基建强制下线旧会话）；⑤ 管理页 + 内置模板 |
| 效果 | 内网合规场景可配；比「一刀切 IP 黑名单」精细（可与数据权限/字段权限形成完整防线） |
| 优先级 · 批次 | P2 · 批三 |
| 风险 | 误配置导致全员登不上 → 保存前「命中预演」（输入样例用户 / IP 看判定结果）+ 超管豁免防自锁 + 策略变更审计 |

#### F-8 文件访问审计 + 上传安全策略

| 项 | 内容 |
|----|------|
| 借鉴 | JumpServer `FTPLog`（文件传输日志：谁传了什么）+ 上传策略 |
| 现状 | 图片有扩展名白名单 + 魔数校验 + 重编码（`common/fields/image.py`）；通用文件仅大小 / 配额 / md5 去重；**下载行为不落审计**（`API_LOG_METHODS` 仅记写方法，GET 下载不入 OperationLog）——「谁下载了合同」查不到 |
| 做法 | ① 文件操作日志（上传 / 下载 / 预览 / 删除：操作人 / 时间 / 文件 / 来源 IP / 结果），文件详情页加「访问记录」页签（含下载次数）；② 上传策略（扩展名 + MIME 白名单，按目录 / 用途配置，fail-closed）；③ 敏感文件下载告警（可选：高频下载 / 非工作时段触发站内提醒）；④ 保留期随审计口径统一 |
| 效果 | 文件流转可追溯；上传面可控（防可执行文件 / 脚本上传） |
| 优先级 · 批次 | P2 · 批三（安全） |
| 风险 | 日志量（下载高频）→ 只记元数据 + 保留期 + 按需开关；**病毒扫描不引入**（登记触发条件：合规要求时评估侧车方案） |

#### F-9 WebAuthn / Passkey 与「认证方式策略」

| 项 | 内容 |
|----|------|
| 借鉴 | JumpServer Passkey（WebAuthn / FIDO2）MFA + `SECURITY_MFA_METHODS` 白名单 + 用户级 `allowed_mfa_types` 只能收窄 |
| 现状 | MFA 支持 OTP / 邮箱 / 短信等（四后端）+ 412 二次确认；**无 WebAuthn / Passkey**；登录方式无按角色限制（管理员与普通用户同策略） |
| 做法 | ① MFA 后端新增 WebAuthn（注册 / 挑战 / 验签），既可独立登录也可作为 412 二次确认方式；② 「认证方式策略」：全局允许集（配置）+ 角色级收敛（如管理员必须 MFA、禁用短信 MFA）+ 用户级只能收窄（`allowed_mfa_types` 已有范式）；③ 前端注册 / 登录流程 + Passkey 设备管理（多凭证 / 撤销） |
| 效果 | 抗钓鱼认证（现代安全标配）；「管理员强制 MFA」可落地 |
| 优先级 · 批次 | P2 · 批三 |
| 风险 | 浏览器兼容（WebAuthn 需 HTTPS 形态）；新增 `webauthn` 依赖（纯 Python，体积小）；降级路径保留（不绑 Passkey 的用户不受影响） |

#### F-10 标准 OIDC 单点登录

| 项 | 内容 |
|----|------|
| 借鉴 | JumpServer CAS / OIDC / SAML 标准协议支持 |
| 现状 | 有 OAuth2 型通用 provider（authorize / token / userinfo）与 IM 扫码；未见标准 OIDC discovery 与 `id_token` 验签（属「准 OIDC」）；CAS / SAML 无 |
| 做法 | ① 标准 OIDC provider：`/.well-known/openid-configuration` discovery + `id_token` JWKS 验签 + claims → 用户字段映射 + 组 → 角色映射（复用 LDAP 组映射口径）；② 登录开关 + 失败可诊断（复用 oauth-login 排错章节口径）；③ CAS / SAML 维持评估出口（触发条件：真实 IdP 仅支持该协议） |
| 效果 | 与企业标准 IdP（Keycloak / Auth0 / Entra ID）直接对接 |
| 优先级 · 批次 | P3 · 批四（触发制：企业 IdP 对接诉求） |
| 风险 | 各 IdP claims 差异 → 映射可配 + 排错日志；安全 → state / nonce / 验签全链路与既有 OAuth 同口径 |

#### F-11 开户体验（随机密码 / 邀请激活 / 账号有效期）

| 项 | 内容 |
|----|------|
| 借鉴 | JumpServer 随机密码规则（`SecretWithRandomMixin`：长度 / 大小写 / 数字 / 符号）+ 用户邀请（invite）+ 用户有效期（`date_expired` + 到期提醒） |
| 现状 | 随机密码函数存在（`common/utils/random.py::random_string`）但仅用于验证码；建号 / 重置密码界面需管理员手输或自己想密码；无「邀请激活」流程；**用户无有效期字段**（临时 / 外包账号只能靠人工记着停用） |
| 做法 | ① 用户创建 / 重置密码弹窗「生成随机密码」按钮：按安全策略规则生成 + 一键复制（**速赢小项，可随批一**）；② 邀请开户（可选开关）：创建用户时选「邀请激活」→ 邮件邀请链接（时效令牌）→ 用户自行设置密码（管理员不再知晓密码），邀请状态可见（待接受 / 已激活 / 过期重发）；③ 账号有效期：可设到期时间 + 到期前 N 天提醒（站内信 + 邮件）+ 到期自动停用（定时任务），与登录拦截口径同源 |
| 效果 | 开户更安全（管理员不掌握最终密码）；临时账号生命周期自动化（到期即停 + 提前提醒） |
| 优先级 · 批次 | P3 · 批四（随机密码按钮随批一） |
| 风险 | 邀请依赖邮件渠道可达性 → 未配 SMTP 时入口隐藏（fail-closed 提示）；有效期误设导致业务账号被停 → 到期双通道提醒 + 超管可批量延期 |

#### F-12 列表关联计数声明式

| 项 | 内容 |
|----|------|
| 借鉴 | JumpServer `RelationCountMixin`（列表附带关联计数） |
| 现状 | 部分手写：部门 `user_count`（`AnnotateUserCountMixin` 预聚合）、字典 `children_count`、审批 `node_count`、公告已读数；**角色行无用户数、数据集无卡片数**等常用列表无计数 |
| 做法 | 序列化器 / 视图声明 `relation_count_fields`（字段 → 关联查询 + 条件），列表统一一次聚合产出（Count 子查询，杜绝 N+1）；补齐角色 / 数据集等常用列表；计数可点击（跳转带筛选的关联列表） |
| 效果 | 列表信息量提升；「这个角色 / 数据集能删吗」一眼有数（与 F-2 影响面**同计算器复用**） |
| 优先级 · 批次 | P3 · 批四（小项） |
| 风险 | 声明过多影响列表性能 → 只对已声明字段计数 + 索引保障 + 上限约束 |

#### F-13 API 查询能力（受控 lookup 透传 + 字段子集）

| 项 | 内容 |
|----|------|
| 借鉴 | JumpServer `LookupFilterBackend`（`field__icontains / startswith / in` + 多值 any/all + 否定 `!=`）+ `QueryFieldsMixin`（`?fields=` 字段子集） |
| 现状 | 过滤基于 django-filter 逐视图显式声明（`BaseFilterSet` 提供时间区间 / pk / creator / description icontains）；不支持通用 `field__lookup` 透传与 `fields` 子集——新页面加筛选需后端逐个声明 |
| 做法 | ① `BaseFilterSet` 扩展「受控透传」：字段白名单取自元数据 `search_fields`，允许的 lookup 限定 `exact / icontains / startswith / in / gte / lte / isnull`（**禁跨关系、禁未声明字段**）；多值与否定的声明式支持；② `?fields=` 子集：与字段权限求交集（只收窄不提权），供列表 / 详情 / 开放平台使用；③ 前端「高级筛选」按需接入（不强制） |
| 效果 | 二开与开放平台 API 灵活度提升（少写后端代码）；大列表 / 集成场景 payload 可控 |
| 优先级 · 批次 | P3 · 批四（评估优先：先在 2 个页面试点） |
| 风险 | 过滤侧信道（用无权字段过滤探测数据）→ 严格白名单 + 字段权限叠加 + 渗透用例守护（无权字段过滤必须 400 / 403 而非空集）；lookup 注入 → 禁 `__` 嵌套 + 参数化 |

## 五、预期效果与 KPI（增量）

> 基线口径以 [metrics.md](../metrics.md) 为准；本节只列本方案新增的可测指标，测量方式全部走既有门禁体系（CI / E2E / 巡检命令），不新增「为指标而指标」的人工统计。

| 维度 | 指标 | 基线 | 目标 | 测量方式 |
|------|------|------|------|----------|
| AI 可靠 | 模型能力已知率（档案数 × 已探测能力项 / 应探测项） | 0（未探测） | 100%（探测端点覆盖） | AI 配置页展示 + 单测 |

## 六、风险与边界

**红线对齐**（长期优化方案附录 A 继续有效）：多租户、业务模块军备、重依赖（无头浏览器 / ES / Vault / 类 Excel 设计器一律不主动引入，只登记触发条件）、适老主题、全面移动端适配、为指标而指标。

| # | 风险 | 对策 |
|---|------|------|
| R1 | 单人维护总线因子，批次铺开导致半成品 | 每窗口 1 主项 + 1 小项（WIP=1）；批次内项必须「可独立交付」（无长期悬挂的半成品） |
| R2 | AI 双轨（原生 / prompt-JSON）长期并存造成维护面翻倍 | 双轨共用同一下游（`drafts` 结构 + `execute_action` 收口）；对照日志定期复核，弱模型占比低到阈值后评估下线 prompt 路径（登记评估出口） |
| R3 | 标签 / 任务中心等平台能力被当作「新业务模块」铺开 | 白名单准入（3 对象 / 3 类型起步）；新增对象 / 类型的门槛 = 真实使用诉求（候选池确认制） |
| R4 | 凭据加密迁移造成存量环境读取故障 | 兼容读取先行（密文 / 明文双读），迁移脚本带 dry-run 与回滚；测试服先行验证再进生产 |
| R5 | 审计归档「归了但恢复不了」 | 恢复演练进季度演练池（冷归档 → 临时表查询全链路）；归档文件纳入备份巡检 |
| R6 | 性能基线门禁误报（数据量波动） | 固定种子数据 + 上限留余量 + 只拦硬上限（趋势看报告不改门禁） |
| R7 | uv 双轨期 requirements 漂移 | CI 一致性守护（lock ↔ 导出产物）；只允许单向生成（lock → requirements） |
