## 一、票据层（L3）—— 先做这个：性价比最高，且与 UX 无关

**现状缺陷**（[captcha/cache.py:78](../../captcha/cache.py#L78)）：票据只携带 `{"scene": scene}`。
攻击路径不需要破解任何图像——**把一个"产票"入口当成流水线**：批量完成验证（真人代打或低成本题型）
产出大量票据，再灌进业务请求。票据与"用在哪一次动作、哪台客户端"完全无关，等于一张不记名代金券。
TTL 120s 对慢速真人偏短、对批量重放偏宽。

**改造**

1. **结构化签名票据**（不引 JWT 库，两段拼接）：
   `ticket = b64url(payload) + "." + hex(hmac_sha256(key_id + secret, payload))`
   ```jsonc
   { "v": 1, "tid": "uuid4", "scene": "login", "action": "identity.login.basic",
     "mode": "allow|light|challenge|hard", "type": "pow|slide|…",
     "fp": "sha256(环境摘要|盐)" ,       // 可空；弱绑定
     "ip": "sha256(/24 或 /64 前缀|盐)", // 可空；弱绑定
     "iat": 1730000000, "exp": 1730000060, "n": "16B 随机 nonce" }
   ```
   分数**不进票据**：票据是 base64 可解码的，携带分数等于把评分表交给攻击者；
   `risk_score` 只落服务端 `CaptchaLog`（复核时已从 payload 移除）。
   Redis 只存 `nonce → {exp}` 供一次性消费与重放窗口，票据内容不进缓存（票据本身自证，签名即真）。
2. **消费校验顺序**（`consume_ticket` 扩展）：HMAC 验签 → `exp` → `atomic_get_delete(nonce)` →
   `scene` 匹配 → **`action` 匹配** → `fp`/`ip` **弱绑定**。
   弱绑定含义：不一致时**不直接拒绝**，而是返回「需重新验证」并计入风险信号——
   移动网络换 IP、代理池、窗口尺寸变化都是真人日常，硬绑定一定会误杀。
3. **`action` 两端单源（实施口径，2026-10-26 定）**：业务消费请求**不得携带** `action`，
   由消费点引用服务端常量（`captcha/const.py` 单源，登录 / 发码 / 邀请激活均已接）；
   出题换票端（verify）由前端声明**意图动作**，服务端按 `scene` 登记表白名单校验——
   `CAPTCHA_ACTION_BIND=True`（默认）时**必填**，缺失或越权与答案错误同形失败；
   票据强绑定该动作，消费端两端完全一致才放行，**未绑票据（绑定关闭窗口签发 / 旧格式）
   一律拒绝并要求重做验证**。开关关闭即整体回退只绑 scene 的旧语义。
   每个业务入口一条 `action` 常量：`identity.login.basic` / `identity.register` / `identity.reset_password` /
   `identity.bind_email` / `identity.bind_phone` / `invite.accept` / `auth.verify_code.send:<category>`。
   → 直接消灭「用登录票去发短信验证码」这类票据挪用（这是今天真实存在的洞）。
   > 设计取舍说明：动作绑定只有在换票时知道意图才可能收紧到单动作（scene 内多动作
   > 无法由服务端猜出），故「前端不得传」约束的是**业务消费请求**；换票端声明意图
   > 受服务端登记表约束，伪造越权值只会得到与答错同形的失败，不构成攻击面。
4. **时效按风险分档**：`allow` 60s / `light` 90s / `challenge` 120s / `hard` 90s
   （难题通过后动作更快，压缩打码平台的响应窗口——真人代打从接单到交答案通常 3~10s，
   票据越短命，代打流水线越难对齐）。
5. **verify 请求自身加签**：`challenge` 下发一次性会话密钥 `ck`（仅本题有效，不落日志），
   verify 携带 `gen_time` + `nonce` + `sign = hmac_sha256(ck, canonical(challenge_id, type, scene, answer_digest, gen_time))`，
   服务端校验 ±5min 时间窗与 nonce 未见过。挡住「离线重放一次 verify 调用」。
   （协议形态与极验 v4 的 `lot_number + gen_time + sign_token` 同源，我们把它落在自托管密钥上。）
6. **密钥管理**：`CAPTCHA_TICKET_SECRET` 以 `config.yml` 为唯一定义处（项目凭据单源红线），
   未配置时由 `SECRET_KEY` HKDF 派生并告警一次；支持 `key_id` 双密钥并行验签实现**轮换不断流**。

**兼容性**：字段名 `captcha_ticket` 不变，值变长；图片码 `captcha_key/captcha_code` 链路完全不动。
外部可见变化有二：①升级瞬间「已签发但未消费」的旧票据失效，用户需重做一次验证；
②交互式 verify 在绑定开启（默认）时必须携带 `action`（前端与本方案同批升级；旧第三方
前端可临时 `CAPTCHA_ACTION_BIND=False` 过渡）。两处都写进升级说明。

## 二、信号层（L0）

新增前端目录 `src/utils/captchaSignal/`（纯 TS，几何与摘要逻辑拆纯函数文件便于单测）：

| 模块 | 采集内容 | 落点 |
|------|----------|------|
| `env.ts` | 时区、语言、屏幕与可用屏幕、DPR、`maxTouchPoints`、硬件并发、`prefers-reduced-motion`、`navigator.webdriver`、插件数量、Referer 是否存在、Canvas 2D 与 WebGL 渲染器**摘要哈希**（不落原始像素） | verify/challenge 请求体的 `env` 字段 |
| `track.ts` | 拖动/点击采样 `(x,y,t,type)`（pointermove 按 ≥16ms 节流，事件合并后仍可读）、`pointerdown→up` 时长、**是否由键盘触发** | `track` 字段（沿用现有形状，加 `ev`/`dur` 扩展） |
| `pow.ts` | Worker 内 SHA-256 求解；Worker 不可用（CSP/老浏览器）时降级 `requestIdleCallback` 分片计算并上报 `pow_degraded: true` | `pow_answer` 字段 |

**三条硬约束（写进设计与用例，不是建议）**

- **键盘与辅助技术不得扣分**：`ReSliderCaptcha` 已实现方向键步进与 Home/End（无障碍基座），
  键盘触发的操作在特征表里必须走独立分支，绝不能因"轨迹不平滑/无抖动"被判 bot——
  那是把残障用户挡在门外的合规与口碑事故。
- **隐私最小化**：不采 cookie、不写 localStorage、不采 IP 明文与用户名做指纹；
  指纹 = 环境摘要 + 服务端盐的哈希，盐可轮换（轮换即切断历史关联）；
  日志保留期默认 30 天且可配；`env` 全量数据**不出本系统**（零第三方请求，可审计）。
- **可绕过不是 bug 而是设计前提**：客户端一切信号都可被伪造（Camoufox 类真实浏览器反检测工具已商用）。
  信号的价值在于**抬高成本 + 让批量行为露形**，不在于不可伪造。因此 L0 的每一个信号都必须
  同时向 L5 留痕，供事后关联分析；单靠客户端信号做"硬拒绝"的规则要审慎（除蜜罐这类必然为假的信号）。

**服务端旁路信号**（零前端成本，最可信的一档）：`X-Forwarded-For` 链路一致性、IP 是否命中
内置机房/云 ASN 段清单（可维护数据表，不发版可更新）、`User-Agent` 与 `sec-ch-ua` 系列是否自洽、
`Accept-Language` 与前端上报语言是否一致、同 IP/同指纹的挑战速率与票据堆积、
以及"从 `challenge` 到 `verify` 的墙钟时间"（低于人类下限即高分）。

## 三、决策层（L1 · RiskEngine）

**形态**：纯函数 + **DB 可配规则表**（`CaptchaRule`：`id/code/name/scope/expr/score/enabled/priority`），
每条规则自解释、可单独开关、可单独改分值——对抗性衰减时**不发版就能调**。
首批 16 条（分值为默认建议，全部可配）：

| 信号 | 判据示例 | 分 |
|------|----------|----|
| `env_headless` | `navigator.webdriver=true` 或 UA 含 Headless | +60 |
| `env_missing` | 未带 `env` 或 `env.v` 版本不符 | +40 |
| `env_contradiction` | 时区/语言/分辨率/DPR 互斥组合；Canvas 摘要命中已知伪造集合 | +25 |
| `ua_mismatch` | UA 声称 Chrome 却无 `sec-ch-ua*`；`Accept-Language` ≠ 前端语言 | +25 |
| `no_pow` | 策略要求 PoW 而解答缺失或不足（降级上报不扣满） | +30 |
| `track_straight` | 拖动路径直线度 > 0.98（贝塞尔/人类抖动缺失） | +25 |
| `track_uniform` | 分段速度方差 < 0.5（匀速滑行＝典型脚本） | +20 |
| `track_toofast` | 复杂题 < 400ms 完成；`challenge→verify` 墙钟低于人类下限 | +30 |
| `track_teleport` | 现有瞬移规则（保留，迁入统一评分） | +35 |
| `freq_ip` | 同 IP 挑战 > 10 次/分钟 | +25 |
| `freq_fp` | 同指纹并发挑战 > 3 | +30 |
| `acct_fail` | 同账号/同标识近 15 分钟失败 ≥3（含"不存在的用户名"命中，撞库特征） | +30 |
| `net_datacenter` | 源 IP 命中机房/云 ASN 段清单 | +20 |
| `net_proxy` | 命中已知开放代理 / TOR 出口清单 | +30 |
| `honeypot` | 隐藏字段被填 | **+100（直接 deny）** |
| `hist_good` | 同指纹近 7 天 ≥3 次成功且无失败（**负分**） | **−40** |

**阈值 → 决策**（默认，页面可配；`off` 模式下本表不生效）：

| 分数 | 决策 | 客户端表现 |
|------|------|-----------|
| `< 20` | `allow` | **无题**，`challenge` 调用直接返回与"做过题"完全同形的票据 |
| `20~39` | `light` | 一个「点击验证」按钮，静默跑 PoW，通过即发票（多数人只看到一次点击） |
| `40~69` | `challenge` | `slide`/`rotate`/`click` 常规难度 |
| `70~89` | `hard` | 难题型（语序点选/多步）+ 容差收紧 + TTL 缩短 |
| `≥ 90` 或蜜罐 | `deny` | 与"答案错"**字节级同形**的失败响应 |

**防探测铁律（不可协商）**：任何拒绝路径（答案错 / 风险高 / 环境异常 / 被封禁 / 次数耗尽）
必须返回**同一个响应体与同一文案**，今天 [captcha/services.py:127 区段的设计](验证码多形态增强方案-2026.10.md) 已如此，
新层延续。否则整张评分表退化为攻击者可枚举的免费探针——"我怎么做才不扣分"直接写在差异里。

**分数不向客户端回显**：既不出现在响应字段，也不进可解码的票据；只落 `CaptchaLog`。
管理员在大盘里看，攻击者看不到。

## 四、挑战层（L2）

1. **题型插件契约扩展**（[captcha/backends/base.py](../../captcha/backends/base.py)）：
   `generate(difficulty: str)` / `verify(secret, answer, difficulty)`；
   难度档 `easy|normal|hard` 取值进配置（容差 e.g. 6/4/2px、干扰强度、点选字数 3/4/5）。
   注册表按 `(type, difficulty)` 取参，向后兼容默认 `normal`。
2. **新增 `pow` 题型插件（本方案对抗打码平台的算力轴落点）**
   - challenge：`{algorithm:"sha256", challenge:<hex>, difficulty_bits:<int>, expire:<ts>}`；
   - 浏览器 Web Worker 自增 `nonce` 求 `sha256(challenge‖nonce)` 前缀 `bits` 个零比特；
   - verify：服务端**一次哈希即可校验**（O(1)），成本几乎不随难度上升；
   - 难度服务端封顶 **20 bits**，并按 `decision` 取值（`allow` 不需要、`light` 18 bits、`hard` 20 bits）；
   - **纯 Web Crypto 实现，不引入 WASM 依赖**。抗 GPU 不是目标（SHA-256 在 GPU 上仍快），
     目标是**把"每次尝试"从免费变成有成本**，且成本可由服务端一键上调——这正是打码平台
     按次计价的商业模式最难受的地方。
   - 反向自伤防线：`allow/light` 路径的 PoW 配额按 IP 限总预算，难度上限锁死，
     避免我们把自己变成别人的算力矿、或被拿去做放大器。
3. **新增 `wordorder` 语序点选**：在既有 `click` 绘制基座上加"按提示语义顺序点击"
   （提示条渲染为图片，沿用现有防 OCR 思路）。对多模态模型的关键难点不是"认出字"而是
   "理解顺序约束 + 输出坐标序列"，且**顺序规则可每日轮换**，定向训练成本高于一次性代打。
4. **题型轮换从均匀随机改为风险加权 + 频次配额**：同一指纹/IP 短时间内不重复同型题，
   抬高"只练一种题"的定向模型收益。
5. `icon` 图标点选**列为可选批次，默认不启用**：需要图标资源包（许可与镜像体积），
   收益不及前几项确定。

## 五、处置层（L4 · **全部复用既有风控基座，不新造第二套**）

项目里已经有一整套封禁/计数基座，本层是**接线**而不是重写：

| 需要的能力 | 现成的东西 | 用法 |
|-----------|-----------|------|
| IP + 账号双维封禁判定 | `identity/utils/auth/block.py` 的 `check_is_block` | 消费点在业务动作前调用，验证码 deny 走同一出口 |
| 阶梯计数与冷却 | `settings/utils/security.py` 的 `BlockUtil`/`BlockUtilBase`（`_LOGIN_LIMIT_{user}_{ip}` 双键计数）、`LoginBlockUtil`/`ResetBlockUtil`/`RegisterBlockUtil`/`SendVerifyCodeBlockUtil`/`MFABlockUtils`/`LoginIpBlockUtil` | 新增一个 `CaptchaBlockUtil` 子类（同范式同键风格），**不另写计数框架** |
| IP 黑白名单 | `BlockGlobalIpUtilBase.ip_in_white_list` / `ip_in_black_list` + `SECURITY_LOGIN_IP_WHITE_LIST` + 管理页 `/api/settings/ip/block`（`SecurityBlockIpViewSet`） | **信任网段直接复用它**，不再新增 `CAPTCHA_TRUSTED_NETWORKS` 清单——两套白名单必然漂移 |
| 匿名端点分维度限流 | `IpScopedThrottle`（防 XFF 伪造的统一 IP 取值口径）、`ClientScopedThrottle`（按 `client_id` 并回退 `ip_` 前缀） | 风险层的"同 IP/同指纹速率"信号直接取这两个类的计数，别再数一遍 |
| nonce 防重放窗口 | `mfa/cache.py` 的 `UsedOtpCodeCache`（`md5(code)`、TTL 90s） | 票据 nonce 与 verify nonce 的存储范式照此走 |
| 失败计数与限流的解耦先例 | `common/utils/verify_code.py`：达 `MAX_VERIFY_ATTEMPTS=5` 作废当前码，但**故意不动发送限流键**（防"输错即重置间隔"变成刷短信入口） | 本层阶梯计数的设计口径以此为准，别把失败计数和放行配额互相抵消 |

**新增的只有策略，不是机制**：

- 三维度阶梯计数（IP / 账号或提交标识 / 指纹哈希），Redis 键登记见 §六。
- 默认阶梯（页面可配，全 0 = 只记录不处置）：
  `失败 3 次 → 该维度强制 hard 题型`；`失败 8 次/15min → 冷却 15min`；`失败 20 次/1h → 冷却 1h`。
  冷却期内仍返回**同形失败响应**（不告诉对方"你被封了"）。
- **登录锁定联动**：`CAPTCHA_FAILURE_LINK_LOCK`（默认 False）——这正是上篇方案留下的那个配置位，
  本方案把它做实（调用现成 `LoginBlockUtil`）。
- **蜜罐**：表单里加一个对真人不可见的诱饵字段（前端 CSS 隐藏 + `aria-hidden`，
  真人与读屏用户都不会填；被填即必然自动化），命中 `+100 → deny`。零成本、零误杀的信号。
- **信任网段**：复用 `SECURITY_LOGIN_IP_WHITE_LIST`，默认值必须包含 RFC1918 与回环。
  ⚠️ **本方案最容易出事故的一处**：白名单为空就开 `enforce`，第一天就会把客户自己的办公网挡在门外。
  `manage.py doctor` 增加一条自检：「`CAPTCHA_RISK_MODE=enforce` 且信任网段为空」→ 告警。

## 六、横切 A：挂载面收口（对应 G8——把"漏挂"变成 CI 红）

零散手工调用是安全能力的头号腐蚀剂。本批把它变成**可声明 + 可守护**：

1. **单一入口**：`captcha` 侧新增装饰器/视图混入 `require_human(scene, action)`，
   内部统一做「场景开关 → 风险决策 → 票据消费（含 `action` 绑定）→ 失败处置 → 留痕」；
   `identity/utils/auth/captcha.py` 的 `check_captcha`/`check_token_and_captcha` 收敛为其薄封装，
   保持既有调用点不破坏（二开兼容）。
2. **`action` 单源登记表**：每个业务动作的 `(scene, action)` 常量集中一处（`captcha/const.py` 或独立 `actions.py`），
   消费点必须引用常量而非字面量——`invite.py:114` 那类硬编码顺手收掉。
3. **守护门禁** `scripts/check_captcha_coverage.py`：扫描匿名可达 + 有副作用的端点清单
   （注册路由 + 权限白名单/匿名视图），断言其要么声明了 `require_human`，要么在**显式豁免表**里写明理由。
   新接口漏挂人机校验 = CI 红，与既有 `check_cross_app_imports.py` / `check_menu_titles.py` 同族。
   ⚠️ 新增门禁必须先在 [docs/ci-gates.md](../ci-gates.md) 登记（后端 AGENTS 的硬规定）。
4. **高 QPS 匿名端点的日志噪音**：新端点要同步登记 `server/settings/custom.py` 的审计忽略面
   （今天已有 `^/api/system/captcha`）与 `SILKY_IGNORE_PATHS`（今天已有 `^/api/identity/auth/captcha`），
   否则操作日志会被验证流量灌满——这是"上线后 DB 爆了"的经典成因。
5. **观测写入与主链路物理隔离**：`telemetry` 失败绝不影响验证结果（catch-all + 自有计数器）。

## 七、观测层（L5）

**新模型 `CaptchaLog`**（`captcha/models.py`，继承 `DbUuidModel`/审计基类，只增不改）：

`ts`、`phase`(challenge|verify|consume|decision)、`scene`、`action`、`mode`、`type`、`difficulty`、
`decision`、`would_decision`(shadow 期)、`risk_score`、`risk_reasons`(JSONField，规则 code 数组)、
`passed`、`attempts`、`latency_ms`、`ip_hash`、`fp_hash`、`ua_class`、`browser`、`env_version`、
`pow_bits`、`key_id`。

- **写入不阻塞主链路**：`captcha/telemetry.py` 单点收口 → Celery 批量落库；
  队列不可用时降级进程内缓冲 + 下次刷写，**任何遥测异常都不得影响验证结果**（catch-all + 静默 + 自有计数器）。
- **采样**：失败 100% 记录；成功默认 100%（中后台流量量级下够用），可配 `CAPTCHA_LOG_SUCCESS_SAMPLE_RATE`。
- **保留与清理**：`captcha_purge_logs` 管理命令（沿用已有 `captcha_clean` 的风格与注册方式），
  默认 30 天，Celery beat 日任务；大表场景注意索引（`(ts,)`、`(decision, ts)`、`(fp_hash, ts)`）。
- **大盘页 `CaptchaDashboard`**（新菜单 + 权限点，走元数据协议）：
  ① 趋势：验证量 / 通过率 / 拦截率（按小时·天）；② 分布：风险分直方图、决策占比、**各题型通过率对比**
  （某题型通过率突然上升＝该题型被打穿的第一个信号，这是本方案最重要的单一指标）；
  ③ TopN：拦截原因、可疑 IP 段、可疑指纹、可疑 UA 类；④ 策略快照：当前模式与阈值。
- **实现选型（倾向明确）**：**优先复用 `dataset` 已有的数据集 + 仪表盘能力**做图表与聚合，
  只为"聚合查询"新增一个 `SecurityCaptchaStatsViewSet`（时间窗参数 + Redis 缓存 60s）。
  不要再手写一套 ECharts 页面——项目铁律是"先查现成实现，不另起一套"。
  该结论若被推翻（复用成本高到不合算），需在本篇执行记录写明理由。
- **shadow 口径**：影子期 `decision` 为空、`would_decision` 有值；大盘聚合按
  「有效决策」（`decision` 为空时取 `would_decision`）统计，否则影子期大盘全空、
  无法回答「若开启会放行 / 拦下多少」。
- **告警**：拦截率/通过率异常波动、同 IP 挑战率突增、题型通过率异常，接既有通知渠道
  （`notifications` 已支持多通道），不做新告警系统。

## 八、横切 B：无障碍与合规（对应 G9——逃生舱必须真的能用）

今天 `interactive` 模式的无障碍路径是「切回图片码」，而图片码的音频链路**默认 404**——
等于没有逃生舱。本批把它做实，且写进 E2E 而不是写在文档里：

1. **首选路径是 `allow`/`light`**：无题直过与「一次点击」天然对读屏友好（按钮有可访问名、
   结果用 `aria-live` 播报）。**风险分级本身就是最大的无障碍改进**——这点要写进设置页文案。
2. **音频回退真的可用**：镜像内置 `flite`（或改用不依赖外部二进制的 TTS 方案），
   `CAPTCHA_FLITE_PATH` 默认可用；顺手替换停维 9 年的 `django-ranged-response`
   （Django 自带 `FileResponse` 支持 Range 的分支足够，或自写小函数）——
   该依赖已在 [docs/security-review.md](../security-review.md) 标注风险。
3. **键盘路径不得扣分**：`ReSliderCaptcha` 的方向键步进 / Home / End 是既有能力；
   特征表为键盘操作开独立分支（无轨迹抖动是正常的，不是 bot 特征）。
   这是**硬约束**，配专项用例（见主篇 §八）。
4. **降级不可判死**：Worker 被 CSP 拦、老浏览器无 `crypto.subtle`、`prefers-reduced-motion`
   → 上报 `degraded` 并走轻路径，不得因"能力缺失"拒绝服务。
5. **告知与最小化**：设置页与登录页文案写清「采集什么/不采集什么/保留多久」；
   零第三方外发（可用 E2E 的 CSP/网络断言验证）；IP 只取网段前缀哈希、Canvas 只留摘要、
   保留期默认 30 天、指纹盐可轮换。产品交付给客户，文档要替客户把 PIPL 的话说完。

## 九、复核与补记（2026-10-27）

按 B1~B8 与本文 §一~§八 逐条复核（读码 + 定向测试 + 静态门禁 + 容器实测），补齐四处缺口：

1. **失败阶梯第一档接线**：`disposal.register_failure` 的 `force_hard` 原先被调用点丢弃，
   `flow.should_force_hard` 无调用方——「失败 3 次 → 强制难题型」实际未生效。现由
   `disposal.forced_hard(dims)` 读取维度计数，`InteractiveCaptcha.challenge` 在 enforce、
   非信任网段时把决策抬到 `hard` 并追加 `fail_ladder`；冷却 / deny / 信任网段的优先级不变。
   守护：`test_disposal.py::test_forced_hard_reads_first_rung`、
   `test_captcha_risk.py::test_failure_ladder_forces_hard_next_challenge`、E2E「失败阶梯」。
   同批修正：`allow` 无题直过此前绕过「同 IP 未消费票据 ≤3」，现与做题路径同样占用 /
   释放槽位，防低风险票囤积（`test_allow_path_respects_inflight_ticket_limit`）。
2. **大盘观测口径补齐**：`captcha/stats.py` 新增风险分五档直方图、deny 行 TopN
   （原因 / IP 网段哈希 / 指纹 / UA 类）、`summary.deny` 与 `deny_rate`，`policy` 增加
   阈值 / PoW 开关 / 阶梯；shadow 档以 `would_decision` 作为有效决策参与聚合
   （否则影子期大盘全空）；「验证数据」页签同步渲染。
   守护：`test_stats.py::test_risk_distribution_and_top_deny_breakdowns`、
   `test_shadow_would_decision_feeds_dashboard`、`test_captcha_insight.py`。
3. **消费日志 key_id**：`tickets.consume_ticket_payload` 返回票据载荷，`phase=consume`
   日志落 `key_id`（原先字段恒空）。
4. **票据不再携带风险分**：票据 payload 可被客户端 base64 解码，原 `risk` 字段等于把
   评分表交给攻击者；已从 payload 与 `issue_ticket` 参数移除，分数只落 `CaptchaLog`。
   守护：`test_tickets.py` 断言 payload 无 `risk`。

**已知偏差（不阻塞交付，已评估）**

1. **fp 弱绑定只记录不校验**：消费请求不带 env，无法重建与挑战期同口径的指纹；用 UA
   重建会误伤窗口尺寸 / 语言变化。IP 网段弱绑定已生效（漂移即要求重验），fp 仍入日志
   供关联分析。
2. **无 `crypto.subtle` 的客户端在 enforce 下 fail-closed**：verify 加签与 PoW 都依赖
   Web Crypto，不为此放宽为「无签放行」（那会变成可伪造的绕过面）。部署侧应使用 HTTPS +
   现代浏览器；旧客户端可临时启用图片码回退或维持 `shadow/off`。
3. **大盘未复用 dataset**：验证数据是设置域内的只读审计聚合，需要与 `SettingCaptcha`
   同权限边界、固定口径与 60s 缓存；dataset 仪表盘面向站点级公共看板，复用需新增数据集 /
   仪表盘种子与跨域授权，成本高于直接聚合。保留独立聚合端点 `SecurityCaptchaStats`，
   页面为设置页内嵌统计条，不引入第二套图表渲染。
4. **遥测投递粒度**：当前每个事件投递一次 Celery 任务，任务内 `bulk_create` 批量落库；
   不是进程内攒批。高流量部署可后续加批缓冲，不影响「遥测故障不拖挂验证」的隔离语义。
5. **阶梯计数未继承 `BlockUtil` 家族**：三维度计数使用独立键
   （`captcha_dim_fail_*` / `captcha_cooldown_*`），因为 `BlockUtil` 的键模型是
   user/IP 双键且绑定登录语义，直接复用会污染登录锁定计数；登录锁定联动仍调用现成
   `LoginBlockUtil`，未另造第二套封禁机制。
6. **`track_toofast` 只用轨迹时长**：challenge→verify 墙钟信号未启用——自动化测试与
   极快真人都会落在阈值内，等有真实基线后再加，避免误伤。
7. **机房 / 代理识别依赖配置**：`CAPTCHA_RISK_DATACENTER_CIDRS` /
   `CAPTCHA_RISK_PROXY_CIDRS` 默认空，未内置 ASN 段清单；运营需按客户网络维护。
8. **题型轮换未做频次配额**：已实现加权 + 短窗防重复；按题型配额（如每 N 次最多一次
   `wordorder`）未实现，当前权重表已能表达优先级。
9. **拒绝同形范围**：deny / 环境异常 / 封禁 / 答案错共用同一 `captcha_invalid` 响应；
   「次数耗尽」仍按既有前端契约返回 `captcha_exhausted`（并带 `attempts_left`），
   属于上篇既有语义，本批未收紧。
