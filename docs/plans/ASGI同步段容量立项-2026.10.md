# ASGI 同步段容量立项（2026.10）

> 立项于 2026-10-01。承接 [NEXT-DEV-PLAN.md](../../../NEXT-DEV-PLAN.md) O1 收口（记录三补充，server `e8e35e9e`）中「达标杠杆走容量规划另立」的开口项：**04-metadata-fields P95 未达 <60ms 目标的根因是 ASGI 同步执行段的串行容量膝点，不是端点代码问题**。本文按项目纪律「先方案后动手」先行立项；改动保留工作区待人工检查，不主动提交。

## 一、背景与定位

### 1.1 问题的来龙去脉

1. **O1 复测（2026-10-01 早，`a6823df0`）**：固定环境三轮中位数，`04-metadata-fields` P95 **117.62ms**（基线 106.71，同噪声平台），未达 <60ms 目标，`loadtest/baseline.json:47-57` 以 `target_met=false` 显式登记；当时沿用 §3.1 旧归因表述为「排队放大 + ASGI 每请求新建 DB 连接开销」。
2. **深度定位（2026-10-01 晚，`e8e35e9e`）**：fields 与 columns（P95 28.67ms、更高吞吐）的 **4 倍差距**无法用通用排队解释，对照实验修正归因为**同步执行段串行容量膝点**（证据链见 §二）。
3. **本立项**：把两个达标杠杆（worker 容量 / 异步中间件链迁移）落成可执行的方案与排期。

### 1.2 与 TD-25 / ADR-006 的边界（防重复立项）

`NEXT-DEV-PLAN.md` O1 行与记录三中「收敛走 ASGI 连接池根因技术债（psycopg3 `OPTIONS.pool` / pgbouncer，另立立项）」的表述**已过时**：连接池债（TD-25）已于 **2026-09-07 由 [ADR-006](../adr/ADR-006-asgi-db-connection-pool.md) 根治**——psycopg3 + `OPTIONS.pool`（默认启用，`DB_POOL=true`，`server/settings/base.py:238-268`），压测失败率 20.33% → 0%。本轮 O1 复测（`loadtest/settings_loadtest.py` 未禁用池）即运行在池化形态上，fields 未达标**与连接建立开销无关**（早间表述系沿用 §3.1 首测旧归因，已被深度定位修正；`pgbouncer` 已被 ADR-006 否决，不再重开）。

因此本立项命名从「连接池」修正为「**同步段容量**」，是 ADR-006 之后该技术族真正剩余的开口项。

## 二、证据链（膝点实测，`docs/metrics.md:307-315`）

固定环境（§3.1 专用容器 + 1000 perf_ 种子，gunicorn UvicornWorker ×4 生产同参）对照实验：

| 实验 | 结果 | 排除/证明 |
|---|---|---|
| 温热缓存压测（零重建窗口） | 慢桶依旧 5.8% | 排除缓存重建 / 单飞锁 |
| 缓存 TTL 采样 | TTL 300s 单键，重建整轮 1 次 ≈0.25% | 排除窗口击穿残留 |
| 单连接 300 发 | 0 个 >100ms（p95 6.4ms） | 排除逐请求代码浪费（命中路径干净） |
| book 同框架对照 | 2000 rps 下 P95 13.7ms 干净 | 排除鉴权 / 框架通用层 |
| 慢请求时序 | 89% 成簇（簇 8-20 ≈ 全部 VU）、TTFB≈总时长 | 服务端停顿波（排队），非网络/客户端 |
| **并发扫描（定案）** | fields：4 并发 = **725 rps / P95 7.8ms / 慢桶 0.02%**；8 并发 P95 83ms；20 并发 = 820 rps / P95 105-130ms；40 并发 = 778 rps / P95 169ms | **吞吐 ~780 rps 封顶、加并发只加延迟 = 串行容量膝点**；columns 膝点 ~1100 rps、book ~2000+，解释 endpoint 差异 |
| **容量验证** | 8 worker（其余同参）+ 20 VU：fields **P95 26.5ms（<60ms 达标）**、吞吐 1209 rps、慢桶 1.73% | 扩容即达标（单轮验证，批 A1 补三轮中位数） |

栈采样：请求线程时间 21.6% 花在 **sync→async 交接等待**。

## 三、机制解释（实测 + 推断，推断部分已标注）

- **实测**：单 worker 吞吐封顶 ≈195 rps（4 worker × ~195 ≈ 780），进程内加并发只加排队；交接等待占比 21.6%。
- **机制推断（与膝点量级吻合，批 A1 顺带核验）**：同步中间件与同步视图经 `sync_to_async` 落线程执行，进程内多个在途请求的同步 CPU 段受 **GIL** 约束，有效并行 ≈1 → 单进程吞吐封顶 ≈ 1/同步段纯 CPU 时间；叠加每请求线程交接开销（Django `ASGIHandler` 的 `ThreadSensitiveContext` 线程模型）放大排队尾。
- **推论**：扩 worker 是线性扩容（进程级并行，绕开 GIL）；异步化同步段只能消除交接开销与 I/O 等待占位，**视图与 DRF 仍同步**，故杠杆 B 有收益上限。

## 五、杠杆 A：worker 容量（本窗口执行，投入 ~1 人日）

### 5.1 现状与旋钮

| 面 | 现状 | 位置 |
|---|---|---|
| 默认 worker 数 | `GUNICORN_MAX_WORKER: 4` | `server/conf/defaults.py:101`、`config_example.yml:136` |
| 压测侧旋钮 | `LOADTEST_WORKERS` 环境变量（默认 4）→ 注入 settings | `loadtest/settings_loadtest.py:41` |
| 启动消费 | gunicorn `-w` 取自该配置 | `common/management/commands/services/command.py:97` |
| DB 连接容量核算 | `GUNICORN_MAX_WORKER × DB_POOL_MAX_SIZE + celery 子进程数 × DB_POOL_MAX_SIZE < PG max_connections`（compose 默认 200） | `server/conf/defaults.py:69`、`docs/ops/deployment.md:429` |

8 worker 的容量核算：`8×8 + 2×8 = 80 < 200`，有富余；每 worker 常驻内存增量在部署文档容量节一并登记。

### 5.2 决策点（改动保留工作区，供人工定夺）

**D1：基线快照口径**（`loadtest/baseline.json`）
- **推荐：维持 4-worker 生产默认形态快照不动**——护栏对「默认部署形态」负责，`04-metadata-fields` 的 `target_met=false` + `target_note` 维持（该目标在默认容量下本就不可达，非代码缺陷）；8-worker 三轮中位数作为**容量档位参考值**登记到 JSON 顶层新键（如 `capacity_reference`，`check_baseline.py` 对额外键宽容）+ `target_note` 追加「8-worker 档位实测达标（见容量立项）」。
- 备选：整体刷新为 8-worker「新标准环境」（`--update` 全量回写，env 元数据同步改写）。风险：`check_baseline.py` 不校验 env 元数据，未来误以 4-worker 复测会对**全部用例**报劣化（噪声故障模式）。

**D2：生产默认 worker 数**
- **推荐：`defaults.py` 默认 4 不动**（保护小内存/低配部署），生产按 [deployment.md](../ops/deployment.md) 新增容量节指引上调（实测数据支撑：8 worker 下 fields 达标 + 吞吐 1209 rps），实际值由部署侧 `config.yml` 决定。

## 六、杠杆 B：异步中间件链迁移（触发制，不在本窗口）

### 6.1 改造面盘点（2026-10-01 在 .venv Django 6.0.8 实测 `async_capable`）

链上 18 项（`server/settings/apps.py:62-86`）：

- **已 async-capable 12 项（无需改造）**：Django 内置 8（Security / Session / Common / Locale / Csrf / Auth / Messages / XFrameOptions）+ 第三方 2（corsheaders、django-csp）+ 自定义 2（`ApiLoggingMiddleware`、`MetricsMiddleware`〔条件挂载〕）。
- **需改造 7 项（均纯 `__call__` 同步类，未声明 `sync_capable`/`async_capable`）**：`server/middleware.py` 的 Start / Request / ModuleGate / RefererCheck / SQLCount / End 六项 + `common/core/middleware.py` 的 `CSPModeMiddleware`。多为轻逻辑（上下文登记 / 模块裁剪查缓存 / header 校验 / SQL 计数 / 响应期 CSP 模式改写），可逐一异步化或保持同步并显式声明边界。

### 6.2 收益边界与触发条件

- **收益上限**：视图与 DRF 保持同步，杠杆 B 只消除中间件段的交接等待（实测占请求线程时间 21.6% 的一部分）与 I/O 占位，**不能替代扩容**；膝点最终受同步视图段 GIL 约束。
- **建议触发条件**（满足其一再立项，立项时先走 ADR——涉及中间件装配结构）：
  1. 生产并发持续贴近部署容量膝点，且 CPU 核数 / 成本约束使扩 worker 不可行；
  2. 杠杆 A 落地后的固定环境复测显示，同 worker 数下膝点仍低于业务峰值需求 ≥30%；
  3. Django 底座升级窗口（D1，2027-04 Django 6.2 LTS）顺带评估官方异步栈新能力后的性价比重估。
