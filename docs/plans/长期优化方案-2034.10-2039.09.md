## 一、总体框架

### 1.1 原则（继承既有红线，不重复发明）

1. **按需插槽制**：无真实触发不虚构需求；候选池启动前需产品优先级确认；每窗口 1 主项 + 运营贯穿（单人维护 WIP=1）；
2. **先 ADR 后动手**；契约改动先行（server schema → client 类型 → `check:contract`）；只收敛不提权，裁剪类改动 fail-closed；
3. **新功能 100% 携带测试**（CI 阻断）；改后端必跑 `pnpm test:e2e:fresh`（防旧进程假失败）；
4. **预算制优先于运动式优化**：体积 / 覆盖率 / 测试时长只在预算内演进，超预算需说明理由并刷新基线；
5. **明确不做清单长期有效**（附录 A），任何突破必须先改 ADR 结论。

### 1.2 优先级模型

| 级别 | 定义 | 判据 | 处置 |
|------|------|------|------|
| **P0** | 红线 / 阻断类 | 安全与数据完整性、可用性 SLO、门禁或 CI 失效、被演练/事故证实的真实缺陷 | 立即插队，占最近窗口主项 |
| **P1** | 条件已满足的高收益 | 触发条件已命中且收益可测（如合 main 后的视觉基线、硬件就绪的独立盘、数据成熟的 SLO 校准） | 排入最近一个可容纳窗口 |
| **P2** | 触发式改进 / 评估出口 | 条件未满足的升级、功能候选、评估出口（各自登记重开条件） | 触发即插；未触发不占窗口 |
| **P3** | 观察 / 不做 | 与红线冲突或数据不支持（多租户、业务军备、重依赖、适老、全面移动端） | 只登记触发条件，不排期 |

排序公式：**优先级 = 影响面（安全 > 数据 > 可用性 > 体验 > 效率）× 紧迫性（是否阻断运营基线或期限承诺）÷ 成本（窗口可容纳性）**；同级按「先清账、后增强」排序。

### 1.3 三阶段路线图（总览）

| 阶段 | 周期 | 主题 | 收口判据 |
|------|------|------|----------|
| **一：收口与固化** | 2034.10 – 2035.09（第九年度，即现行年度计划） | 清账闭环 + SLO 校准 + 告警补强 + 演练收尾；框架/功能短板首批收口 | 本方案 §六「阶段一」列全部达标；触发条件台账完成首次复核 |
| **二：深化与提效** | 2035.10 – 2037.09（第十 ~ 十一 年度） | 覆盖率/类型/视觉基线常态化；模块治理与二开验证；依赖大版本按触发跟进 | 阶段二 KPI 达标；存量评估出口无「无判据悬空项」 |
| **三：稳态演进** | 2037.10 – 2039.09（第十二 ~ 十三 年度） | 触发式演进；运营基线维持；框架代际预研（触发式） | 阶段三 KPI 维持；明确不做清单未被被迫突破 |

## 三、框架评估（优点 / 不足 / 优化方向）

> 评估对象：支撑所有功能的基础框架层。不足列中标注「**边界**」= 设计内取舍（登记触发条件）；「**短板**」= 真实可优化项，进入 §五 目标。

### 3.1 服务端框架（Django 6.0 + DRF + 元数据驱动）

| 层 | 优点（已验证能力） | 不足 | 优化方向（优先级 · 阶段） |
|----|--------------------|------|--------------------------|
| 元数据驱动 CRUD | `search-columns` / `search-fields` / `table_fields` / `input_type` 驱动前端；契约入 [schema/](../schema/) + 生成类型 + `check:contract` 门禁；字典/状态彩色 tag 已贯通（`dict.ts` 统一入口）；**渲染器成对守护已入 vitest**（注册表分类完整性 + 列表/详情成对） | 契约耦合面大：字段类型判定须 `isinstance`（历史上精确匹配导致详情列空白）；新增 `input_type` 需同步元数据/序列化器/列表渲染/详情渲染多处（**短板**，守护与检查清单已落地） | 新增字段类型按 [framework-cookbook](../architecture/framework-cookbook.md)「新增 input_type 检查清单」执行（P2 · 阶段一已完成） |
| ViewSet / Action 体系 | 权限/导出/导入/批量/回收站统一基座（BaseViewSet + Action 族）；[framework-cookbook](../architecture/framework-cookbook.md) 有选型对照与覆写点 | 覆写有隐式规则（如批量非逐行分支不走 `perform_destroy`，历史留孤儿块）；默认行为与自定义行为是追加合并（前端侧同类约束见 3.2）（**短板**） | Action 清单与覆写红线维持文档化；新增覆写附守护测试（P2 · 阶段一） |
| 权限内核 | 三层权限统一出口 + 数据权限编译器 fail-closed；14 种数据规则；缓存失效链路文档化；权限扫描守护 68 例 | 配置门槛高：空配置 = 全裁剪（显式授权口径）；字段权限需「详情菜单白名单」配套；部门主管缺失等 fail-closed 报错对用户偏晦涩（**短板**） | 报错文案与配置体检继续打磨（P2 · 阶段一）；保持 fail-closed 口径不变 |
| 通知框架 | 三件套模型（渠道枚举 + 渠道模块 + 渲染注册），新增渠道 = 一个文件 + 一行注册；两层可达性过滤；短信模板约束清晰 | 未绑定账号用户静默跳过（仅 debug 日志），"为什么没收到"需查日志；短信受服务商模板单变量约束（**边界**） | 渠道可达性诊断视图（P3 · 按需） |
| 审计内核 | 操作日志全链（module / auth_type / token_pk / diff）；AI 动作独立审计 | DEBUG 级正文裁剪未做，冗余细节占存储（**短板**，评估出口） | 按条件触发（P2 · 评估出口） |
| 缓存体系 | 四套键规范 + `check_cache_keys --strict` 审计 + 失效矩阵文档 | 菜单/权限缓存 24h TTL 与配置变更耦合（靠启动清理）；进程内 `lru_cache` 变更需重启（**边界**） | 维持（启动清理已实现）；新增长 TTL 缓存须登记失效路径（P1 · 常态纪律） |
| 异步与队列 | celery worker / heavy / beat 三进程；重任务隔离（Office 预览走重队列）；周期任务声明式注册（模块裁剪联动） | 探测曾拖死线程（已修，缓存化探针）；队列健康依赖探针正确性（**短板**已收敛） | 守护测试维持；新增队列按探针口径接入（P1 · 常态） |

## 四、功能模块逐个评估（优点 / 不足 / 优化方向）

> 覆盖 6 域 30+ 项能力。不足列标注「**边界**」（设计内）与「**短板**」（可优化）；优化方向与 §五 编号（Q/A/T/U/F）互通。
> 读法：优点回答「现在能做什么、凭什么可信」；短板回答「哪里还欠」；优化方向回答「什么时候、以什么代价补」。

### 4.1 身份与访问域

| 功能 | 优点（已验证） | 不足 | 优化方向（优先级 · 阶段） |
|------|----------------|------|--------------------------|
| 登录 / 注册 / 重置 / 锁定 | 多策略登录；失败锁定；密码规则；站内/邮件重置链路 | 无异常登录阻断能力（无风控，仅日志可从审计追溯）（**边界**：非定位） | 登记观察，不做（P3） |
| MFA（敏感操作二次验证） | 四后端 + 412 协议 + 权限工厂；未验证不推进业务状态有守护 | 敏感操作覆盖按 `APPROVAL_MFA_REQUIRED_ACTIONS` 逐动作灰度，非默认全覆盖（**边界**） | 按需扩充动作清单（P3 · 按需） |
| 第三方登录（OAuth） | 钉钉/企微/飞书适配器 + 官方端点预设；绑定唯一；登录后置链路单一收口 | 依赖企业应用配置，无内置联调沙箱（**边界**）；配置错误提示依赖文档（**短板**） | docs 排错章节维持（P2 · 常态） |

## 七、持续迭代机制

1. **年度 — 窗口双层排期**：年度计划（12 窗口，按需插槽制）+ 窗口出口门禁（后端 pytest/ruff/覆盖率；前端 typecheck·strict·lint·stylecheck·vitest·contract·bundle-size；E2E 双浏览器 fresh；数据/部署重灌幂等；CI 全绿；治理三红线）；
2. **季度节奏**：季度演练（≥1 轮场景轮换）+ 依赖 audit + SLO 快照 + **维度巡检（本方案新增：五维度 KPI + §4.7 短板台账走一遍，异常项登记触发器）**；
3. **候选池三态管理**：登记 → 半年复核（带触发条件与复核日期）→ 执行 / 关闭（记录理由）；「已评估关闭」项保留重开条件；
4. **ADR 前置与触发条件制**：重大改动先 ADR；升级类决策必须有触发条件与回滚预案，禁止提前动手；
5. **度量回填**：每阶段收口把 KPI 实测回填 [metrics.md](../metrics.md)；年度回顾附 KPI 对照与遗留交接；
6. **演练 / 事故驱动闭环**：每个演练结论沉淀为 runbook / 规范 / checklist 项；缺陷修复附守护测试；
7. **框架评估刷新（本方案新增）**：§三/§四 的「不足」列每年度回顾时复核一次——短板已修复则移入优点，新发现的短板登记并映射优化项；
8. **本方案自我复核**：每年年度回顾时校准本方案 KPI 与优先级（允许调整目标，但须记录理由）；每 6 年编一次阶段全景盘点；
9. **文档同步**：新增文档先登记 [plans/README](README.md) 或 [docs/README](../README.md) 索引；ADR 状态变更同步索引表。
