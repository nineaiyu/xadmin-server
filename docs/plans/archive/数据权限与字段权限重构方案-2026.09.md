## 1. 结论先行

数据权限的问题不在性能，而是**语义模型不自洽**：

1. 「全部数据」规则在且模式下反转为**全拒绝**（语义 bug，有稳定复现路径）；
2. `mode_type` 概念错位：三个模型继承 `ModeTypeAbstract`，实际只有**用户本部门**的字段被读取，祖先部门的是死配置，`UserInfo.mode_type` 是全仓无引用的死字段；
3. `get_filter_q_base` 120 行巨型函数：规则筛选、值归一化、模式组合、Q 拼装混在一起，就地改写 dict，`Q(id=0)` / `q == Q()` 魔法值散布；
4. 写入端零校验：字段名写错 → 绑定用户所有列表接口 500；
5. 零缓存：非超管每个列表请求 4~6 条 SQL，而它挂在全局 `DEFAULT_FILTER_BACKENDS` 上。

推荐方案：**规则编译器四段管线 + ScopeResult 布尔代数**。理由见第 5 节与 5.8 的备选对比。

> **批注 D1/D2（动手前必须拍板）**：上述 5 条定位经代码复现全部成立。但「完整重构」前有 2 个语义决策必须先定：
> ① `combine` 对空输入、以及「规则因 table 不匹配被排除」的取值（D2，**直接关系 fail-open**）；
> ② 层间「缺一层即拒」是否保留（D1）。两者分别落在 §5.2 / §5.3，未定之前不宜进入 P0 编码。

## 2. 现状架构（数据流）

```
请求 → IsAuthenticated.has_permission
        ├─ API 权限：get_user_permission（24h 缓存）→ 菜单 method/path 匹配
        ├─ 注入 request.user.menu = 当前菜单 pk
        └─ 字段权限：get_user_field_queryset（10s 缓存）→ request.fields = {model_label: {字段名}}
              ↓
       BaseModelSerializer.__init__ / BasePrimaryKeyRelatedField.get_allow_fields
              └─ 初始化时 pop 掉无权限字段（读写同时受限）

列表/详情 → BaseDataPermissionFilter（全局默认 backend，server/settings/libs.py）
        └─ get_filter_queryset(queryset, user)
              ├─ superuser / 未启用 → 全量
              ├─ 部门祖先链（含本部门，逐级向上）：每层取绑定授权 → get_filter_q_base → Q
              │        层间固定 AND（逐级收紧，缺一层即拒绝）
              ├─ 个人授权：get_filter_q_base → Q，与部门链结果 OR
              └─ 无任何授权 → queryset.none()
```

规则 JSON 形态（DataPermission.rules）：

```json
[{"table": "demo.book", "field": "admin", "type": "value.user.id", "value": "*", "match": "exact"}]
```

14 种 `type`（ModelLabelField.KeyChoices）+ 约 18 种 `match`，由前端规则 builder 生成，后端读时解释执行。

## 4. 具体案例（可复现）

以下案例均可用现有代码行为推演复现（单测载体：`tests/unit/common/test_data_permission_filter.py`，demo.Book 模型，`admin` 字段为归属字段）。

### 案例 1：部门配「全部数据」→ 部门成员看到空集

配置：
- 部门「技术部」，`mode_type = 且模式`；
- 技术部绑定授权 `P1`：单条规则 `[{table: "demo.book", field: "admin", type: "value.all"}]`；
- 用户小王挂在技术部，无个人授权。

| | 结果 |
|---|---|
| 期望 | 小王可见全部数据（部门授予全部） |
| 现状 | **空集**。单规则组强制或模式 → ALL 分支检查 `dept_obj.mode_type == OR` 不成立 → 不短路 → 组编译为 `Q()` → 末尾 `q1 == Q()` → `return Q(id=0)` → 该层恒假 → 链结果 `queryset.filter(Q(id=0))` |

根因：ALL 在且组合下应为**单位元（恒真）**，现状当成了「无规则 → 恒假」。唯一没炸的原因是现有测试的部门 fixture 默认或模式，恰好绕开。

### 案例 2：个人「全部数据」授权被部门模式吞掉

配置：
- 小李挂「销售部」（且模式），部门授权：`creator in 销售部及下级`；
- 小李个人授权 `P2`：单条规则 `value.all`。

| | 结果 |
|---|---|
| 期望 | 全部数据（语义说明承诺「个人授权与部门链结果做或合并」，个人 ALL 应胜出） |
| 现状 | 仅销售部范围。个人组同案例 1 路径返回 `Q(id=0)`，OR 合并后无增益，静默失效 |

### 案例 3：祖先部门上的 mode_type 是死配置

配置：管理员在「总经办」（技术部的上级）上把 mode 从或改成且，期望控制「总经办绑定授权的组间组合方式」。

现状：**完全无效**。层内组合读的是 `user_obj.dept.mode_type`（用户本部门），祖先部门自身的 `mode_type` 从未被读取；反过来说，改 A 部门的 mode 实际改变的是「本部门挂在 A 的用户」的规则组合，对 A 的子孙部门用户毫无影响。同时 `UserInfo.mode_type` 全仓无引用——两个字段都是配置陷阱。

### 案例 4：字段名手滑 → 绑定用户全量 500

管理员建授权时字段名写成 `creat0r`（绕过前端下拉直改 JSON）。`RelatedManager.get_filter_attrs_qs` 拼出 `Q(creat0r=…)`，用户每次列表请求 FieldError → 500。写入端 `validate()` 只查 rules 非空，不做字段/lookup 校验。对比：`permission_preview.run_data_trial` 已示范注册表白名单 + label 正则校验，写入侧却没做。

### 案例 5：match 与 type 的隐式契约

`TABLE_USER` 类型规则读时把 value 归一化为 pk 数组，但 `match` 保留前端所设。前端 builder 现在约定给 `in`，一旦某版本手滑传 `exact` → `Q(admin=<list>)` → DB 层报错。后端对「类型→合法 match」没有防御，契约只存在于前端代码里。

### 案例 6：字段权限的默认拒绝（维持现状，显性化）

`PERMISSION_FIELD_ENABLED` 默认 True（server/conf.py L187）。新部署给普通角色配了菜单但没配字段权限 → `request.fields = {}` → 序列化器把**所有字段裁空**，列表页空转。这是「未配置=默认拒绝」的既定语义（有测试背书），本次维持，但配套要求：

- 权限预览页已能看到字段矩阵，配置缺失可见；
- 文档与字段权限配置页提示语明确「未配置该菜单字段白名单的角色，将看不到任何字段」。

## 5. 目标设计（推荐方案）

### 5.1 规则编译器四段管线

新模块 `common/core/data_scope.py`（数据权限编译器 + 代数），`common/core/filter.py` 退化为薄壳（filter backend + 入口函数）：

```
RuleSpec(JSON) --validate--> RuleResolver --resolve--> Condition --compile--> Q --combine--> ScopeResult
```

| 段 | 职责 | 形态 |
|---|---|---|
| validate | 写入侧结构校验（见 5.4），与 preview 共用 | `validate_rules(rules) -> None/raise` |
| resolve | 14 种 type 的值归一化：`type → resolver` 字典分发，纯函数、不改写入参 | `resolve_rule(rule, user_ctx) -> Condition` |
| compile | Condition + model → Q 或哨兵；match 翻译收口于此（含 ip_in/regex/m2m 等特例，从 RelatedManager 迁移） | `compile_condition(model, cond) -> Q/ALLOW_ALL` |
| combine | ScopeResult 布尔代数组合（见 5.2） | `combine(results, mode) -> ScopeResult` |

`user_ctx` 显式携带：`user_pk / dept_pk / menu_pk / leader_dept_pks`（为部门主管预留），不再从 ORM 实例上取属性——`get_filter_queryset` 对 `user_obj.dept` 的隐式依赖改为显式上下文构造，可测性大幅提升。

### 5.2 ScopeResult 布尔代数（核心）

用三值代数替代 `Q() / Q(id=0)` 魔法值：

```python
class ScopeResult:
    ALLOW_ALL  # 恒真：任何 AND 组合的单位元，任何 OR 组合的支配元
    DENY_ALL  # 恒假：任何 AND 组合的零元，任何 OR 组合的单位元
    Q(q)  # 普通条件
```

组合规则（对称、封闭、无需特判）：

| combine(list, AND) | combine(list, OR) |
|---|---|
| 含 DENY_ALL → DENY_ALL | 含 ALLOW_ALL → ALLOW_ALL |
| 全为 ALLOW_ALL → ALLOW_ALL | 全为 DENY_ALL → DENY_ALL |
| 否则取 Q 的交集 | 否则取 Q 的并集 |

组内「ALL 在且模式被忽略、在或模式支配全组」的现状语义，正是该代数在组内层的自然推论——**组内行为完全兼容现状**；案例 1/2 的 bug 在层间/个人层使用同一代数后自然消失，无需逐 case 打补丁。

> **批注 D2（fail-open 风险，必须定调）**：代数表本身正确，但缺两个关键定义。
> ① **空输入**：`combine([], AND)` / `combine([], OR)` 未定义，而它要承担两个**相反**语义——「某层没有任何授权组」
> 必须 DENY_ALL（fail-closed），而「某组规则被 table 过滤后为空」现状是**丢弃该组**（既非 DENY 也非 ALLOW）。
> 建议显式规定 `combine([], AND) = ALLOW_ALL`（单位元，仅用于组内被过滤空），「该层无授权」由调用方传 `[DENY_ALL]`。
> 同时钉死 `combine([], OR) = DENY_ALL`（空析取恒假）——两个端口都写死，不留实现歧义。
> 否则实现者极易把现在 `q1 == Q() → Q(id=0)` 的错误原样复刻。
> ② **「被排除」必须与 `ALLOW_ALL` 区分**：§5.1 的 `compile_condition(model, cond) -> Q/ALLOW_ALL` 缺少第三个返回态。
> 现状 filter.py L43 先按 `table` 过滤、L51 组内无规则则丢弃该组；若新实现把「table 不匹配」归入 `ALLOW_ALL`，
> 则「绑定到其他模型的授权」会变成「不加任何限制」→ **越权放行**。建议 compile 增加 `EXCLUDED/SKIP` 态，
> 或把 table 过滤前置为 resolve 之前的独立步骤，并在 §8 增加「绑定他表授权不得放行」的回归用例。

> **批注 D3（表述修正）**：**「组内行为完全兼容现状」不成立**。当一条授权 `mode_type=AND` 且其规则**全部**为
> `value.all` 时：现状是 L44-46 全部 `continue` → `rules` 为空 → L51 该组**被整体丢弃** → 若为该层唯一组，
> L54-55 返回 `Q(id=0)`（全拒）；新代数下 `combine([ALLOW_ALL...], AND) = ALLOW_ALL`（该层放行）。方向上是修复
> （属案例 1/2 同类），结论不受影响，但应把这行写进 §6 行为变更清单，避免评审误判为零影响。

> **批注 D11（补漏）**：代数表缺取反算子，而 `get_filter_attrs_qs` 支持 `exclude` → `~Q`。实现时需明确
> `NOT ALLOW_ALL = DENY_ALL`、`NOT DENY_ALL = ALLOW_ALL`（即 `exclude=True` 的 ALL 规则语义为「排除全部」），
> 并在 §8 的代数矩阵里补齐 NOT 维度。
> 注意现状细节：`match == "all"` 分支的 `continue`（db/utils.py L66-68）先于 exclude 取反（L105-106）——
> 即**现状对 ALL 规则的 exclude 是忽略**（恒放行）；仅通配值（`val == "*"` / `in ["*"]`）的 exclude 会真正
> 取反（`~Q()` = 全拒）。若新代数实现 `~ALLOW_ALL`，exclude+ALL 从「忽略」变「全拒」，属行为变更，
> 需在 §6 登记或由校验器直接拒绝该组合。

### 5.3 组合语义归位（重构后的语义表）

| 层级 | 新语义 | 对比现状 |
|---|---|---|
| 组内 | 授权自身 mode_type；单规则强制或模式的读侧特例**删除**（代数下单条件与/或等价） | 行为等价 |
| 层内 | 组间组合模式 = **该部门自身 mode_type** | 修复案例 3：祖先部门配置生效，且对所有链上用户一致 |
| 层内无授权 | DENY_ALL（fail-closed 保留） | 不变 |
| 层间 | 固定 AND（逐级收紧保留） | 不变 |
| ALL | ALLOW_ALL 哨兵贯穿组内/层内/层间 | 修复案例 1/2 |
| 个人授权 | 组间按**各授权自身 mode_type** 组合；与部门链 OR | 修复错位（现状用本部门 mode） |
| 个人无授权 | 部门链结果；无部门无授权 → none() | 不变 |
| 菜单上下文（dq） | 授权 menu 为空=通用，否则匹配当前菜单 | 不变 |

`UserInfo.mode_type`：死字段，**删除**（迁移 + 表单/序列化器联动清理）。`DeptInfo.mode_type` 含义变为「本部门绑定授权的组间组合模式」，对所有经过该部门的用户一致——直观且与 admin 界面展示相符。

> **批注 D1（必须定调）**：表中「层内无授权 = DENY_ALL」与「层间固定 AND」保留后，**案例 1 的修复只在部门是根时成立**。
> 案例 1 未交代「技术部」是否有父部门：按现行与新版语义，只要祖先链上有任意一层没配 `DataPermission`，该层
> DENY_ALL 经 AND 后整体全灭——即「子部门配了权限、祖先没配 → 权限完全不生效」。这正是最容易被管理员当 bug
> 上报的规则，建议在此显式定调并补一个「非根部门」的案例与决策理由。可选替代：只让「配了授权的层」参与 AND，
> 未配授权的层跳过（不引入放行，只是不再额外收紧）。

> **批注（表述修正）**：`UserInfo.mode_type` 的「全仓无引用」不准确——它出现在 `system/views/admin/user.py` L42 的
> fields、`UserInfoSerializer` 与 i18n 文案中，属「可写不可用」。删除需连同表单单选、导入导出映射、前端字段一起清，
> 建议在 P1 交付物里列成检查清单。

### 5.4 写入校验

`DataPermissionSerializer.validate` 调用编译器的 `validate_rules`：

1. `table` ∈ 数据权限注册表（ModelLabelField DATA 根节点）或 `*`；
2. `field` ∈ 该模型注册字段 ∪ 模型真实字段名（双保险，`*` 除外）；
3. `type` ∈ KeyChoices；`match` ∈ 编译器支持集；
4. 类型联动校验：`TABLE_*` 的 match 强制 `in`、value 是 pk 数组；`DATE` value 是整数秒；`DATETIME_RANGE` 是 2 元素时刻；`JSON` 可解析。
5. `exclude` 仅布尔。

坏规则在保存时被拒，而不是让绑定用户用 500 发现。preview 的试算校验同步换用该函数。

> **批注 D7（规则不成立）**：第 2 条「`field` ∈ 该模型注册字段 ∪ 模型真实字段名」按字面会**误拒合法的跨表路径**——
> 现有规则支持 dunder 写法（`tests/unit/common/test_data_permission_filter.py` L73 即使用 `admin__dept`），且
> `table="*"` 时拿不到「该模型」。建议明确：按 `__` 逐段解析、每段必须是真实字段名或注册字段；`table="*"` 时
> 只校验注册表、跳过模型真实字段校验；并把「`field` 为 `*`」单独列为合法值（现第 2 条括号内「`*` 除外」指代不明）。

> **批注 D6（补漏）**：本节只解决「以后不再产生坏规则」，但**库里已有的坏规则仍会让绑定用户 500**——案例 4 的前提
> （绕过前端直改 JSON）意味着线上很可能已存在此类数据。建议 P1 增补：① 一次性巡检/清理管理命令（列出并修正
> 非法 table/field/type/match 的授权）；② 读侧兜底（编译期捕获 `FieldError` → fail-closed 或跳过该规则 + 告警），
> 避免「改一处配置炸一个页面」。此外，写入校验收紧会使**存量坏规则在管理员编辑时被拒**，属对外行为变化，
> 应补进 §6 清单。

### 5.5 缓存与失效

- 缓存对象：`(user_pk, menu_pk)` → **resolve 后的授权清单快照**（部门链每层授权组 + 个人授权组，值为 Condition 的 JSON 形态；不缓存 Q 对象——redis msgpack 不可序列化，且 model 维度组合多）。compile/combine 是纯内存操作，每请求现做。
- TTL 60s（对齐部门树缓存姿态，权限变更容忍分钟级），`MagicCacheData` 占位保护基建直接复用。
- 信号失效挂进 `system/signal_handler.py` 现有钩子模式：
  - `DataPermission` save / `userinfo m2m` / `deptinfo m2m` 变更 → 失效关联用户（`userinfo_set` ∪ 绑定部门及子树用户）；
  - `DeptInfo` save（树结构 / leader 变更）→ 失效子树用户；
  - 已有的 `invalid_user_cache_handler` 等钩子位照旧。
- **教训规避**：`load_init_json` 导入期屏蔽信号，种子导入尾部必须显式失效本缓存（同字典缓存的处理方式）。

> **批注 D4（必须登记）**：本方案把数据权限从「每次实算（变更即时生效）」改为「最长 60s 生效」。数据权限是安全属性，
> 「收紧延迟」必须写进 §6 行为变更清单并说明可接受理由（对齐部门树 60s 姿态），否则会被当成回归。

> **批注 D5（失效清单补漏）**：现有列表缺 3 项——
> ① `DataPermission.menu` 的 **m2m 变更**（决定授权只在哪些菜单上下文生效；现只列了 userinfo/deptinfo m2m）；
> ② `UserInfo.dept` 变更（用户换部门 = 整条祖先链变）——原文「已有的 `invalid_user_cache_handler` 等钩子位照旧」
> 不成立：该钩子目前只删 `get_user_permission_*` 与响应缓存，必须显式追加新 key；
> ③ `DataPermission.is_active` 切换（走 save 算覆盖，但建议写进清单防遗漏）。
> 另需注意：`system/signal_handler.py` L26-34 的 `get_cache_data_keys` 是按 `(user, method)` 拼 key 的，
> 新缓存是 `(user, menu)` 维度，**必须另写失效函数**，不能复用现有 generator。

> **批注 D9（补漏·其一）**：`(user_pk, menu_pk)` 缓存能消掉 DB SQL，但同一请求内 `search-columns`（N 个关联列）
> 与导入 `to_internal_value`（R 行 × F 字段）仍会对同一 model 重复 compile。compile 是纯内存，可接受；建议
> 顺手在 request 上按 `(user.pk, model_label)` 再 memo 一层 Q，并在本节注明这一层存在，避免后续误判查询预算。

### 5.6 部门主管（leader）设计

模型与规则类型（表达层增量，不动组合逻辑——主管授权天然走现有 OR 合并）：

```python
# system/models/department.py
leader = models.ForeignKey(
    "system.UserInfo",
    on_delete=models.SET_NULL,
    null=True,
    blank=True,
    related_name="leader_depts",
    verbose_name=_("Leader"),
)
```

```python
# system/models/field.py KeyChoices 新增
LEADER_DEPARTMENTS = "value.leader.dept.ids", _("My led departments and their descendants")
LEADER_USERS = "value.leader.user.ids", _("Members of my led departments")
```

| 规则类型 | resolver 行为 | 典型规则 |
|---|---|---|
| `value.leader.dept.ids` | `user.leader_depts` 各部门递归展开的并集 | `dept_belong in 主管部门及下级` |
| `value.leader.user.ids` | 主管部门及下级成员的 pk 并集 | `creator in 我的下属组织全员` |

- 不是任何部门 leader → 解析为空列表（`in []` 恒假），语义自洽；
- 失效：`DeptInfo` 信号增补失效「leader 本人 + 该部门子树用户」；
- 联动：迁移、规则类型枚举、前端规则 builder 选项、ModelLabelField 种子、permission_preview 文案、i18n。

### 5.7 字段权限口径收口（不改语义）

新模块 `common/core/field_permission.py`，单一函数 `allowed_field_names(request, label_lower, declared) -> set`，收编豁免判定（ignore / 超管 / 白名单 / 未启用）与白名单交集。`BaseModelSerializer.get_allow_fields` 与 `BasePrimaryKeyRelatedField.get_allow_fields` 改为调用方，删除两份手写拷贝。「未配置=裁空」语义原样保留（案例 6 已显性化）。

`FieldPermission` 复合主键 hack 本次不动（当前写入路径逐条 save，无 bulk 场景），列为后续可选项。

> **批注 D9（补漏·其二）**：`FieldPermission` 目前**没有任何缓存失效信号**（signal_handler.py 只挂了 Menu / UserRole /
> UserInfo / DeptInfo / SystemConfig / DataDict / DataMaskRule），字段权限改动只能等 `get_user_field_queryset` 的 10s
> TTL 过期，属「延迟收紧」。本次给数据权限配了完整信号失效，字段权限却仍是裸 TTL，两者不一致。建议在 P4 一并补
> （`FieldPermission` post_save/pre_delete + `field` m2m_changed，反查 `instance.role.userinfo_set` 后精确失效）。

> **批注（语义口径不一致，本节「不改语义」需再确认）**：`BaseModelSerializer` 在「未配置该模型字段权限」时是
> **裁空整个模型字段**（有单测 `test_no_field_config_for_model_keeps_nothing` 锁定），而
> `BasePrimaryKeyRelatedField.get_allow_fields` 在同一情况下返回空 attrs，`to_representation` 会退化为
> **返回裸 pk**（fields.py L242-243）——即「未配置 = 默认拒绝」对关联字段并不成立，字段仍可见（只是只剩 id）。
> 本节把两者收口到同一函数时，需明确这个差异是**保留**（则函数要能表达两种结果）还是**统一**（则属行为变更，须进 §6）。

### 5.8 备选方案对比（为什么推荐编译器方案）

| 方案 | 说明 | 评价 |
|---|---|---|
| **A. 编译器 + 代数（推荐）** | 本方案 | 一次把语义地基打对：bug 消失是代数推论而非补丁；validate/resolve/compile 各自可单测；主管与未来规则类型是纯增量；preview 复用编译器消灭第二份语义实现 |
