## 一、背景与目标

### 1.1 背景

xadmin 当前是一个**工程化程度远超平均水平**的项目：46 篇 ADR、六层模块裁剪（路由 / WS 通道 / 菜单 / 周期任务 / 种子 / 缓存）、服务端 2600+ 测试与前端 7 项门禁、契约镜像（`contract/schema` ↔ `docs/schema`）、离线安装器（安装 / 升级 / 回滚 / 备份）、PITR 与备份演练体系。

但其历史优化目标是「长期自用演进」，导致**对"从零开始的陌生开发者"存在系统性摩擦**：

- 上手路径依赖对内部机制的隐性理解（元数据契约、权限码约定、注册时机）；
- 初始化存在必踩的手工步骤（配置拷贝、密钥生成）；
- 文档分散在 3 处且存在可验证的漂移；
- 前端仓库存在跨仓库路径假设，无法独立检出使用。

### 1.2 目标（可度量）

| 编号 | 目标 | 判定标准 | 现状 |
|------|------|----------|------|
| G1 | **快速启动** | clean clone → 浏览器登录成功 ≤ 10 分钟（目标 5 分钟），除登录密码外零手工配置 | ✅ P0 批次后：`dev_up.sh` 一条命令起全栈 + 幂等 `init_data` + `doctor` 自检（2026-09-20 容器实跑通过，见 §七 v1.3 批次） |
| G2 | **自检可用** | 一条 `manage.py doctor` 输出全部环境/配置/种子问题及修复命令 | ✅ `manage.py doctor`（P1-1）：8 项只读检查 + 修复命令 + 失败项非零退出码 |
| G3 | **扩展闭环** | 新增业务模块 = `generate_crud` 生成 + 一次启动自检通过，过程中无需阅读框架源码 | ✅ 生成器 + 「后续步骤」清单 + `--with-module`（P2-4）+ 2026-09-20 沙箱全链路走查（含「注册 app 时 config.py 尚未生成」的容错）；种子灌库与角色授权仍为超管管理动作 |
| G4 | **文档零漂移** | 版本号 / 端口 / 默认值等事实在文档中单一事实源，CI 防漂移 | ✅ P2-5 后 CI 事实校验就位（历史漂移已于 P0-4 清零） |
| G5 | **仓库独立** | 前端仓库可独立检出运行 dev 与 e2e（不依赖固定兄弟目录） | ✅ `E2E_SERVER_DIR` 参数化（P1-7，代码原已支持）+ `e2e/README.md`「独立检出运行」章节 |
| G6 | **失败可见** | 最常见的两类"静默失败"（元数据缺失缺列、权限点未灌库 403）在开发期显式报错 | ✅ 元数据缺失 DEV 警示条（P1-5）+ 启动期权限点缺口告警（P1-2）+ `doctor` 检测（P1-1） |

### 1.3 设计原则

1. **只补路径，不推倒重来**——所有改造项与既有机制（模块裁剪、门禁、安装器）零冲突；
2. **默认值即文档**——能靠默认配置解决的，不写进文档让人照做；
3. **失败前置**——静默错误改为启动期 / 开发期显式报错；
4. **单一事实源**——事实（版本、端口、密码策略）只保留一处定义，其余引用它。

**目录结构（注意：无 `apps/` 目录，Django app 平铺在仓库根）**：

```

loadjson/      初始化种子（21 个 json）      tests/  pytest（sqlite + FakeRedis，无需外部依赖）

utils/         运维脚本（init_data / db_backup / pitr_drill / check_celery / nginx.conf）
```

**核心依赖链（请求处理）**：

```
请求 → RequestMiddleware（request_uuid）→ ModuleGateMiddleware（模块裁剪 404）
     → 三层权限：① API/菜单权限 {action}:{ViewSetName} ② 数据权限（16 种规则）③ 字段权限
     → BaseModelSet（CRUD/批量/导入导出/回收站/联想）→ 统一响应 code=1000
```

**扩展入口约定**：新业务 app 必须在 `config.yml` 的 `XADMIN_APPS` 登记（参与 migrate + 路由自动注入 + 权限前缀）；跨 app 调用必须走 `<app>.services`（CI 门禁 `check_cross_app_imports.py`）；模块声明走 `{app}/modules.py`（ADR-045/046）。

**目录结构**：

```
src/api/         BaseApi / ViewBaseApi（元数据驱动的接口封装）
src/views/       业务页面（system / dashboard / analysis / chat / login / account / integration…）
src/components/  Re* 组件体系（RePlusPage / ReDialog / ReDrawer / ReAuth / ReIcon… 共 193 文件）
src/utils/       http/（拦截器 + 错误策略表 + 审批暂存 + 路由取消）aes（v2/旧双协议）sse / websocket / dict
src/store/       Pinia modules（user / permission / multiTags / app / settings / epTheme / siteConfig）
src/router/      守卫 + 动态路由生成（async-routes）+ 静态模块收集
contract/schema/ 后端契约镜像（与服务端 docs/schema 逐字一致，CI 守护）
e2e/             60+ spec + README（**陷阱表，项目经验数据库**）
scripts/         门禁脚本（strict 类型 / 契约同步 / 体积基线 / 文件长度 / 元数据类型生成）
```

**核心机制（二次开发必须理解的三件事）**：

1. **列表页=元数据驱动**：RePlusPage 的列/表单/搜索项全部来自后端 `search-fields` / `search-columns`，前端只注册渲染器（`registry.ts`）；
2. **权限= `hasAuth("动作:组件名")`**（无 `v-auth` 指令；组件名来自 `defineOptions({name})`，必须与后端权限点一字不差，否则整页不渲染）；
3. **契约=三重锁定**：服务端 `docs/schema` → 前端 `contract/schema` 镜像 → `gen:metadata-types` 生成类型（CI 门禁）。

### 2.4 前后端依赖关系（咬合点清单）

| 咬合点 | 机制 | 破坏后的现象 | 防护 |
|--------|------|--------------|------|
| 元数据协议 | `search-columns` / `search-fields` JSON Schema | 表格空列 / 表单缺域（**静默**） | 契约镜像 + 守护测试 |

## 四、改造方案（四大方向设计）

### A. 简化初始化流程

**目标**：G1（clone → 登录 ≤ 10 分钟，零手工配置）。

| 设计 | 说明 | 涉及文件 |
|------|------|----------|
| A1 配置兜底 | `ConfigManager.load_user_config()` 找不到 `config.py` / `config.yml` 时，**回落读取 `config_example.yml`** 并在 DEV 模式（`XADMIN_DEV=1`）自动生成随机 `SECRET_KEY`、`DEBUG=true` | `server/conf/manager.py`、`config_example.yml` |

| A3 一键开发脚本 | 新增工作区级 `scripts/dev-up.sh`：cp 配置（如缺）→ 生成 key → `docker compose up -d postgresql redis nginx` → `init_data`（幂等化）→ `pnpm dev`；配套 `dev-down.sh`；幂等可重跑 | 工作区顶层（新建）或 `xadmin-server/utils/` |
