四层检查，逐页覆盖，无抽查：

| 层 | 手段 | 覆盖 |

>
> **v1.1 追加**：§九为**后端功能面**补充轮次（接口能力 / 权限点 / 菜单种子 / 模型覆盖），方法与结论见该节。

### P0-01 执行记录（✅）

**根因**：后端 `BaseModelSerializer` 对未声明 `label_format` 的外键统一下发 `{pk, label}` 关联对象
（`xadmin-server/common/core/fields.py` `to_representation`），且此时 `label` 与 `pk` 同值：

```json
"dataset": {"pk": "5eed0001-0000-4000-8000-000000000001", "label": "5eed0001-0000-4000-8000-000000000001"}
```

前端两处按字符串 pk 消费：

- 列表列 `xadmin-client/src/views/analysis/report/utils/hook.tsx`：`find(item => item.pk === pk)`
  拿字符串比对象恒 false → 返回对象 → `h("span", 对象)` 被 Vue 当作 props 渲染成空 span；
- 编辑表单 `xadmin-client/src/views/analysis/report/components/ReportForm.vue`：`form.dataset`
  存的是对象，与 `el-option` 的标量 pk 失配 → 不回显。

> 搜索区「数据集」下拉不受影响（走 filter 的 `__str__` 标签）；仪表盘卡片的 `dataset` 存于 JSON 字段、本就是字符串，无此问题。

**改动（4 个文件）**

| 文件 | 改动 |
|------|------|
| `xadmin-client/src/api/system/analysis.ts` | 新增 `RelatedPk` 联合类型 + `relatedPk()` 取主键；`ReportItem.dataset` 由 `string` 修正为 `RelatedPk` |
| `xadmin-client/src/views/analysis/report/utils/hook.tsx` | `datasetName()` 先经 `relatedPk()` 归一化再映射数据集名称 |
| `xadmin-client/src/views/analysis/report/components/ReportForm.vue` | `form.dataset` 初值走 `relatedPk()`，回显与提交载荷均为标量 pk |
| `xadmin-client/e2e/analysis.e2e.ts` | 补回归断言：报表行的数据集列必须显示数据集名称 |

取主键写法沿用项目既有约定（与 `utils/dict.ts` 的 `choiceValue`、`utils/tree.ts` 的 `?.pk ??` 同款形态）。

**验证证据**

| 项 | 结果 |
|----|------|
| `tsc --noEmit` + `vue-tsc --noEmit --skipLibCheck` | EXIT=0 |
| `eslint --max-warnings 0` + `prettier --check`（4 个改动文件） | 全部通过 |
| `playwright test e2e/analysis.e2e.ts --project=chromium` | **2 passed**（含新增回归断言） |
| 运行时实拍 · 列表列 | `示例-用户日报 \| 示例-全部用户 \| 每天 \| 08:00 \| admin@example.com \| 邮件`（此前数据集列空白） |
| 运行时实拍 · 编辑弹窗 | 「数据集」正常回显 `E2E报表数据集-017rwo` |

### 9.2 B-01 详情（根因 · 实证 · 连带后果）

**涉及位置**（三处覆写均漏装饰器）：

| 文件 | 行 |
|------|----|
| `xadmin-server/approval/views/approval_flow.py` | 85（`batch_destroy` 覆写） |
| `xadmin-server/approval/views/leave.py` | 95 |
| `xadmin-server/system/views/admin/dict.py` | 56 |

**根因**：DRF 的 `get_extra_actions()` 靠函数对象上的 `.mapping` 属性识别 action；子类覆写后该属性丢失，路由不再生成。
`batch_destroy` 原本由 `BatchDestroyAction`（`common/core/modelset/batch.py`）以
`@action(methods=["post"], detail=False, url_path="batch-destroy")` 提供，三个 ViewSet 为加业务守卫
（静默排除受保护记录）覆写时未保留装饰器。

**同仓正例**（均保留装饰器，可直接作修复模板）：
`system/views/admin/user.py:89-90`、`system/views/admin/role.py:58-60`、`system/views/admin/dept.py:47-49`。

**运行时实证**（空数组入参，仅探路由与鉴权）：

```
200  对照组 role   POST /api/system/role/batch-destroy
200  对照组 dept   POST /api/system/dept/batch-destroy
405  审批流程      POST /api/system/approval-flows/batch-destroy
405  请假申请      POST /api/system/leaves/batch-destroy
405  数据字典      POST /api/system/dict/batch-destroy
```

**精确检测口径**：遍历 **126 个 ViewSet** 的 MRO，比对父类中带 `.mapping` 的方法在本类上是否仍具 `.mapping`
——**全仓仅上述 3 处**，无其他漏网。

**连带后果**（比 405 本身更值得注意）：

1. 三段守卫逻辑成**死代码**——「批量删除时静默跳过受保护记录」的能力实际不存在；
2. `batchDestroy:SystemApprovalFlow` / `SystemLeave` / `SystemDataDict` 三个权限点已在 `loadjson/menu.json` 登记、
   在**角色授权树可见可勾选**，但因路由不存在**不会被下发**给任何用户 → 管理员配了也无效（误导性权限）；
3. 前端因此不渲染批量删除按钮（自洽降级），故**当前点不到**——属「能力缺失」而非「点击报错」。

**修复要点**：三处补回 `@extend_schema(...)` + `@action(methods=["post"], detail=False, url_path="batch-destroy")`；
修复后权限点会恢复下发、按钮出现，须同步补 E2E 断言（选中行 → 批量删除 → 受保护记录被静默排除）。
