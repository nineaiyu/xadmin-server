## 一、结论先行

1. **项目已越过「功能补课」阶段**：年度 12/12 窗口全部提前完成（ADR-001~036）、代码审查全轮整改已提交、
   两仓库工作区干净、E2E 47 spec 双浏览器全绿、pytest ~2100+、vitest 225。当前风险不是「能力缺失」，而是「方向分散」。
2. **本轮复核的 3 个「缺口」已有两个当天闭环**（见 §三）：① `FormMySubmission` 页面权限点为**种子滞后误判**
   （库内 6 个权限点早已存在并绑定模型，种子已收敛）；② 间隔调度原判「死端点/死代码」→ 已**反转为补齐管理页**
   （端点 + 页面 + 6 权限点 + 唯一性校验，双浏览器 E2E 通过）；③ 仅剩首屏 KPI 口径待改（§三.3）。
3. **建议主线**：立即收口（2 周）→ 主攻「权限边界内的 AI 执行」（方向 A）→ 开放平台二期按需求门控（方向 B）
   → 体验/性能改「预算制」（方向 C）→ 明确不做清单（方向 D）。
4. **最高风险**：A 的写操作与 B 的权限模型都直接耦合权限体系（项目护城河）——必须 ADR 先行 + 越权矩阵随项交付；
   首屏优化先做 bundle 分析再立项（避免第二个「ReIcon 实测后关闭」的浪费）。

## 三、立即收口清单（0–2 周，P0/P1，可拆独立提交）

### 1. `FormMySubmission`（我的填报）—— 复核修正：非缺口（种子滞后误判）✅

| 项 | 内容 |
|---|---|
| 原判 | 扫 `loadjson/menu.json`/`menumeta.json` 无 `dynamic-form-submissions` 条目、白名单未放行 → 判「零权限点、非超管一律 403」 |
| 复核（2026-09-14 晚，库内权威口径） | 页面 `FormMySubmission`（`067a4d61-…`）下 **6 个权限点全部在库且 active**：`list/create/retrieve/partialUpdate/destroy/batchDestroy`（其中 4 个绑定 `system.dynamicformsubmission` + `system.dynamicform`）；覆盖扫描缺口 0 |
| 结论 | 原判系**种子文件滞后**（库已由上一轮权限补齐落地、种子未回写）造成的误读；本轮 `--update-seed` 已收敛，库/种子一致 |
| 剩余（可选） | 受限角色（演示模式 / 管理员等，当前仅 System Administrator 全量持有）如需用「我的填报」，在角色页勾选这 6 个权限点即可；受限视角运行时断言建议随后续受限 E2E 补齐 |

| 项 | 内容 |

## 四、下一年度方向（A–D + 推荐排序）

> 年度回顾 §五 已给 5 条方向（稳定收口 / AI 深化 / 开放平台二期 / 多租户条件触发 / 体验债）。
> 本节按「差异化价值 × 单人维护约束 × 可验证性」重排为 A–D，并给出启动门控。

### A（推荐主攻）AI 深化：从「问答」到「权限内执行」

现状：AI 一期/二期 + 知识库（**词频重叠检索**，`system/utils/ai.py:225`）+ 聊天室流式 + 多档案。

| 子项 | 具体动作 | 关键决策 / 验收 |
|---|---|---|
| A1 检索升级（评测驱动） | 先建**检索评测集**（20–30 问 + 期望出处，入 CI）；实测 hit@5；再决定是否引入向量 | 门控：hit@5 < 75% 或分块数 > 500 才升级。选型：① OpenAI 兼容 embedding API（零新依赖）+ Python 侧余弦（<1 万块够用，**不动部署**）；② 语料超 1 万块再上 pgvector（部署变更，需 ADR）。混合检索（词频 + 向量 RRF）保持 fail-closed 权限口径不变 |
| A2 助手写操作（最大差异化） | AI 只产出**受限 action draft**（白名单动作类型：发起请假 / 提交动态表单等），前端渲染确认卡片 → 以**用户身份**执行 → 复用 412 审批协议 + `auth_type=ai` 审计 | 红线：AI 永不直接执行、不越权、必可审计；默认关闭灰度；越权矩阵新用例随项交付 |
| A3 AI 观测 | 用量 / 成本 / 失败率 / 档案对比看板（对标 Dify 观测面） | 复用多档案 + OperationLog；低优先级 |

### B（需求门控）开放平台二期

现状 G11：client-credentials 发卡机 + 按应用限流 429 + 回调探测；应用权限 = 复用 creator 的菜单权限（粒度不够）。

| 子项 | 内容 |
|---|---|
| B1 应用级权限体系 | 独立 scope 集 + 资源级授权（参考 Directus policies/roles 粒度），只做收敛不做提权 |
| B2 OAuth 授权码 | 仅当接入方需要「代表用户」访问；纯服务端 ↔ 服务端 client-credentials 已够 |
| B3 用量与配额报表 | 已有按应用限流，补配额、用量统计与告警 |
| B4 Webhook payload schema 治理 | 事件版本化 + 字段契约 + 订阅方文档（接入方增多触发，已挂候选池） |
| **启动门控** | **≥2 个真实外部接入方或 1 个明确集成项目**；否则保持候选池（W5–W6 由备选项顶替） |

### C（按需）体验与性能

| 子项 | 内容 | 备注 |
|---|---|---|
| C1 首屏 | 按 §三.3 预算制执行 | 先分析后立项 |
| C2 动态表单数据导出 | CSV 导出复用导出框架 | 比 RePlusPage 动态列协议改造便宜一个量级；触发条件 = 用户提出导出诉求 |
| C3 移动端 | 不做全面适配；仅「核心页平板宽度 + 触屏降级」抽查修补 | 单维护者约束下的务实边界 |
| C4 类型/样式债 | `typecheck:strict` 推进顺序：`src/components`（RePlusPage/ReDialog 框架层）→ `src/layout` → views；T2 `!important` 存量清零前置 = **视觉回归门禁**（Playwright `toHaveScreenshot` 仅覆盖 5–10 核心页） | 前置未达成则维持冻结 |

### D（明确不做，防漂移红线）

- 多租户（ADR-031 重开条件未命中）；
- 业务模块军备（商城 / CRM / WMS）；
- 类 Excel 报表设计器、vxe-table、schema-form 等重依赖；
- 适老主题（已否决，仅保留「浏览器缩放引导」类轻方案的说法）；
- PITR（除非备份 RPO 升为硬需求并经成本评审）。

**重 BI 需求的正确解法**：并行部署 Metabase 指向只读副本，而不是自研报表设计器——守住「权限内生」的自研边界。

## 五、开源同类对比与借鉴矩阵

| 项目 | 定位 / 优势 | 不足（相对 xadmin 视角） | 可借鉴结论 |
|---|---|---|---|
| **vue-pure-admin**（上游） | Vue3+Vite+EP 模板，生态活跃（16.5k★） | 是「模板」不是业务框架；无权限/审计/测试深度 | 只跟踪安全补丁与新组件，**不回灌合并**（已分叉过深）；Renovate 纪律保持 |
| **Django-Vue-Admin** | Django+DRF+RBAC 快速开发平台，门槛低 | 前端栈旧（D2Admin 系）、测试/安全/契约深度浅 | 借鉴「开箱即用」文档体验；能力面 xadmin 已全面领先 |
| **ruoyi-vue-pro（芋道）** | 国内标杆，模块化业务库（v2026.05 增 WMS/IoT/MES）+ AI | 业务全家桶，单人维护无法跟 | 借鉴**模块可插拔的组织方式与 AI 产品化形态**；不跟业务模块 |
| **jeecg-boot** | 低代码全家桶（在线表单/报表设计器、AI 2.0） | 重依赖设计器，违背本项目红线 | 借鉴 AI 与低代码**融合的产品形态**；实现维持自研轻量路线 |
| **NocoBase 2.0** | 「AI+无代码」平台：前端流引擎、AI 员工、工作流插件 | 通用无代码平台定位，与 xadmin「权限底座」不同 | 借鉴：动态表单联动/区块设计、「AI 员工」交互形态、插件化 |
| **Dify** | RAG 管线 + Agentic 工作流 + 观测 | 不做权限内嵌，外部系统集成成本高 | 借鉴：**检索评测与观测**、知识库管线产品化（分段/召回测试）；xadmin 差异化 = 权限约束 + 审批挂接 |
| **Metabase / Superset / DataEase** | BI 能力、行级权限与嵌入方案成熟 | 引入即新增部署面与权限对齐成本 | 不引入引擎；重 BI 需求走「只读副本 + Metabase」并行解法 |
| **Directus** | 任意 SQL 上生成 REST/GraphQL，行/字段级权限 | 架构与定位不同 | 借鉴：**开放平台二期权限模型设计**与 API 体验 |
| **Django Unfold** | Tailwind 现代 admin，可增量采用 | xadmin 自带完整前端，不适用 | 借鉴其「增量迁移」策略；将来若需 DB 直管场景可作备选 |

**定位结论**：xadmin 的独特位置 =「权限/审计/安全底座 + 元数据驱动 CRUD + 轻量平台能力」；同类要么是模板（无深度），
要么是业务全家桶（无边界）。下一年应深化「权限边界内的 AI 执行」与「开放集成」，而不是补业务模块。

## 七、验证方式（门禁矩阵）

| 层级 | 每窗口出口门禁 |
