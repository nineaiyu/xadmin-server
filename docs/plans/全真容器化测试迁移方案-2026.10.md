# 全真容器化测试迁移方案（真实 PostgreSQL + Redis 全面替换 sqlite）

> 2026-10-01 立项。**一句话**：在 [容器化 PG 的 nightly 测试档](容器化PG-nightly测试档立项-2026.10.md) 落地并实证了 sqlite 门禁方言盲区的真实性之后，按用户决策将方向从「双轨兜底」升级为「全面真环境化」——**PR 门禁（`test.yml`）全量后端 pytest 直接对真实 PostgreSQL 17 + Redis 8 容器执行，sqlite 从测试链路退役**。
>
> 本文档**替代** nightly 立项文档 §二「PR 门禁不换 PG」的非目标与 §六「阶段二（触发制）」的保守路线；nightly 档的实证发现（§五）是本方案的全部依据来源。

## 一、背景与动机

### 1.1 nightly 档首轮即实证：盲区是真实的

2026-10-01 nightly PG 档（`tests/settings_pg.py` + `test-nightly-pg.yml`）首轮跑通，**在 4562 个通过的用例之外暴露 5 类 sqlite 无法发现的缺陷**（处置详见 nightly 立项文档 §五台账，本文 §五有摘要）：

1. **产品级 500**：`select_for_update()` 作用于可空外连接（`upload_chunk.py:182`），PG 直接拒绝（`FOR UPDATE cannot be applied to the nullable side of an outer join`）——若生产跑在 PG 上，分片上传完成接口即 500；
2. **连接池 + 测试库换名**：Django postgres 后端 pool property「读即建池」，应用启动后台线程在 pytest-django 换库名前把池固化到不存在的库名 → 全量 3630 errors；
3. **连接池 + 事务内关连接**：`safe_atomic_db_connection(auto_close=True)` 把 `autocommit=False` 的连接还给池，判活探针 `SELECT 1` 又开启新事务 → INTRANS 状态循环污染，76 errors 雪崩；
4. **PG 序列不随事务回滚**：「superuser fixture ⇒ pk=1」不变量（loadjson 种子 `creator=1` 的解析前提）在 PG 上必然漂移；
5. **sqlite 专属 SQL 与规划器语义**：`EXPLAIN QUERY PLAN`、空表规划器索引选择。

### 1.2 决策

- **用户决策（2026-10-01）**：与其长期维护「sqlite 快门禁 + 真库周档」双轨，不如全面走向真实环境测试——「完全走真实的环境，真实的 redis 和 postgresql，全面替换 sqlite」。
- **成本论据被实测削弱**：nightly 首轮实测全量 4562 用例在真实 PG 上本地仅 **43s**（`-n auto`），CI 时长瓶颈是 runner 启动与容器拉起，而非「真 SQL 慢」——原立项「PG 进门禁是三输」的成本判断不再成立。
- **缺陷前移价值**：上述 1-3 类问题若发生在 PR 阶段，修复成本是 nightly 分诊的数分之一；若逃逸到 PG 生产，是线上事故。

## 二、目标与非目标

**目标**

- G1：PR 门禁（`test.yml`，push/PR 触发）对真实 PG 17 + Redis 8 容器跑全量后端 pytest，口径（覆盖率门禁 `--cov-fail-under=85`、`-n auto`）不变；
- G2：单元/集成测试层 sqlite 全面退役：`DJANGO_SETTINGS_MODULE` 缺省指向真环境配置，`tests/settings_test.py` 的 sqlite `:memory:` 分支仅作为**本地快速反馈可选项**保留（或删除，见 §四 阶段 3 决策点）；
- G3：E2E（playwright，现 sqlite 文件库）迁移到真实 PG，保留其确定性重置语义；
- G4：门禁时长预算 ≤ 20 min（实测基线：本地 43s，CI 预估 8-15 min，含容器启动）；连续 2 周全绿后视为稳定；
- G5：nightly 立项文档确立的分诊纪律延续：每个红 = 修复 commit 或显式登记，**禁止 skip 污染**。

**非目标**

- ❌ MySQL 档（维持 ADR 触发制）；
- ❌ 真实 celery broker（eager 保留，见 §三.4 论证）；
- ❌ lint/security 等静态档变化（与运行环境无关）。

## 三、目标架构

### 3.1 `tests/settings_real.py`（真环境单一配置，由 `tests/settings_pg.py` 演进）

沿用已验证的「前置 Config 注入 + star-import」形态（不可放 `server/settings/` 包内，父包 `__init__` 会强制加载 config.yml）：

```python
# 环境变量驱动（CI services / 本地容器同构）：
#   DB_HOST/DB_PORT/DB_DATABASE/DB_USER/DB_PASSWORD —— PG（已验证形态）
#   REDIS_HOST/REDIS_PORT/REDIS_PASSWORD           —— Redis（新增）
#   PYTEST_XDIST_WORKER —— xdist 每 worker 独立库（已验证形态）
```

| 配置面 | sqlite 档（现状） | 真环境档（目标） | 说明 |
|---|---|---|---|
| DATABASES | sqlite `:memory:` | postgresql（`DB_*` 注入，`OPTIONS.pool` 真实生效） | 已在 nightly 验证 |
| CACHES | `tests.cache_backend.FakeRedisCache` | `django_redis.cache.RedisCache`（**生产同款 backend 与参数**，`LOCATION` 指向测试 Redis 的 `DEFAULT_CACHE_ID` 逻辑库） | 见 §三.3 隔离设计 |
| CHANNEL_LAYERS | `tests.channel_layer.TestInMemoryChannelLayer` | `common.cache.channel.RedisChannelLayer`（真 pubsub，`CHANNEL_LAYERS_CACHE_ID`） | websocket consumer 行为首次被真覆盖 |
| CELERY | eager + `memory://` | **保持 eager + `memory://`** | 见 §三.4 |
| PASSWORD_HASHERS / MEDIA_ROOT / 日志隔离 | 与现 settings_test 一致 | star-import 继承，不重写 | 单变量原则 |

### 3.2 Redis 的 xdist 隔离设计（本迁移的核心风险点）

nightly 立项 §六 阶段二已预判：FakeRedis 是进程内的，天然隔离；真 Redis 在 xdist 下被全部 worker 共享。隔离方案：

- **CI（ubuntu-latest，4 核 → xdist 约 4-8 worker）**：`db` 编号分配——Redis 16 个逻辑库，预留 db0 兜底，worker `gwN` → db `1 + (N % 15)`；同时叠加**键前缀双保险**（cache `KEY_PREFIX = f"t{N}:"`、channel layer prefix、限流计数器前缀同源），彻底杜绝跨 worker 串扰；
- **本地（-n auto 可达 16+ worker）**：同款前缀规则（前缀与 db 双保险在任意 worker 数下都正确）；
- **conftest 清理语义**：`_clean_cache` 现依赖 `cache.clear()`——真 Redis 上会清掉**整个逻辑库**，多 worker 下互踩。改造为「只清本 worker 前缀」：`delete_pattern(f"{prefix}:*")`（django_redis `delete_pattern` 走 SCAN，大库下有开销，测试库体量可忽略）；
- **限流类用例重审**：真实 INCR + TTL 语义下，共享计数器的用例断言（login 50/h 等）需按 worker 前缀隔离（与 FakeRedis 行为对齐的部分自然兼容）；
- **`MagicCacheData` / `MagicCacheResponse` / `CommonResourceIDsCache`**：依赖 django_redis 的 `lock` / `delete_pattern` / `get_redis_connection`——真 backend 原生支持，FakeRedisCache 的使命终结；lock 的真实语义（阻塞/超时/释放）从「进程内 named lock」升级为真 SET NX PX。

### 3.3 GHA `test.yml` 改造

```yaml
services:
  postgres:                       # 同 nightly 档（health: pg_isready，55433:5432）
    image: postgres:17
  redis:                          # 同 perf.yml 既有形态（health: redis-cli ping，56379:6379）
    image: redis:8.10

env:
  DJANGO_SETTINGS_MODULE: tests.settings_real
  DB_HOST: 127.0.0.1
  DB_PORT: "55433"
  REDIS_HOST: 127.0.0.1
  REDIS_PORT: "56379"
```

其余步骤（uv sync → `uv lock --check` → `pytest -n auto --cov --cov-report=term-missing --cov-fail-under=85` → `check --database default`）保持不变；`manage.py check` 的 `DJANGO_SETTINGS_MODULE` 同步改为真环境档（PG 专属模型检查在真库上执行，覆盖更强）。

### 3.4 celery 保持 eager 的论证

- 真实 broker 只覆盖「任务投递与消费」的传输语义，不改变任务体本身的正确性；任务体已被 eager 覆盖；
- 真消费者引入异步时序 → 断言需要轮询等待 → 门禁 flaky 化（与 pytest-django 的确定性回滚模型相抵触）；
- 导入导出等异步链路已有 Inspect 探针直接执行分支（与 E2E 同款语义）；
- 若后续出现 broker 语义缺陷逃逸，再评估「独立 broker 容器 + 单 worker 专用 db」触发制档位。

### 3.5 本地等价跑法

```bash
cd xadmin-server
bash utils/test_env_reset.sh              # 容器数据清空重启（一次性容器 down→up，零数据态）
DJANGO_SETTINGS_MODULE=tests.settings_real DB_HOST=127.0.0.1 DB_PORT=55433 \
  REDIS_HOST=127.0.0.1 REDIS_PORT=56379 .venv/bin/python -m pytest -n 8
```

`compose.test.yml` 为一次性专用容器（数据不落盘 volume），禁止指向日常/生产实例；Redis 与 loadtest 同用 56379 端口，两者不可同时运行。每次全量测试前先 `bash utils/test_env_reset.sh` 销毁重建（2026-10-01 固化，#33）——PG/Redis 从零数据开始，避免上一轮测试库/Redis 键/E2E shard 库残留的跨轮串扰；E2E 跑批（xadmin-client `pnpm test:e2e:parallel`）每 shard 仍由 `e2e_seed.py` 按库重置。

## 六、风险与对策

| 风险 | 对策 |
|------|------|
| 门禁时长超标 | 实测本地全量 43s（PG `-n auto`），CI 预估 8-15 min（容器启动 + uv sync 占大头）；预算 ≤ 20 min，超则评估 `-n` 上限与 uv 缓存命中 |
| Redis 跨 worker 串扰 | db 编号 + 键前缀双保险（§三.2）；`_clean_cache` 清理语义按前缀收敛 |
| flaky 化（容器/网络抖动） | services health check + retries（同 nightly 档）；连接池超时参数已生产化（connect_timeout=3 等） |
| pk/序列类假设残留 | 阶段 2 全量盘点 `loaddata` / `load_init_json` / 显式 pk 断言消费面；`seed_creator_user` 模式可复制 |
| sqlite 专属 SQL/断言残留 | 已知 1 处（EXPLAIN）已收敛；阶段 1 双轨期由真环境档自动暴露其余 |
| GHA minutes 双轨期 | 阶段 1-2 双轨约 +100-200 min/月，处于 2000 min 免费额度内；阶段 3 起与现状持平 |
| 断言被「弱化以适配 PG」（如 test_index_usage 的规划器分支） | 弱化仅限「规划器选择」类断言（PG 侧改为存在性/前缀守护并注明原因），「行为正确性」断言一律双侧等价 |
