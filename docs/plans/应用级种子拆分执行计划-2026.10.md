## 一、交付定义

拆分完成需同时满足四条，缺一条都算没做完：

1. **归属唯一**：全部种子行（当前 2,094 字段树 + 714 菜单 + 253 白名单 + 约 760 其它）
   100% 可归属到某个 app 或平台层，0 孤儿、0 双归属，由 `load_init_json --check` 守护。
2. **可按 app 装载**：`load_init_json --apps <app>` 只装该 app + 平台层 + 依赖闭包，
   不触碰其它 app 的行，不存在悬空引用。
3. **导入导出对称**：`dump_init_json --apps <app>` 的输出可以直接作为该 app 的 `seeds/` 使用，
   经 `load_init_json --apps <app>` 装回后再导出，逐文件逐字节一致（时间戳除外）。
4. **存量零变化**：空库与存量库各跑一次，`dump_init_json` 结果与改造前等价；
   pk、角色授权、前端契约、权限点行为全部不变。

此后新增逻辑只认这个入口。

### 2.3 数据结构（评审基线，编码时按此实现）

```python
@dataclass(frozen=True)
class SeedFileSpec:
    app: str  # app label 或 PLATFORM
    model: str  # "system.menu"
    path: Path
    kind: str  # contract | generated | sample
    order: int
    rows: int = 0  # discover 阶段填充，用于 --list 与空文件跳过


@dataclass(frozen=True)
class SeedManifest:
    app: str
    depends: tuple[str, ...]
    url_prefixes: tuple[str, ...]
    menu_roots: tuple[str, ...]
    config_keys: tuple[str, ...]
    dict_codes: tuple[str, ...]
    files: tuple[SeedFileSpec, ...]
    sample: tuple[SeedFileSpec, ...]


@dataclass(frozen=True)
class SeedPlan:
    platform: tuple[SeedFileSpec, ...]  # 平台层，内部固定序
    apps: tuple[str, ...]  # 拓扑序
    files: dict[str, tuple[SeedFileSpec, ...]]  # app → 已排序文件
    samples: tuple[SeedFileSpec, ...]
    notes: tuple[str, ...]  # 裁剪 / 跳过说明


@dataclass(frozen=True)
class Problem:
    level: str  # error | warning
    code: str  # OWNERSHIP_DUP | PREFIX_UNCOVERED | REF_MISSING | MANIFEST_INVALID | PK_CONFLICT
    file: Path | None
    row_index: int | None
    message: str
```

### 2.4 接口契约

```python
def discover(*, include_sample: bool = False) -> Discovery
def plan(*, apps=None, include_sample=False, module_filter=None) -> SeedPlan
def validate(seed_plan: SeedPlan) -> list[Problem]        # 只读，不写库、不改文件
def load(seed_plan: SeedPlan, *, isolate=False, strict=True) -> LoadReport
```

四条硬约定：

- `plan()` 是纯函数（只读文件系统），同样的输入永远得到同样的顺序——这是"导入导出对称"的前提。
- `validate()` 不写库；`--check` 就是 `plan() + validate()`，可在 CI 无库环境跑。
- `load()` 内部复用现有的 `filter_conflicting_rows` / `write_seed_rows` /
  `backfill_null_timestamps`，不重写冲突预检（这套逻辑已经覆盖 NULL 键与条件唯一约束）。
- `load()` 结束后固定跑收尾链：时间戳回填 → 字典/配置/路由缓存失效 → 内置角色同步 →
  字段白名单补齐 → 声明式授权应用。顺序不可调换（角色同步依赖菜单与字段树已入库）。

### 批次四：按 app 迁移（由小到大，先叶子后核心）

**实施方式（与初版计划的差异，已落地）**：原计划「逐 app 六步、双读过渡」改为
**一次性文件重排 + 写盘前逐行等价校验**（`manage.py seed_split`）。理由：

- 交付物是纯文件操作，不需要连库，也就不需要「双读」这种过渡态；
- 等价性从「事后对比」前移为**写盘前 fail-closed**（缺行/多行/内容变化任一即拒绝写盘），
  比事后双读更严；
- 幂等：未选中的应用原地不动，重复执行结果不变。

```bash
python manage.py seed_split --dry-run     # 预演：打印各层迁移行数
python manage.py seed_split               # 执行（写盘前先做逐行等价校验）
python manage.py seed_split --verify-only # 幂等复跑校验
```

## 四、导入导出对称性（本方案的核心收益）

拆分后导入与导出共用同一份规划，于是获得三个此前没有的能力：

1. **按 app 导出补丁**：`dump_init_json --apps identity` 产出该 app 的种子文件，
   可直接用于另一个环境的灰度回灌；不再需要整库 dump 后手工挑行。
2. **幂等往返**：`导出 → 清空 → 导入 → 再导出` 逐字节一致。
   这条作为批次五的门禁，任何"拆分后导入导出不等价"都会当场暴露。
3. **首装与升级同源**：新装用 `load_init_json`，升级也用同一份 `seeds/`；
   不再出现"新装靠 loadjson、升级靠 post_upgrade 补丁"的两套事实。

对称性的实现要求（编码时不可省）：

- `dump` 的归属计算与 `load` 必须是**同一函数**，不允许两处各写一份。
- `dump` 的排序按 `plan()` 的输出顺序，保证文件内容稳定（否则 diff 噪音掩盖真实变更）。
- 时间戳字段在比较时归一（`created_time` / `updated_time` / `last_login` 等），
  其余字段逐字比对；不允许"排除整表"式放水。

### 测试基建修复（2026-10-17，与种子拆分同 session）

- **现象**：全量 `pytest` 跑到 98% 后所有 worker 休眠、0% CPU、永不结束（连续复现）。
- **根因**：`pytest.ini` 的 `--maxprocesses=15` 只是 Redis 独库方案的**硬上限**，
  但在 18 核开发机上 `-n auto` 会顶到 15 worker，单个 worker 被拖到失联后
  xdist master 永久等待（xdist 不检测 worker 失联）——不是用例失败，是调度崩溃。
  单文件/`-n 8` 均正常，可排除用例本身问题。
- **修复**：默认并行度降为 8（`--maxprocesses=8`），理由与实测写进 ini 注释；
  CI 仅 4 核且显式 `-n auto`，不受影响。
- **验证**：`uv run pytest tests/unit tests/integration`（不带 `-n`）→ 6219 passed /
  2 skipped / EXIT=0 / 5分23秒。
