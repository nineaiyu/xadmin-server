# 原地升级立项与方案（存量 4.x 库零丢失升级到 5.x）

> **一句话结论**：四域切分之前的旧库（`system_userinfo` 等表名）当前只能「备份 → 清库重建 → 回灌」，
> 该路径对二开用户代价过高（业务域数据不在搬运清单、二开表物理文件不搬、二开 app 的旧迁移引用要人工改写）；
> 本方案**立项**做「真·原地升级」——把旧结构**在同一个库里**对齐到 5.x 目标结构（表改名 + 补列 + 账本/权限/存量串重指），
> 数据、主键、UUID、时间戳、媒体文件全部不动，二开表原样保留。决策见
> [ADR-094](../adr/ADR-094-inplace-upgrade-legacy-libraries.md)。

- 状态：**立项（设计与分期已定，分批实施）**；本文是方案与调研台账，执行入口见 [DEV-TASKS.md](DEV-TASKS.md)
- 分工：升级**判定与处置口径**见 [ops/upgrade-stock.md](../ops/upgrade-stock.md)、**操作手册**见
  [ops/upgrade-4x-to-5x.md](../ops/upgrade-4x-to-5x.md)（现状）；本文回答「怎么从根上改成原地升级」

## 一、目标与验收基线

| # | 目标 | 可测口径 |
|---|------|----------|
| 1 | 旧库**不动数据**即可升到 5.x | 升级前后逐表行数一致；用户/部门/角色的主键、UUID、`created_time` 与旧库完全相同 |
| 2 | **二开数据完整** | 二开表原样保留（含行、主键、外键、文件字段）；二开 app 的迁移无需人工改写即可继续 `migrate` |
| 3 | 业务域数据不丢 | 审批实例 / 动态表单提交 / 数据集 / 报表 / 大屏 / 聊天 / 审计与登录日志 / 任务与执行记录 / PAT 与 API 应用 / webhook 投递 全部在库（旧版本没有这些表时自然为空） |
| 4 | 媒体与附件可用 | 附件与头像的存储路径不变、下载与预览可用（不重新落盘、不重新编码） |
| 5 | 一键、判定明确、失败可退 | 安装器一条命令内完成（判定 → 预演 → 执行 → 复检）；不支持的结构**fail-closed** 并给差异报告；任何阶段失败可用升级前备份原样恢复 |
| 6 | 不牺牲全新安装 | 全新安装与「四域切分之后」的库继续走现有链路，行为与性能零变化 |

## 二、调研结论

### 2.1 迁移链是怎么变成今天这样的

2026-10 期间迁移链经历**四轮清库重建式整理**（删除业务 app 历史迁移、按当前模型重新生成初始迁移）：

| 轮次 | 范围 | 依据 |
|------|------|------|
| 第一轮 | approval / ai / dataset 等 app 的初始迁移由「零 DDL 认领」改为真实建表 | [ADR-058](../adr/ADR-058-system-migration-squash.md) |
| 第二轮 | system `0004~0011` 合并；dataset / approval / ai / message 全链合并；表归域改名 | [ADR-084](../adr/ADR-084-migration-squash-2026h2.md) |
| 第三轮 | system 拆分为 identity / file / audit / task 四域 | [system四域切分映射-2026.10.md](system四域切分映射-2026.10.md) |
| 第四轮（5.0） | 全部业务 app 收敛为初始迁移（每 app `0001_initial`，必要时 `0002_initial`） | [ADR-093](../adr/ADR-093-migration-consolidation-and-ledger-claim.md) |

**分界线**＝四域切分：切分**之后**的 4.x 链与 5.0 合并链**结构等价**（可账本认领 → 原地升级，已交付）；
切分**之前**的库（表名 `system_*`、字段集更少）与合并链不等价，被 `upgrade_check` 判为
`legacy-chain-pre-split` 并拒绝（`system/utils/platform/migration_ledger.py:61-68` 的 `PRE_SPLIT_TABLES`）。

### 2.2 结构差异的事实（可量化）

用仓库内的历史 tag 直接对账（`git show`/`git grep`，全部可复现）：

| 维度 | 4.2.5（切分前） | 5.0.0 | 当前工作树 |
|------|----------------|-------|-----------|
| 顶层业务 app | 5 个（system / notifications / settings / captcha / common） | 15 个（identity / file / audit / task / approval / dataset / ai / message / mfa / demo / …） | 同 5.0.0 并继续增长 |
| `CreateModel` 合计 | 28 | 86 | 库内 126 张表（含框架与三方表） |
| 业务迁移文件 | 9 个（`system/000{1,2,3}`、`notifications/000{1,2}`、`settings/000{1,2}`、`captcha/0001`、`common/0001`） | 24 个 | 每 app 初始迁移为主 |

- **同名换域（域切分的直接证据，9 个模型）**：`UserInfo` / `DeptInfo` / `UserRole` → `identity`；
  `UploadFile` → `file`；`OperationLog` / `UserLoginLog` → `audit`；`Field` → `audit` + `system`；
  `Monitor` → `common` → `system`。
- **73 个模型在 4.2.5 根本不存在**（approval 13 / dataset 9 / ai 6 / task 7 / message 3 / mfa 1 …）：
  即对 4.2.5 库而言它们是**全新表**（`migrate` 建即可），**没有历史数据需要搬运**。
  → 4.2.5 → 5.x 的真正风险面收敛在「这 28 个旧模型的结构与数据」上，而不是全库。
- **列集演进**：`deleted_at`（软删）、`file_uploadfile.md5sum` / `category`、`system_menumeta` 展示列等
  为切分后新增（[ADR-093](../adr/ADR-093-migration-consolidation-and-ledger-claim.md) §修订）。
- **关键使能条件（本次调研最重要的发现）**：`v4.1.0 ~ v4.2.5` 的历史 tag **都在仓库里**——
  旧模型定义、旧迁移、旧列集可以**权威还原**（本节的量化即由 tag 直接产出），
  因此「原地改名 + 补列」的映射表**可以机械生成并逐条校对**，不再受「缺素材」限制。

### 2.3 根因：为什么今天必须清库重建

1. **同名迁移让结构永久停旧**：5.x 链是清库重建式产物（与旧链同名、内容不同、且**不使用 `replaces`**，
   `grep -r replaces **/migrations` = 0 命中）。旧库的 `system.0001_initial` 被 Django 视为「已应用」，
   合并链的建表/加列**永不执行**。实测两处硬报错：
   `column system_menu.deleted_at does not exist`、`InconsistentMigrationHistory: system.0001_initial is applied
   before its dependency identity.0001_initial`（[ADR-093](../adr/ADR-093-migration-consolidation-and-ledger-claim.md) §修订）。
2. **账本认领只写记录、不执行 DDL**（`migration_ledger.py:184-219`）：它只能让「结构已经等价」的库
   把记录对齐，无法把旧结构变成新结构；`evaluate_ledger` 对 pre-split 直接判 `unsupported`
   （`migration_ledger.py:173-174`）并抛 `LedgerError`（`:195-203`）。
3. **四域切分改了表名与 `app_label`**，还改了存量数据里的**字符串引用**（`DataMaskRule.model`、
   `ImportTemplate.target_model`、`ModelLabelField.name`、`DataPermission.rules[].table`、
   `dataset.target_model`、trgm 表名快照、菜单 `/api/system/*` 前缀等，
   清单见 [system四域切分映射-2026.10.md](system四域切分映射-2026.10.md) §1.2）：**当前没有任何迁移承担重指**。
4. **二开 app 的迁移图在 5.x 里解析不了**：二开迁移若依赖旧节点（如 `("system","0002_operationlog_exec_time_…")`、
   `("common","0001_initial")`、`("notifications","0002_initial")`）或写 `to="system.userinfo"`，
   在 5.x **要么节点不存在、要么同名不同内容**；`migrate` 建图即失败。
   这一条同时解释了「回灌为什么会丢二开」：**不是行丢了，而是二开 app 装不回去**——
   必须先人工改写它的迁移（现有文档只给清单，见 [ops/upgrade-4x-to-5x.md](../ops/upgrade-4x-to-5x.md) §附）。

### 2.4 现有「回灌」路径的真实损失面（逐条给证据）

| # | 损失面 | 现状与证据 |
|---|--------|-----------|
| 1 | 二开 app 迁移要人工改写 | 文档只给改写清单（[ops/upgrade-4x-to-5x.md](../ops/upgrade-4x-to-5x.md) §附「在框架模型上新增的字段」「改了框架自带 app 名/表名」两行） |
| 2 | 二开表的**物理文件**不搬 | 同上「二开表里的文件字段：当前工具只搬框架附件」 |

> 上表 1~5 才是二开用户真正的代价来源。也正因如此，**方向不是在回灌上打补丁，而是补上原地升级**。

## 三、方案设计与选型

### 3.1 三条候选路线

| 维度 | 路线一：结构对齐器（introspection + 声明式计划） | 路线二：过渡迁移链（state-only 历史链 + 真实拆分迁移） | 路线三：无损回灌增强 |
|------|-----------------------------------------------|--------------------------------------------------|---------------------|
| 做法 | 读活库 + 目标态 → 生成 DDL/DML 计划 → 同库执行 → 重写账本 | 用 tag 把旧链还原为「只声明状态」的迁移，把域切分写成真实迁移追加其后 | 扩展 `ENTITIES` 到全部业务域 + 二开文件 + 加密处置 |
| 数据保全 | **全保**（改名不动行；业务域表原样） | **全保** | 仅搬运面内 |
| 二开迁移兼容 | 需配合兼容层（见 3.3） | **天然兼容**（旧节点名与 `to=` 全部可解析） | 同样需兼容层（新库里二开 app 也要装得上） |
| 对全新安装的影响 | **零**（不动 5.x 链） | 大（要么条件化 DDL，要么重做历史链） | 零 |
| 可预演 / 可回滚 | 强（计划可打印、可逐阶段、可断点续跑） | 中（迁移链不可预演，回滚靠备份） | 中 |
| 工作量 | 中（映射目录 + 执行器 + 报告） | 大（重建多条历史链 + 双轨语义） | 中（但解决不了 2.3 第 4 条） |
| 结论 | **主路线** | **取其兼容层**用于二开迁移图 | **降级为逃生舱** |

**选型**：路线一为主（物理结构对齐），路线二的「兼容层」形态用于解决二开迁移图（3.3），
路线三保留为无法就地对齐时的兜底（文档标注为逃生舱，不再是官方首选）。

### 3.2 主路线详细设计

**① 结构画像与家族（fail-closed 的输入）**

- 从 tag 生成「旧结构目录」：`depts/roles/users/...` 等实体的旧表名、列集、可空性、默认值、索引名，
  以及 `system.0002/0003` 这类历史节点；产物入库为**数据文件 + 生成脚本**（可重生成、可 diff）。
- 结构画像 = 表存在性 + 关键列存在性 + 关键约束存在性；按家族收敛：`4.1.x` / `4.2.0~4.2.4` / `4.2.5`（tag 全在）。
- 画像命中不了任何家族、或检测到客户自定义改动（框架表被改列/改名/加约束）→ **拒绝执行**，
  输出差异报告与人工路径（宁可让用户走回灌，也不产生「半对齐」的库）。

**② 结构差异目录（catalog）**

- 形态：`{旧表 → 新表, 旧列 → 新列/新增列 + 回填策略, 需要重指的存量字符串注册表}`，
  由 tag 机械生成初稿 + 人工校对入库；**每条映射必须可守护**（旧表在 tag 中存在、新表在当前模型中存在）。
- 覆盖：4.2.5 的 28 个模型（表改名 / 补列）+ 现有 126 张表的归属分类（保留 / 改名 / 新建 / 由种子提供）。

**③ 执行计划（每步可 dry-run，输出人类可读 + JSON 报告）**

| 步 | 动作 | 关键点 |
|----|------|--------|
| 0 | 预检与画像 | 复用 `upgrade_check`；新增「可原地升级 / 阻断原因」判定 |
| 1 | 强制备份 | 复用 `ops/db_backup.sh`（含媒体清单与 `.latest_backup` 标记） |
| 2 | 表改名 / 跨域迁移 | `ALTER TABLE ... RENAME TO`（PG 保留约束、索引、序列、外键）→ 二开表的外键**自动跟随**，无需改数据 |
| 3 | 补列与回填 | `deleted_at` 等新增列 + 默认值；需要数据推导的列单独登记回填策略 |
| 4 | 索引 / 约束 / 序列修正 | 与新链建出的结构做归一化比对（沿用 ADR-093 的 `pg_dump --schema-only` 归一化比对口径） |
| 5 | `contenttypes` / 权限点重指 | 旧 `system.*` 标签行 → 新 `app_label`；`auth_permission` 由 `post_migrate` 重建，本步只保证不冲突 |
| 6 | 存量字符串重指 | 按 §2.3 第 3 条的登记表逐项改写（模型串、表名快照、菜单 API 前缀用既有 `migrate_api_prefixes`） |
| 7 | 账本重写 | 复用认领机制：删旧记录、把 5.x 链补记为已应用（此时结构已对齐） |
| 8 | `post_upgrade` | 种子 / 语言包 / 缓存 / 权限缺口扫描（既有命令，幂等） |
| 9 | 验收 | 逐表行数、外键完整性、旧密码登录、附件可下载、`upgrade_check` = `up-to-date` |

- **事务与停机**：PG 支持事务性 DDL，第 2~7 步在**单事务**内提交（失败自动回滚）；长事务时间需实测评估
  （10 万级业务表规模下目标 < 2 分钟），必要时拆阶段 + `--resume`（幂等重入）。
- **回滚**：任一步失败 → 事务回滚（结构层）；跨阶段失败 → 恢复第 1 步备份。不做「反向迁移」承诺。
- **接线**：`xadmin.sh upgrade` 内新增判定分支（预演报告 → 交互确认 → 执行 → 复检），
  `SKIP_*` 逃生舱与既有交互默认值口径保持不变。

### 3.3 二开适配层（解决 2.3 第 4 条）

- **首选：历史链兼容包**。用 tag 把旧链原样还原为「只声明状态、不执行 DDL」的迁移
  （`SeparateDatabaseAndState(state_operations=[…原 operations…])`，节点名与原链完全一致），
  随 5.x 一起发布但**只在升级库路径被使用**（全新安装不经过它）。
  效果：二开迁移的 `dependencies` / `to="system.userinfo"` **零改动即可解析**；
  结构与数据由 3.2 的对齐器负责，兼容包只解决「迁移图能不能建起来」。
- **降级：迁移改写工具**。`manage.py rewrite_legacy_refs`（或安装器封装）按登记表改写二开 app 的
  `app_label` / `to=` / `dependencies` / 表名字符串，改写前打印 diff、改写需显式确认。
  适用：深度定制（自建表名前缀、改了框架表结构）且兼容包无法覆盖的场景。
- **报表化**：二次开发侧的处理结果（兼容包命中 / 改写条数 / 无法自动处理项）必须写进升级报告，
  做到「机器能判的全判、判不了的说清楚」。

### 3.4 边界（明确不做）

1. 不做零停机升级：结构对齐需停机窗口（目标为分钟级，可用 `blue-green.md` 兜底另议）。
2. 不承诺「任意定制库自动收敛」：改了框架表结构/字段的库一律 fail-closed + 差异报告 + 人工或回灌。
3. 不做 Django 迁移的反向回滚；回滚一律走备份恢复。
4. 不改动已发布历史链的组织方式（不回滚四轮重建）；全新安装路径保持零变化。
5. PG 大版本（16 → 17）数据目录迁移维持现有做法（`pg_dump` / `pg_restore`），不在本项内升级为 `pg_upgrade`。

## 八、执行记录

### 第一批（可行性验证）——2026-10-17

**关键突破：旧迁移能被当前 Django 直接执行**。旧迁移是标准 Django 迁移，只依赖
`common.core.models` / `common.fields.image` 这类仍在的基类；把它们放进一个只装旧 app 迁移的
临时工程（+ `AUTH_USER_MODEL` 最小存根），就能在测试 PG 上**真实建出 4.2.5 结构库**（含旧表名、
列类型、索引、外键与旧迁移账本）——不需要旧版本依赖，也不需要客户库导出。这使「样本靶 →

已交付（`xadmin-server`）：

| 交付物 | 职责 |

     不修复** → 现改为收尾**自动补齐**（`fill_field_permissions`，只补缺口、不改管理员已配置的裁剪）
     + 清元数据缓存；实机补齐 4868 个节点、约 490 条「角色×菜单」行后，公告/已读/我的消息/用户/
     部门/角色等页面全部恢复；
- **安装器**：新增 `INPLACE_ALIGN=1`（无人值守；说明「管道喂 y 会被 `docker exec -i` 吞掉」）+ 探询四态
  结论（安装器按 `inplace-*` 标记行判读）+ 预检/预演/确认/执行/复检接线。
