# 验证码企业级增强方案：风险分级 + 无感验证 + 协议加固（2026-10）

> 状态：**B1~B8 已交付（2026-10-26）** ｜ 范围：`captcha` + `identity` + `settings`（server）、登录与验证码组件族（client）
> 姊妹篇：[验证码多形态增强方案-2026.10.md](验证码多形态增强方案-2026.10.md)（**已于 2026-10-26 交付**三题型交互式验证码）。
> 本篇承接其 §十.3 明确留白的部分：行为风控、无感放行、设备/环境信号、难度自适应、观测与处置联动，
> 并补一条该篇未覆盖的主线：**票据协议不可离线重放**。

## 〇、一句话结论

现在的验证码「题型像产品，决策像 demo」：出题与判题已经合格，但**所有人一律被要求做题**，
判据只有几何容差加三条轨迹硬规则，票据不绑定动作，且系统里**没有任何一处记录过"谁在打我们、打成什么样"**。
本方案把它升级成五层纵深（信号 → 决策 → 挑战 → 票据 → 处置）+ 一层观测，
并保证**默认关闭、影子先行、一键回退**——因为误拦一个真人的代价远大于放过一个脚本。

### 差距清单（对标极验 v4 / 网易易盾 / 腾讯天御 / Cloudflare Turnstile / ALTCHA·Cap）

- **G1 无风险分级**：所有人一律做题。大厂对低风险用户**无感放行**（Turnstile 官方口径：无交互与图片题等效），
  易盾/极验的「智能无感」是主推形态。这是我们**体验差距最大的一条**。
- **G2 行为判据太薄**：三条规则只挡得住"直接 POST 一个坐标"的最低成本脚本。业界实测打码平台的
  滑块轨迹模拟准确率可达八成以上，真正区分人机的是**曲线度、加速度分布、抖动、按下-抬起时长、
  点击间隔分布**这类多维特征。
- **G3 无环境信号**：`navigator.webdriver`、UA 与 `sec-ch-ua` 一致性、时区/语言/分辨率矛盾、
  Canvas/WebGL 摘要、PoW 是否完成——一个都没采。攻击者用 requests + 一张图就能走完全部协议。
- **G4 票据可转移**：ticket 只绑 `scene`。**在 A 会话/浏览器上验证通过的票，可以在 B 上一模一样地消费**，
  这正是打码平台的商业模式（批量产票再灌业务请求）。极验 v4 / 阿里云盾用
  `lot_number + gen_time + HMAC-SHA256 sign_token` 把这一点堵在协议层。
- **G5 零观测**：我们**不知道**有没有人在打、哪种题被打穿、拦截率随时间怎么变。上篇方案 §10 记的
  业界教训（上线两周后拦截率明显下降，一查是打码平台适配了新样式）——我们连"下降"这件事都看不见。
- **G6 难度恒定**：高风险流量和低风险流量拿到同一道 4px 容差的题。
- **G7 无阶梯处置**：失败 1 次和失败 100 次，攻击者面对的阻力完全一样。
- **G8 无统一挂载面（这是最容易被忽略、后果最实在的一条）**：人机校验靠逐视图手工调用，
  **没有中间件、没有装饰器、没有门禁**。今天已有 6 个消费点，二开用户再加匿名写接口时
  漏挂一个就等于开了个无防护入口——而且**没有任何机制会发现**。
  对照：`identity/views/auth/register.py` 与 `reset.py` 都不直接校验 captcha，
  只是"依赖前置发码端点已校验"，这个隐含约定现在无处可查。
- **G9 无障碍回退实际是断的**：上篇方案把"图片码 + 其音频链路"当作交互式验证码的无障碍逃生舱，
  但 `CAPTCHA_FLITE_PATH=None` 且 `flite`/`sox` 二进制不在镜像里——**音频验证码默认 404**。
  也就是说视障用户在 `interactive` 模式下的"回退"只剩仍然需要看清扭曲字符的图片码。
  安全产品意义上的"可用性"和文档里写出来的不是一回事，这条必须实测收口。
- **G10 缓存故障语义不统一**：交互式链路处处 fail-**closed**（[captcha/services.py:116](../../captcha/services.py#L116) 等），
  但限流底座 `allow_by_identity` 在缓存故障时 fail-**open**（[common/core/throttle.py:31](../../packages/xadmin-common/common/core/throttle.py#L31)）。
  新风险层必须明确表态：**限流可以宽松（宁可放行也不误伤），风险决策必须严格（拿不到信号就当高风险）**，
  两者语义不同，不能笼统继承。

### 一个必须承认的前提（决定本方案的取舍）

字符码有 OCR、滑块缺口有 CV 模板匹配、点选文字能被多模态大模型读出——**"把题目出得更难"这条路在
2026 年已经走到头**（公开评测显示新一代视觉语言模型可批量攻破数十种主流网页验证码，
且攻击者把模型能力提升的成本转嫁给了我们，我们却不能相应提高真人答题成本）。
还剩下三条能持续抬高成本的轴，本方案就长在这三条上：

1. **协议轴**：让"离线拿答案 + 在线重放"不可行（签名、极短时效、动作绑定、一次性 nonce）。
2. **算力轴**：让每一次尝试都必须**付出真实浏览器的计算成本**（PoW），且成本可由服务端上调。
3. **数据轴**：让**批量行为在数据面上必然露形**（指纹/网段/频率/时间序列 → 大盘 → 阶梯封禁）。

题型难度只是第四位的装饰。

## 二、目标与非目标

**目标**

1. **更安全**：过验证的成本从「识别一张图」抬到「模拟真实浏览器 + 付算力 + 承担被识别与封禁的风险」。
2. **更好用**：正常用户默认路径是**零交互或一次点击**；只有可疑流量才看到题目，且越可疑越难。
   无感路径端到端 P50 < 300ms。
3. **可运营**：全链路留痕 + 大盘 + 阈值/权重/开关在管理页面热更，不发版就能调策略。
4. **可回退**：`off / shadow / enforce` 三档，默认 `off` —— 升级零行为变化（项目铁律），
   出问题一键退回今天的语义。
5. **零新增运行时依赖**：全部自研（Pillow 出题已有，PoW 用 Web Crypto，HMAC 用标准库），
   不引入任何第三方验证码包/云服务。私有化离线部署是产品底线。

**非目标（明确不做，防反复重提）**

- 不接极验/易盾/天御/reCAPTCHA/Turnstile 等**任何**运行时云依赖：私有化底线 + 行为数据出域的 PIPL 风险。
- 不上 ML 训练与推理管线：无标注样本、无算力预算、单人维护。只做**可解释规则评分 + 统计基线**，
  决策函数留一个 `score_provider` 注册位供未来接入。
- 不做人脸/活体/摄像头手势验证（合规与成本都不匹配中后台场景）。
- 不做跨站追踪式设备 ID；不做"永久唯一标识某台设备"。
- 不动短信/邮箱验证码链路（`auth_verify_code_*`）；不改图片码 `CaptchaStore` 对外契约。
- 不为开放平台 API（PAT / OAuth / Webhook）引入人机验证——那是速率限制与签名的问题，边界见 §十.6。

## 三、总体架构（五层纵深 + 一层观测 + 两项横切）

```
L0 信号层 ── 前端环境包 env / 行为包 track / PoW 解答  +  服务端旁路（IP·网段·UA·ClientHints·Referer·会话历史）
     ↓
L1 决策层 ── RiskEngine：信号 → 风险分 0~100 + reasons[] → decision
     │       allow(无感发票) | light(点击即过) | challenge(常规题) | hard(难题型) | deny(直接拒)
     ↓
L2 挑战层 ── 题型插件注册表（已有基座扩展 difficulty 维度）
     │       slide / rotate / click（已有）+ pow（新增）+ wordorder 语序点选（新增）
     ↓
L3 票据层 ── TicketAuthority：HMAC 签名 + (scene, action) 绑定 + fp/IP 弱绑定 + 内嵌 exp + nonce 一次性
     ↓
L4 处置层 ── 阶梯计数（IP / 账号 / 指纹）→ 强制难题型 → 冷却 → 临时封禁 → 可选联动登录锁定 → 蜜罐
     ↓
L5 观测层 ── CaptchaLog 全链路留痕 → 大盘（趋势/通过率/风险分布/TopN 拦截原因）→ 保留期清理
```

**贯穿三档模式**：`CAPTCHA_RISK_MODE = off | shadow | enforce`

| 模式 | 行为 | 用途 |
|------|------|------|
| `off`（默认） | 完全等于今天：每场景出题、判题、发票，风险层不跑 | 升级零行为变化；事故回退 |
| `shadow` | 跑完整评分与决策并落日志，但**不改变放行结果**（仍按今天出题） | 积累基线、校准阈值，看"若开启会放行/拦截多少" |
| `enforce` | 按决策执行分级验证 | 达标后正式启用 |

切换 `enforce` 的**硬前置**：影子期 ≥3 个自然日、样本 ≥1000 次验证、
且「按 enforce 会被 deny 的流量」中经人工核对确认为真人的比例 < 0.5%。

## 四、逐层设计（要点）

> 详细设计（信号项、规则表、PoW 参数、票据字段、处置阶梯、观测字段、挂载面收口与无障碍落地）
> 已拆至姊妹篇 **[验证码企业级增强实施细则-2026.10.md](验证码企业级增强实施细则-2026.10.md)**（受 40KB 单篇体积门禁约束）。
> 本节只留每层的一句话结论，评审以细则篇为准。

| 层 | 一句话结论 | 详见 |
|----|-----------|------|
| **L3 票据** | 票据从「不记名代金券」升级为 **HMAC 签名 + `(scene, action)` 绑定 + nonce 一次性 + 内嵌过期 + 分档 TTL + 双密钥轮换**，并给 verify 请求本身加签与时间窗——**这是协议轴的主战场，也是第一批要做的** | 细则 §一 |
| **L0 信号** | 前端环境包 / 行为包 / PoW 解答 + 服务端旁路（IP 网段、Client Hints 自洽性、challenge→verify 墙钟）；三条硬约束：键盘不扣分、隐私最小化、承认客户端信号必然可伪造 | 细则 §二 |
| **L1 决策** | 16 条**可解释、DB 可配**规则 → 风险分 → `allow/light/challenge/hard/deny` 五档；所有拒绝路径响应体字节级同形（防评分表变成攻击者的免费探针） | 细则 §三 |
| **L2 挑战** | 题型契约加 `difficulty` 维度；新增 **`pow`（算力轴）**与 `wordorder`（抗多模态顺序约束）；题型轮换按风险加权 + 频次配额 | 细则 §四 |
| **L4 处置** | **全部复用既有基座**（`check_is_block` / `BlockUtil` 家族 / IP 白名单 / `IpScopedThrottle` / `UsedOtpCodeCache` 防重放范式）——新增的是策略不是机制 | 细则 §五 |
| **L5 观测** | `CaptchaLog` 全链路留痕（异步写、遥测故障不得影响验证结果）+ 设置页「验证数据」页签；**「各题型通过率对比」是题型被打穿的第一预警信号** | 细则 §七 |
| **横切 A** | `require_human(scene, action)` 统一入口 + 新守护门禁 `check_captcha_coverage.py`：**新匿名写接口漏挂人机校验 = CI 红**（治 G8） | 细则 §六 |
| **横切 B** | 音频验证码实测可用 + `allow/light` 读屏可完成 + 键盘不扣分 + 合规告知落点（治 G9——今天的无障碍逃生舱实际是 404） | 细则 §八 |

## 五、接口与契约变更

```
POST /api/identity/auth/captcha/challenge   # 变更：请求 +{scene, env?}；响应 +{difficulty, pow?, ck?}
                                            # 新语义：decision=allow 时**不出题直接发票**（响应体与"做过题"同形）
POST /api/identity/auth/captcha/verify      # 变更：请求 +{action, env?, pow_answer?, gen_time, nonce, sign}
                                            # action=意图动作（scene 登记表校验，CAPTCHA_ACTION_BIND 开启时必填）
GET  /api/settings/captcha/general          # 变更：+风险策略字段组（模式/阈值/权重/PoW/白名单）
GET  /api/settings/captcha/stats             # 新增：大盘聚合（时间窗）
GET  /api/settings/captcha/log               # 新增：CaptchaLog 列表（SearchFields+SearchColumns，只读）
```

- `GET /api/identity/auth/capabilities` 各场景节点：`captcha_types` 语义不变；新增中性字段
  `captcha_flow: "always" | "adaptive"`。**注意**：capabilities 是匿名端点，
  绝不能用它泄露"你现在是低风险会被放行"——`adaptive` 只表达"可能需要、也可能不需要做题"。
- 消费点：`identity/utils/auth/captcha.py` 的 `check_token_and_captcha` 从 `(ticket, scene)`
  扩为 `(ticket, scene, action)`，`action` 由各视图传入常量（服务端单源）。
- 契约流：先改 [docs/schema/](../schema/) → `dump_openapi` → 前端 `pnpm sync:contract`
  → `check:contract` / `check:openapi-types` / `check:api-routes`（红线 3，不可跳）。
- 权限点：新页面/新视图的权限码落 **所属应用**的 `<app>/seeds/{menu,menumeta}.json`
  （`SettingCaptcha` 已存在，大盘页新起 `CaptchaDashboard`），
  `sync_menu_permissions --update-seed` 回写后 `--dry-run` 缺口 0；同一 `(path, method)` 只登记一个权限码。
- 新视图 docstring **首行 ≤24 字名词短语**（会被取作菜单显示名，`check_menu_titles` 拦）。

## 八、测试与验收口径

**后端单测**
- 规则表逐条 命中/未命中/开关关闭 三态（表驱动）；阈值→决策全区间边界（含恰好等于阈值）；
- 票据：HMAC 篡改必败、`exp` 过期必败、nonce 二次消费必败、**跨 `action` 消费必败**、
  `fp`/`ip` 漂移→降级重验而非硬拒、双密钥轮换期间两把 key 都能验；
- PoW：固定向量解答校验、bits 上限、降级路径可过；
- 难度档容差边界；阶梯计数与冷却；蜜罐命中即 deny；`hist_good` 负分生效。

**后端集成**
- **`off` 模式行为与今天逐字节一致**（守护用例锁死，防误开造成生产事故）；
- `shadow` 下放行结果与 `off` 一致、但日志多出 `would_decision`；
- `enforce` 下：低分无题直登、高分出难题型、deny 与答案错误**响应体全等**（防探测断言）；
- 信任网段命中时恒 `allow`（内网白名单实测）；
- 遥测异常注入（Celery 不可用）不影响验证结果。

**负面用例（攻击模拟，本方案的价值就体现在这里）**
- 纯 `curl` 直接 POST `verify`（无 `env`/无 PoW/无轨迹/无签名）→ 必被拒；
- 直线 + 匀速 + 零抖动轨迹 → 分数落在 `hard`/`deny` 区间；
- 同一票据重放两次 → 第二次必败；A scene 票据用于 B action → 必败；
- 批量 challenge 囤票 → 触发 `freq_ip` 并被冷却。

**回归**
- 现有 `tests/integration/test_captcha_login.py` 与 E2E `e2e/captcha-interactive.e2e.ts`
  （三题型真实登录 + 无障碍回退 + 设置页）在默认 `off` 下**必须零改动全绿**；
- `tests/settings_e2e.py` 显式 `CAPTCHA_RISK_MODE = off`（新增键，防大盘测试流量把风险层跑起来）；
  另新增 `e2e/captcha-risk.e2e.ts`：以受控配置临时 `enforce` + 测试网段白名单，
  断言"无题直登"与"连续失败后升级为难题型"，`finally` 恢复（用例幂等，双浏览器共享库）。

**门禁全绿清单**（后端）`uv run pytest -n auto`、`ruff format --check && ruff check`、`uv run mypy`、
`check_cross_app_imports`、`check_file_length`、`check_function_length`、`check_cache_keys --strict`、
`check_ledger_ids`、`check_menu_titles`、`check_doc_facts/index/paths/size`、
**`makemigrations --check --dry-run`（本方案有新增模型，必须配套迁移）**、`load_init_json --check`、
`sync_menu_permissions --dry-run`（缺口 0）、`manage.py doctor`（含"enforce 且白名单为空"告警项）；
**（前端）**`pnpm typecheck`、`pnpm lint`、`pnpm test:run`、`check:*` 全套、`node scripts/check-file-length.mjs`；
**（E2E）**改后端 → `*:fresh` 变体 + 双浏览器；**（真实环境）**重启容器后手工跑一次
`off → shadow → enforce` 三档切换与白名单直登。

**「做完了」的判据（不是"代码写完了"）**
1. `off` 下全站行为与今天一致（升级安全）；
2. `shadow` 大盘能回答"如果开启，会放行/拦下多少、按什么理由"；
3. 负面用例全绿（攻击路径确实变贵，不是自我感觉）；
4. `enforce` 在真实浏览器 + 真实移动网络 + 键盘辅助三条路径下均无误拦实测；
5. 内网白名单实测有效（不会把自己人锁在外面）。

## 十、风险与开放问题

1. **误拦真人是本方案唯一不可接受的失败模式。** 防线是四重：默认 `off` → `shadow` 看基线 →
   `enforce` 灰度 → 信任网段白名单兜底。`doctor` 增加"enforce 且白名单为空"告警。
2. **规则分值会随对抗衰减。** 业界经验：行为模型对已知 bot 识别率可达 94%，对新变种衰减到 ~78%。
   对策是把"变贵"做在**协议轴与算力轴**（不依赖识别准不准），把识别层做成
   **不发版就能改的数据**；大盘的「各题型通过率对比」是衰减的第一个预警信号。
3. **PoW 的双刃性**：客户端算力成本若被服务端无上限调用，等于我们自己造了个放大器，
   也给低配设备/低端浏览器制造障碍。硬约束：bits 服务端封顶 20、按 IP 限总预算、
   Worker 不可用有降级路径且不因降级判死。
4. **指纹的合规与口碑**：PIPL 最小必要 + 告知同意。落点＝设置页文案写清采集面、
   零第三方外发（可审计）、IP 只取网段前缀哈希、Canvas 只留摘要、保留期默认 30 天、盐可轮换。
   中后台部署在客户内网，风险面远小于 C 端，但**产品是交付给客户的**，文档必须替客户把话说清。
5. **客户端信号必然可伪造**（真实浏览器反检测工具已商用化）。不与之对赌：单信号不做硬拒绝，
   靠多信号加权 + 频率/历史关联 + 算力成本抬升。蜜罐是唯一"必然为假"的强信号。
6. **非浏览器客户端不在本方案射程内**：开放平台（PAT / OAuth / Webhook）与二开 API 调用的
   滥用治理是速率限制 + 签名 + 数据权限的问题，**不要**给人机验证抢这个职责，边界写进文档防止误用。
7. **默认模式要不要变**：图片码既然可 OCR，长期方向是 `interactive`/`risk` 取代 `image` 作默认。
   但这违反"升级零行为变化"，属于发版级决策（见 §十一）。
8. **`inspect` 端点风险面扩大**：现有答案检查端点仅在 E2E 配置挂载、并有"生产默认配置下该路由不存在"
   的守护用例；本方案新增的统计/日志端点同样必须是**只读 + 需权限 + 不含任何可反推答案的字段**，
   且新增守护用例。

   消费端两端完全一致才放行，未绑票据一律拒绝（封死「省略 action 签发万能票」）。

2. **verify 加签**：`CAPTCHA_RISK_MODE` 非 off 时下发 `ck`，前端以 Web Crypto 计算

3. **日志 `mode` 记风险档**（off/shadow/enforce），不是出题模式（后者由 `type` 与链路本身表达）。
4. **观测端点落 settings 安全域**：实际路径 `/api/settings/captcha/log` 与
