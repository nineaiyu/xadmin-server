# 应用级种子拆分方案（2026.10）

> 状态：**方案设计，待评审，未实施**。
> 影响面：`xadmin-server` 的种子组织与装载链路（`loadjson/`、`load_init_json`、`sync_model_field`、
> `sync_menu_permissions --update-seed`、`dump_init_json`、`module remove`）、守护测试与二开文档。
> 决策落地后需补 ADR，并重开《[模块化与功能裁剪](../architecture/模块化与功能裁剪.md)》中
> 「`loadjson` 目录级拆分 不立项」的结论（理由见§十一）。

## 一、结论摘要

1. **按 app 归属拆分文件**，而不是按功能模块拆分：一行种子的归属由「它描述谁的接口/模型」决定，
   每个 app 一个 `seeds/` 目录，文件级零共享；功能模块裁剪仍是装载时的过滤层，两者正交。
2. **平台共享层保留为 `loadjson/`**（目录菜单、内置角色、全局配置、通用字典、跨 app 的默认授权），
   不迁移、不改名——二开文档里 `loaddata loadjson/seed_xxx.json` 的契约必须继续成立。
3. **契约种子与示例种子分离**：示例数据集/仪表盘/大屏/表单/示例部门从默认装载移出，
   归入各 app 的 `seeds/sample/`，只在 `--with-sample` 或 `seed_demo_all` 时装载。
4. **依赖由 manifest 自声明**，装载器做拓扑排序 + 引用完整性校验 + 冲突预检定位到具体文件；
   支持 `--apps` 单独装载某 app 及其依赖闭包。
5. **pk 一律冻结**，迁移不产生任何数据变更；新种子用 uuid5 派生。
6. **默认仍是单事务**（行为与现在一致），`--isolate` 提供逐 app 事务；「互不干涉」的收益落在
   文件归属、可单独装载与失败定位上，而不是靠拆事务换取。

## 二、现状实测

`loadjson/` 共 21 个文件、约 4,700 条种子对象，其中三个巨型文件占 93% 体积：

| 文件 | 体积 | 行数 | 内容 |
|---|---|---|---|
| `modellabelfield.json` | 814 KB | 2,094 | 字段权限树（ROLE 序列化器树 + DATA 模型/字段树） |
| `menumeta.json` | 449 KB | 740 | 菜单展示元数据 |
| `menu.json` | 436 KB | 714 | 菜单树 + 全部权限点 |
| `fieldpermission.json` | 300 KB | 253 | 角色 × 权限点的字段白名单 |
| 其余 17 个 | — | 约 760 | 配置 / 字典 / 角色 / 数据权限 / 流程 / 表单 / 示例数据 |

**关键观测：没有一行业务种子是"全局"的，全部天然有 app 归属**，只是被塞进了同一个文件。

字段树 2,094 行的归属分布（按根节点 `app.model` 统计）：

| app | 行数 | app | 行数 |
|---|---|---|---|
| identity | 416 | audit | 108 |
| approval | 361 | notifications | 103 |
| system | 322 | file | 58 |
| dataset | 238 | demo | 54 |
| task | 198 | django_celery_beat | 36 |
| ai | 171 | settings | 21 |
| | | 公共（`*`/公共字段） | 8 |

菜单 714 行的归属分布：**权限点 639**（system 126 / identity 118 / dataset 72 / task 69 /
approval 65 / settings 57 / ai 36 / notifications 34 / audit 26 / file 18 / chat 13 / 其他 5）
\+ **页面 61**（system 31 / integration 7 / settings 6 / approval 6 / analysis 4 / form-collection 3 /
user 2 / chat 1 / about 1）+ **目录 14**。

字段白名单 253 行：identity 66 / system 46 / settings 31 / notifications 31 / audit 19 /
dataset 18 / approval 15 / task 14 / file 11 / ai 2。

由此定位五个真实痛点（不是"文件不好看"）：

1. **归属不可见**：新增 app 要人肉在 814 KB 的文件里插行。历史后果有据可查——
   `sync_menu_permissions --dry-run` 曾一次性扫出 5 个"从未登记"的权限点。
2. **并发改动必冲突**：两个开发者改两个 app，diff 落在同一个文件的相邻行。
3. **一处冲突回滚全部**：`loaddata` 是单事务，一行自然键冲突会回滚全部种子；
   现有 `filter_conflicting_rows` 是打在这个语义上的补丁。
4. **二开无法分发**：二开 app / 插件只能往共享文件里塞行，`module remove` 还要**改写**共享文件
   （`menu.json` / `menumeta.json` / `fieldpermission.json` / `userrole.json` / `datapermission.json`）。
5. **示例与契约混装**：默认装载里含示例数据集、仪表盘、大屏、报表、表单提交、示例部门与示例流程，
   改示例数据会牵动首装契约面。

外加一条隐蔽问题：`load_init_json` 顶层 `import` 了 approval/audit/dataset/identity/settings 的模型，
**app 未注册即 import 失败**——种子加载与 `XADMIN_APPS` / `INSTALLED_APPS` 完全没有联动。

## 三、目标与边界

### 目标

- 每行种子有**唯一且可计算**的归属（某个 app 或平台层），工具能穷尽校验（0 孤儿、0 双归属）。
- 每个 app 独立目录、独立升级；文件级零共享。
- 能单独装载某个 app（自动带平台层与依赖闭包），失败信息定位到「文件 + 行 + 原因」。
- 二开 app 通过约定目录自带种子，不改内核任何文件。
- 存量库、pk、角色授权、前端契约**全部零变化**。

### 明确不成立的期待（边界）

- **"各装各的、互不感知"不成立**：种子之间存在真实引用（`menu → menumeta`、
  `fieldpermission → menu + 字段树`、示例数据 → 数据集、`flow → node`）。
  本方案给的是「**文件隔离 + 依赖编排**」，不是"任何一个 app 的种子可以随手删掉"。
- 不重新生成 pk、不改变权限点生成与授权语义、不改变 `loaddata` 的 upsert 语义。
- 不做运行期动态加载（种子仍由管理命令装载）。

## 四、目标结构

```
xadmin-server/
├── loadjson/                    # 平台共享层（保留原名、保留可直接 loaddata 的能力）
│   ├── menu.json                # 目录菜单 + 平台级页面 + 平台级权限点
│   ├── menumeta.json
│   ├── userrole.json            # 内置种子角色定义（menu 列表留空，授权走声明式增量）
│   ├── systemconfig.json        # 全局配置键（站点/安全/日志等）
│   ├── datadict.json            # 通用字典（yes_no / gender / boolean 等）
│   ├── datapermission.json      # 跨域数据权限策略
│   └── modellabelfield.json     # 仅 `*` 公共字段节点（其余迁到各 app）
├── identity/seeds/
│   ├── manifest.json
│   ├── menu.json                # 18 个页面 + 118 个权限点
│   ├── menumeta.json
│   ├── modelfields.json         # 416 行
│   ├── grants.json              # 角色 × 权限点的默认字段白名单（66 行）+ 角色菜单授权声明
│   ├── config.json              # 本 app 拥有的配置键（会话超时、登录策略默认值等）
│   └── dict.json               # 本 app 拥有的字典（login_type 等）
├── dataset/seeds/
│   ├── manifest.json
│   ├── menu.json / menumeta.json / modelfields.json / grants.json
│   └── sample/                  # 示例数据集 / 仪表盘 / 大屏 / 报表 / 表单 / 提交
└── <其余 app>/seeds/…           # 同上
```

**为什么叫 `seeds/` 而不是 `fixtures/`**：Django `loaddata <name>` 会在每个 app 的 `fixtures/` 目录里
按名搜索，多个 app 都有 `menu.json` 时会出现同名歧义；`seeds/` 不参与该搜索，路径由装载器显式给出。

**manifest 示例**（`dataset/seeds/manifest.json`）：

```json
{
  "version": 1,
  "app": "dataset",
  "depends": ["system", "identity"],
  "url_prefixes": ["api/dataset/"],
  "menu_roots": ["DataDashboard", "DataScreen", "DataReport", "FormDesigner", "FormData"],
  "files": [
    {"name": "menumeta.json",     "model": "system.menumeta",       "kind": "contract",  "order": 10},
    {"name": "menu.json",         "model": "system.menu",           "kind": "contract",  "order": 20},
    {"name": "modelfields.json",  "model": "system.modellabelfield","kind": "generated", "order": 30},
    {"name": "grants.json",       "model": "system.fieldpermission","kind": "contract",  "order": 40},
    {"name": "dict.json",         "model": "system.datadict",       "kind": "contract",  "order": 50}
  ],
  "sample": [
    {"name": "sample/datasets.json",  "model": "dataset.dataset",   "order": 10},
    {"name": "sample/dashboards.json","model": "dataset.dashboard", "order": 20}
  ]
}
```

`order` 复刻现有 `model_names` 的手工拓扑序（menumeta 先于 menu、字段树先于白名单），
把它从"全局清单"下沉为"app 内部清单"。

**双读兼容**：装载器同时识别两层——`loadjson/*.json`（平台）与各 `seeds/*.json`（应用）。
同一 pk 出现在两层时，默认按「应用层覆盖平台层」（`loaddata` 天然 upsert 语义），
但守护测试禁止同一 pk 双归属（见§十）。这样迁移期可以先"复制"再"删除"，全程可回滚。

## 五、归属规则（可生成、可校验）

归属不能靠人工标注（2,094 + 714 行），必须由规则计算 + 守护穷尽校验。

| 种子内容 | 归属规则 | 无法判定时 |
|---|---|---|
| 权限点（`menu_type=2`） | 取 `path` 前缀，最长匹配 app 的 `url_prefixes` 声明 | **报错**，不猜 |
| 页面菜单（`menu_type=1`） | 取其权限点子节点的归属众数；平票或无子节点时必须显式登记 `menu_roots` | 报错 |
| 目录菜单（`menu_type=0`） | 平台层（保守：避免拆坏父引用） | — |
| `menumeta` | 跟随引用它的菜单；被多个 app 的菜单引用 → 平台层 | 报错 |
| 字段树（ROLE / DATA） | 根节点 `name` 形如 `app.model` → 该 app；子节点跟随父节点 | 报错 |
| 公共字段节点 | `*`、`*.*` 与 `DbAuditModel` 公共字段 → 平台层 | — |
| `fieldpermission` | 按 `menu` 的归属 app | 报错 |
| `systemconfig` | 按 manifest 的 `config_keys` 登记 | 未登记 / 双登记 → 门禁失败 |
| `datadict` | 按 manifest 的 `dict_codes` 登记 | 同上 |
| 业务示例 | 各 app `seeds/sample/`，默认不装载 | — |

`url_prefixes` 由 app 自己声明（内置 app 的路由挂在 `server/urls.py`，二开走 `{app}/config.py`
的 `URLPATTERNS`）；装载器的 `--check` 会校验「全部权限点前缀都被某个 app 覆盖」，
内置 app 的前缀若漏声明即失败——这是把「权限点归属」从隐性知识变成显式事实的关键一步。

页面菜单的众数规则对现有数据成立：`SystemUser` 页的权限点是 `api/identity/user$` → identity；
`DatasetDashboard` 页的权限点是 `api/dataset/dashboards` → dataset。少数例外（如 `integration/`
目录下的多个页面分属不同 app）在迁移期一次性写进 `menu_roots` 固化。

## 六、装载编排

新增编排模块（建议 `system/services/seeding/`），职责四段：

```
discover()   发现：loadjson/（平台）+ 各 INSTALLED_APPS 的 seeds/manifest.json
plan()       规划：kind 过滤（contract/sample）→ 模块裁剪 → --apps 过滤 → 依赖拓扑排序
validate()   校验：归属唯一性 / 引用可解析 / 自然键冲突预检 / pk 不重复
load()       执行：平台层 → app 按拓扑序 → 收尾（内置角色、字段白名单、缓存失效）
```

要点：

- **发现按 `INSTALLED_APPS`**，天然与 `XADMIN_APPS` 联动，顺带解决「app 未注册即 import 崩」。
- **顺序不是 `os.listdir`**：先平台层固定内部序，再 app 拓扑排序（`depends` 成环即 fail-closed
  并打印环），再 app 内 `order`。
- **引用完整性在装载前校验**：把全部待装行建 `pk → (层, app, model)` 索引，
  逐个 FK / m2m / 内嵌 pk 列表检查可解析；缺失时输出
  「`dataset/seeds/menu.json` 第 N 行的 `parent` 指向 `identity` 的菜单，但 identity 未装载」，
  而不是让 `loaddata` 抛一条没有上下文的 `IntegrityError`。
- **模块裁剪仍是过滤层**：`ModuleSeedFilter` 在 `plan()` 阶段按行过滤，口径与运行期
  `compute_hidden_menu_pks` 保持一致（现在就是这么做的，不重复实现）。
- **失败语义**：默认单事务（与现在一致）；`--isolate` 时平台层一个事务、每个 app 一个事务，
  失败回滚该 app 并停止下游（已完成的上游保留，因为上游是幂等的契约基座）。
  `kind=sample` 的种子默认 `--continue-on-error`。

## 七、三类跨层引用与处理（这是方案的关键难点）

拆分后跨 app 引用会变多，分三类，处理方式不同：

**1. 普通外键**（`menu → menumeta`、`fieldpermission → menu/字段树`、`dashboard → dataset`）
按依赖顺序装载即可，pk 冻结所以引用不变。校验交给 `validate()`。

**2. 多对多**（`userrole.menu`、`menu` 的 m2m 等）——**必须改机制，不能简单拆行**。
`loaddata` 对 m2m 是**覆盖式赋值**：同一个角色行被两个 app 的文件各装一次，后者会把前者的授权清零。
现状 `userrole.json` 的 `menu` 就是一个横跨所有 app 的巨型 pk 列表（种子角色 4 个），
属"平台层反向引用 app 层"，单独装载任一 app 必然悬空。

处理方式：**授权改为声明式增量**。
- 平台层只保留角色定义（`menu: []`）；
- 各 app 的 `grants.json` 声明 `{role_code → [menu name...]}`（用 `name` 而不是 pk，可读、可合并）；
- 装载收尾统一做「本轮声明的并集」应用，天然幂等、可重复执行，且不会互相清零。
  内置角色本来就由 `identity/builtin.py` 按全部活跃菜单动态算，这套机制与它口径一致。

**3. 内嵌 pk 列表**（`datapermission.rules` 的 JSON 字符串里的菜单 pk）
无法用 ORM 关系解析。`datapermission` 是**跨域策略**，保留平台层归属；
`--check` 做弱校验：引用的菜单 pk 必须落在本轮计划装载集合内，缺失时告警（不阻断，
与现有 `ModuleSeedFilter` 从列表中移除被裁剪 pk 的行为一致）。

## 八、命令族改造

| 命令 | 现状 | 改造 |
|---|---|---|
| `load_init_json` | 无参数、全量、单事务 | 保留为唯一入口；新增 `--apps` / `--list` / `--check` / `--with-sample` / `--isolate` / `--strict` |
| `sync_model_field` | 全量重建字段树 | 新增 `--write-seeds`：按 app 回写各 `seeds/modelfields.json`（替代整份回写） |
| `sync_menu_permissions --update-seed` | 回写 5 个扁平文件 | 按归属回写到各 app 的 `seeds/`；平台级仍写 `loadjson/` |
| `dump_init_json` | 固定 10 个模型 | 新增 `--split-apps`：一次性迁移工具，按归属规则拆分并保留原 pk |
| `module remove` | 改写共享 JSON 文件 | 归档/删除目标 app 的 `seeds/` 条目，共享文件只在平台层部分变化 |
| `doctor` | 权限点缺口 / 依赖检查 | 新增种子段：归属唯一性、引用完整性、字段树与代码推导是否漂移 |

**单一路径入口**：现在 `loadjson` 字面量散落在 12+ 处（`seed.py`、`load_init_json`、
`sync_menu_permissions`、`module.py`、`dump_init_json`、`parity_permissions.py`、`e2e_seed_scenes.py`）。
先抽 `seed_paths(app_or_model, kind)` 一个模块，全部改为经它解析——否则拆分后必然出现漏改。

## 九、迁移路线（四阶段，每阶段可独立验收、可回滚）

> 本节是阶段性概览；**详细任务分解、按 app 的迁移顺序与每批验收命令见
> [应用级种子拆分执行计划-2026.10.md](应用级种子拆分执行计划-2026.10.md)**。

### 阶段一：只读盘点（不改任何行为）

- 实现归属规则模块 + `load_init_json --list` / `--check`；
- 守护测试断言：现有 2,094 + 714 + 253 行 **100% 可归属、0 双归属、0 孤儿**，引用完整性 0 缺失；
- 产出「归属映射表」入库，作为后续唯一依据。

这一步就能暴露历史包袱（例如若干 app 共用 `api/settings` 前缀、`api/flower` 代理端点、
`django_celery_beat` 模型是否该进 DATA 树），**先对账再动手**。

### 阶段二：生成 app 种子 + 双读

- `dump_init_json --split-apps` 生成各 `seeds/`（保留原 pk、原字段值、原缩进风格）；
- 装载器双读（平台层 + 应用层），同 pk 应用层覆盖；
- 新增**等价性门禁**：拆分层规划出的行集合与旧扁平层**逐行逐字段**一致（迁移期临时门禁，
  切换后改为快照比对）。
- 验收：空库与存量库各跑一次 `load_init_json`，`dump_init_json` 输出与改造前**字节级等价**
  （时间戳字段除外），且 `--check` 零错误。

### 阶段三：切换为单读 + 清理

- `loadjson/` 只留平台层，已迁移的行移出（归档到工作区 `_delete/` 保留可恢复）；
- `sync_model_field` / `sync_menu_permissions` / `module remove` 的回写目标切到 app 目录；
- 改造既有守护测试（清单见§十）；
- 更新二开文档中的路径说明（保留"扁平文件仍可 loaddata"的能力）。

### 阶段四：二开与插件分发

- `generate_crud` / `generate_module` 的产物直接写 `{app}/seeds/`（替代
  `loadjson/seed_<app>_<model>.json`，保留旧路径读取兼容）；
- 插件（`guide/plugin-development.md`）的种子纳入编排；
- 文档：《30 分钟第一个模块》的步骤 3/4 改为「生成器已写入 `{app}/seeds/`，`load_init_json --apps <app>`」。

## 十、测试与门禁

新增守护（每条都要能独立跑）：

| 测试 | 断言 |
|---|---|
| `test_seed_ownership.py` | 每行恰好归属一层/app；双归属 0、孤儿 0；`url_prefixes` 覆盖全部权限点 |
| `test_seed_manifest.py` | manifest 与目录文件双向一致；`model` 是已注册模型；`order` 唯一 |

## 十一、风险、边界与未决项

1. **与既有"不立项"结论冲突，需要显式重开**。
   2026-09-17 的结论是「`loadjson` 目录级拆分 ✖ 不立项」，理由是"会打断二开对 `loadjson/*.json`
   的路径引用"，触发条件是"种子需要按模块独立升级分发"。本方案给出的差异是：
   ①按 app 而非按模块；②双读兼容 + 保留扁平层，**不断二开路径**；
   ③多出的收益是归属可校验与失败可定位，不只是"文件组织方式"。
   触发条件中的"按模块独立分发"现在以"按 app 独立分发"的形式命中，建议在 ADR 里写清差异再重开。
2. **pk 必须冻结**。任何"顺便重新生成 pk"的冲动都会打断存量库、角色授权与前端缓存。
3. **`userrole.menu` 的覆盖式语义是硬障碍**，不先改成声明式增量，拆分就是"看起来拆了、
   实际装哪份由顺序决定"——必须在阶段二之前完成这项改造（可作为独立前置任务）。
4. **字段树的双源风险**。`modelfields.json` 是 `sync_model_field` 的生成物，
   长期终态其实是"首装直接跑同步、不存 JSON"。本方案先拆种子（确定性优先），
   同时把"种子与代码推导不一致"做成 `doctor` 告警；待稳定后再评估 `SEED_MODEL_FIELDS=auto`。
   这是本方案唯一可能自我否定的部分，需明确写成"可撤销决策"。
5. **`module remove` 与物理移除的边界**：未来"删一个 app"会同时涉及代码、迁移、`seeds/` 目录与
   共享层的授权声明，需要一次演练确认不会留下悬空 pk。
6. **示例种子移出默认装载会改变首装观感**（新库仪表盘为空）。属于有意的行为变更，
   需在发布说明里点明，并让 `init_data --with-demo` 保持"装了就有"的体验。

## 附：一句话回答"能不能每个应用单独种子"

能，而且现有数据天然支持（2,094 行字段树全部可按 `app.model` 前缀切分，714 行菜单全部可按
`api/<前缀>` 归属）。但"互不干涉"要落在正确的位置上：**文件归属互不共享、装载可单独执行、
失败可定位到文件**——而不是"各装各的"。真正的耦合只剩三处（角色多对多授权、数据权限内嵌 pk、
跨 app 的示例数据引用），前两处按§七处理，第三处本来就不进默认装载。
