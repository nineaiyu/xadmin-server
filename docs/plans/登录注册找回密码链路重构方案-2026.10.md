# 登录注册找回密码链路重构方案

> 状态：**已交付（2026-10-19）** · 编写日期 2026-10-19
>
> 交付结论：四阶段全部落地。新增 `identity/services/token_issue_login.py` 的 `issue_session_token`
> 为登录态签发唯一收口（原 7 处拷贝收敛，账密登录补显式 `last_login`、注册补
> `must_change_password`）；`reject_login` 收口策略拒绝三处重复写法并修 `login_type` 漏传；
> `verify_code.py` 改 `CATEGORIES` 表驱动；`utils/auth.py` 拆为 `auth/` 包（导入面不变）；
> 前端抽 `useAuthInfo`/`RememberLogin`/`PasswordFields`/`useVerifyCodeSubmit` 四个共享件。
> 收敛后的链路约定写入 [architecture/auth-flows.md](../architecture/auth-flows.md)。
>
> 范围：`identity/`（认证域）+ `xadmin-client/src/views/login/`（登录子页）
> 约束：**接口契约不变**（请求/响应字节级不变，`docs/schema/` 与 `contract/schema/` 不受影响，
> 现有 E2E 与集成测试的行为断言不失效）。本文只做实现收敛与缺陷修复，不改协议。

---

## 一、为什么要动它

这套链路的功能是完整的，安全底线也守住了（AES v2 传输、登录锁定、防枚举、分级限流、
MFA、会话级吊销都在）。问题不在"缺功能"，而在**同一件事在每个入口各写一遍，且已经开始漂移**：

- 签发 JWT 的 5 个步骤，在 7 个位置各写一遍，其中至少 3 处已经不一致；
- 登录成功后的处理逻辑，前端 4 个页面各写一遍；
- 三个验证码类表单页，骨架代码重复度约 70%；
- 若干真实缺陷（控制流错误、缺空值保护、重复清理）散落其中。

**判断：这是"技术债累积到影响正确性"的临界点，不是洁癖驱动的重构。** 每新增一种登录方式
（SAML、扫码、企微），都要在 7 个地方复制粘贴一遍，漏一处就是一条后门——这个风险已经被
`services/auth_login.py` 的 docstring 明确记录为历史教训。

## 三、后端问题详单

### B1（最高优先级）：签发 token 的 5 步逻辑有 7 份拷贝且已漂移

一条登录链路签发的完整步骤是：

1. `register_user_session()` 登记 `UserSession`（失败降级，不阻断登录）
2. `RefreshToken.for_user(user)` 签发
3. `bind_session_claim(refresh, session.pk)` 写 `sid` claim（失败降级）
4. `get_token_lifetime(user)` 附生命周期
5. 附 `must_change_password` + 更新 `last_login`

实际分布：

| 位置 | 会话登记 | sid 绑定 | lifetime | must_change_password | last_login |
|---|---|---|---|---|---|
| `login.py:73-86`（serializer 内） | ✅ 降级 | ✅ 降级 | 视图层 | ✅ | ❌ |
| `login.py:253-268`（验证码登录） | ✅ 降级 | ✅ 降级 | ✅ | ✅ | ✅ |
| `register.py:117-127` | ✅ 降级 | ✅ 降级 | ✅ | ❌ | ✅ |
| `mfa.py:163-175` | ✅ 降级 | ✅ 降级 | ✅ | ✅ | ✅ |
| `oauth.py:370-382` | ✅ 降级 | ✅ 降级 | 调用方 | 调用方 | 调用方 |
| `impersonation.py:61-72` | ✅ 降级 | ✅ 降级 | ✅ | ❌ | ❌ |
| `impersonation.py:123-125`（退出模拟） | ❌ | ❌ | ✅ | ❌ | ❌ |

漂移后果：

- **账密登录不写 `last_login`**：依赖 simplejwt 的 `UPDATE_LAST_LOGIN=True`
  （`server/settings/libs.py:115`）在 serializer 内补写。这条隐式依赖没有注释说明，
  一旦将来 serializer 换成非 `TokenObtainPairSerializer` 或关掉该开关，账密登录的
  `last_login` 会静默失效，而 `online` 列表与登录日志的时间判断依赖它。
- **注册不返回 `must_change_password`**：管理员预建的邀请账号注册/激活后不会触发改密引导。
- **降级分支的 try/except 嵌套写法在 7 处各不相同**，审计时无法用统一口径判断
  "哪些路径真的降级了"。

更结构性的问题是 `SessionTokenObtainPairSerializer.validate()`（`login.py:73-86`）：
**serializer 里做了建会话、改 token 编码两件事副作用**。`serializer.is_valid()` 的语义
应该是"校验并返回数据"，调用方读代码时不会预期它创建了数据库行。

### B2：`VerifyCodeLoginAPIView` 是挂着羊头的视图

`login.py:189-270` 继承 `TokenObtainPairView` 但：

- 没有 `serializer_class`，走父类默认的 `TokenObtainPairSerializer`；
- `post()` 完全没用 serializer，直接 `authenticate()` + 手签 `RefreshToken.for_user`；
- 因此**继承了不该有的 `get()`**——对 `/api/identity/login/code` 发 GET 会命中
  父类的配置接口行为，属于意外的额外暴露面。

它应该是一个 `GenericAPIView`。

### B3：`login_failed` 调用点缺终止语义（控制流错误）

`login_failed()`（`services/auth_login.py:66`）内部是 `raise ValidateError(detail)`，
但两个调用点写法不一致：

```python
# login.py:140 —— 正确（return 终止）
return login_failed(request, username)

# login.py:231-232 —— 缺 return，依赖异常栈展开跳过后续代码
if not user:
    login_failed(request, target)
# ↓ 这行在异常路径下不会执行，但静态读代码无法确认
force_mfa, reject_detail = evaluate_login_policy_for_request(request, user, ipaddr)
```

当前**能工作**，因为 `ValidateError` 抛出时栈展开跳过了后续语句。但这是脆的：
任何人给 `login_failed` 加一个"记录后返回 None"的分支，或者在 `if not user`
块里补一行日志，就会立刻变成 `evaluate_login_policy_for_request(request, None, ...)`
的 `AttributeError`。

同类问题：`login.py:147-148` 与 `login.py:235-238`、`login.py:248-251` 的
"策略拒绝"分支在三处各写一遍（`request.user = user` + `save_login_log(status=False)`
+ 返回文案），其中两处漏了 `login_type` 参数。

### B4：登出重复清理 + 潜在未认证访问

`logout.py:36-37` 和 `logout.py:67` 都调了 `UserConfirmStateCache(request.user).clear()`。
第一处有 `is_authenticated` 保护，第二处（`logout.py:67`）没有——如果走到 `logout(request)`
之后 `request.user` 变成 `AnonymousUser`，`.clear()` 会拿到一个匿名用户的缓存键
（无害但是废操作，且语义上错误）。第二处是复制粘贴残留。

### B5：`verify_code.py` 的 category 调度靠字符串拼装

5 个场景的配置与校验是散装方法：

```
get_register_config / check_register_config
get_login_config    / check_login_config   → 内部转发到 check_reset_config
get_reset_config    / check_reset_config
get_bind_email_config / check_bind_email_config
get_bind_phone_config / check_bind_phone_config
```

靠 `getattr(self, f"get_{category}_config")`（`verify_code.py:132`）和
`getattr(self, f"check_{category}_config")`（`verify_code.py:187`）字符串拼装调度。

问题：

- **新增场景要改 4 个地方**（`CATEGORY_KEYS`、`get_*_config`、`check_*_config`、
  两处 `getattr`），漏一个就是运行时 `AttributeError` 500。
- **"登录与重置行为相同"这个重要语义藏在转发方法里**（`verify_code.py:296-297`）。
  读者必须跳进 `check_reset_config` 才知道登录场景不区分账号存在性。
  这个语义恰好是安全相关的（防用户枚举），值得显式表达。
- 测试已经直接 monkeypatch `SendVerifyCodeAPIView.check_register_config`
  （`tests/integration/system/test_verify_code_api.py:512`），改成表驱动时要保持
  这个 patch 点可用，否则测试要跟着改。

### B6：`identity/utils/auth.py` 一个文件混四类职责

181 行里同时有：

1. 异常类（`ValidateError`，`auth.py:26-29`）
2. 图形验证码 / 临时令牌校验（`check_captcha` / `check_tmp_token` / `check_token_and_captcha`）
3. 凭据解密与锁定检查（`get_username_password` / `check_is_block`）
4. **登录日志写入**（`save_login_log`，`auth.py:93-115`）与**短信验证码核验**
   （`verify_sms_email_code`，`auth.py:118-161`）与**异地登录提醒**
   （`check_different_city_login_if_need`，`auth.py:164-181`）

`save_login_log` 里还有惰性 import（`auth.py:111` 的 `LoginLogSerializer`）。
导入 `check_captcha` 时会顺带建立对 `audit` / `captcha` / `identity.models` /
`settings.services` 的依赖，环依赖风险靠惰性 import 压住。

### B7：`{cls}` 模板占位符残留进 docstring

- `token.py:39` `"""获取{cls}"""`
- `token.py:61` `"""获取{cls}"""`
- `views/user/userinfo.py:59` `"""获取{cls}信息"""`

这些首行会被 `get_doc_first_line` 取作 `MenuMeta.title`。`{cls}` 是按原样计入长度的
（`scripts/check_menu_titles.py:16`），且这三个方法都不在 CRUD/`@action` 名单里所以
门禁没拦，但占位符本身不该出现在 docstring 里。

### B8（次要）：`register.py` 的锁粒度和幂等

`register.py:88` 的 `ReentrantLock("register_user", timeout=10)` 是全局锁（所有注册请求
串行）。功能正确（防并发重复注册撞唯一约束），但高并发注册场景下是吞吐瓶颈。
本方案不动它——它是安全相关的正确取舍，只在此登记，不作为重构项。

同一个后端接口（`GET /api/identity/login/basic` 或 `/api/identity/auth/verify`）
的响应，前端有 4 种本地形状：

- `Basic.vue:51-59`：`reactive<AuthInfoResult["data"]>`，7 字段全量
- `Login.vue:54-59`：`ref({access, encrypted, lifetime, reset})`，4 字段
- `Register.vue:25-29`：`ref({access, encrypted, password})`，3 字段
- `ResetPassword.vue:28-32`：`ref({access, encrypted, password})`，3 字段

`AuthInfoResult["data"]` 类型已经定义了，却没被三页使用。字段缺失时
`authInfo.password` 是 `undefined`，`passwordRulesCheck` 对 `undefined` 的行为

### F6：`rule.ts` 的死代码

```ts

export const REGEXP_PWD = /^(?![0-9]+$).../ // rule.ts:10 零引用
```

全项目搜索无引用。登录密码的实际校验只查空（`rule.ts:24-32`），强度规则

## 五、重构方案

原则：**契约不动、行为不动、只收敛实现**。分四个阶段，每阶段独立可验证、可回滚。

### 阶段一：后端收敛签发路径（收益最大）

#### 1.1 新增唯一签发函数

在 `identity/services/` 下新增 `token_issue_login.py`（与既有 `token_issue.py` 并列，
后者管 PAT 三类凭证，本文件管登录态凭证）：

```python
def issue_session_token(request, user, login_type, *, extra_claims=None, touch_last_login=True):
    """登录态 token 签发的唯一实现：会话登记 → 签发 → sid claim → 生命周期 → 改密标记。

    任何签发"给人登录用"的 JWT 的路径都必须调本函数，不得自行拼接
    RefreshToken.for_user / bind_session_claim / get_token_lifetime。

    降级口径统一：会话登记失败、claim 注入失败均退回无 sid 令牌并告警，
    绝不阻断登录（会话管理属附加能力）。

    :param extra_claims: 额外 claim（如用户模拟的 impersonator claim）
    :param touch_last_login: 是否刷新 last_login（注册/模拟等已有明确写入时传 False）
    :return: dict，键为 refresh/access/access_token_lifetime/refresh_token_lifetime/
             must_change_password
    """
```

实现内部按 B1 表格的**最全口径**（含 `must_change_password` 与 `last_login`）统一，
然后逐点收敛：

| 调用点 | 改动 |
|---|---|
| `login.py:73-86` serializer | **删除副作用**。serializer 回归纯校验；签发移到 `post()` 内 `complete_login` 之后 |
| `login.py:253-268` | 替换为 `issue_session_token(...)` |
| `register.py:117-127` | 替换；`touch_last_login` 由函数统一处理，删掉手工 `update_fields` 拼接 |
| `mfa.py:163-175` | 替换 |
| `oauth.py:370-382` + `:293-299` | `_issue_token` 改为薄包装调 `issue_session_token`；删掉调用方手工拼的 `get_token_lifetime` 与 `must_change_password` |
| `impersonation.py:61-72` | 替换，`extra_claims={"impersonator": ...}` |

## 六、风险与回滚

| 风险 | 影响 | 缓解 |
|---|---|---|
| `issue_session_token` 收敛时漏掉某路径的 `extra_claims` | 用户模拟的 `impersonator` claim 丢失 → 顶栏横幅不显示 | 阶段一测试包含 `test_impersonation.py`；逐路径对照 B1 表格 review |
| `last_login` 改显式写入后与 `UPDATE_LAST_LOGIN` 双写 | 多一次 UPDATE（无害） | 保留 `UPDATE_LAST_LOGIN=True` 作兜底并注释说明；两者写同值 |
| `verify_code.py` 表驱动破坏测试 monkeypatch | 3-5 行测试改动 | 提前确认 patch 点从类方法改为模块级函数，测试同步 |
| `utils/auth.py` 拆包时导入面变化 | 大面积 import 报错 | `__init__.py` 显式再导出全部原符号，`grep` 对账导入清单 |
| 前端 `handleOperation` 统一后 Basic 的验证码刷新行为变化 | 登录失败后图形码不刷新，用户卡住 | `failed`/`exception` 回调显式接住 `initToken(true)` + `getImgCode()` |
| `menumeta.json` title 变更 | 菜单显示名变化 | 跑 `sync_menu_permissions --dry-run` 确认缺口 0，并 `load_init_json` 复灌 |
| E2E 复用旧进程导致假失败 | 误判为回归 | 改了后端必须 `*:fresh` 变体（AGENTS.md E2E 铁律） |

**回滚**：四个阶段互不依赖，每阶段单独提交。任一回退只需 `git revert` 对应提交，
不存在跨阶段的数据库迁移或契约变更。
