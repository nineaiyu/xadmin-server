**结论摘要**：

- **代码缺陷面已收敛**：两轮全量审查（390 条宇宙）全部处置完毕，R6/R7 连续两轮重扫新发现率

## 二、外部优化案例与可借鉴点（本计划的直接依据）

> 以下案例均为公开可访问的实践记录，用于给方向提供**方法论与量化锚点**，不作为照抄模板。
> 每条给出「来源 / 可借鉴做法 / 对本项目的映射」。

**案例一：API P95 7s → 0.1s（后端性能优化全流程，2026-03）**
来源：<https://jeongil.dev/en/blog/backend/performance/backend-api-performance-optimization/>

- 关键做法：**先度量后动手**（看 P95 不看均值）→ Prometheus/Grafana 按 P95 排序 + 分布式追踪定位 →
  EXPLAIN 看执行计划 → 把瓶颈归三类（查询低效 / 串行处理 / 重复查询）→ 按类治理（**sargable 查询改写 →
  并行化 → Cache-Aside 缓存**）→ 上缓存命中率面板与 **P95 告警**；
- 细节可借鉴：TTL **随机抖动**防缓存雪崩、Redis 故障**降级回源**（超时 100ms）、
  `supervisorScope` 式隔离（渠道互不拖累）、缓存 hit/miss 计数驱动 TTL 调优；
- 量化：排行接口 P95 1.9–2.4s → 95ms；缓存接口 P95 4.0s → 50ms；批次作业查询次数 4001 → 2；
- 反思原话：**「有索引 ≠ 用得上索引」；「难在定位，不难在修复」**；
- **映射**：本项目 ① 未达标项（`04-metadata-fields` 117.62ms / `03-list` 192.2ms）正是「有基线无闭环」——
  缺的是**按 P95 的告警与缓存命中率可视**，而非算法；② 缓存 TTL 抖动 / 降级回源口径值得逐处核对。

**案例二：Vue3 后台系统首屏 9.8s → 1s（2026-09）**
来源：<https://blog.csdn.net/weixin_31881651/article/details/164656534>

- 关键做法：产物可视化定位大户（`rollup-plugin-visualizer`）→ UI 库**按需加载**（含
  `ElMessage` 等调用式组件需手工 import 的坑）→ 重型库（ECharts 核心按需、富文本、3D/词云）
  **动态 import 拆 chunk**（入口链路静态 import 照样预加载，必须改动态）→ `manualChunks` 克制的
  三方分组（**分包过细会反噬**）→ 路由懒加载 + 页面内 `defineAsyncComponent` 两级
  → **无依赖请求 `Promise.all` 并行 + 请求去重（`Map<string, Promise>`）**
  → 组件拆分限制渲染范围、`shallowRef` / `markRaw` / `v-memo`、稳定 key
  → nginx `immutable` 长缓存 + `preconnect` + `modulepreload`；
- 量化：主包 gzip 800 KB → 180 KB；首屏可交互 9.8s → 1s；
- **映射**：本项目 element-plus 单块 239.3 KB 与闭包 567.5 KB 说明**体积仍有明确空间**；
  但项目已有门禁与体积预算，缺的是「**首屏画像**」——没有 LCP/TTI/请求瀑布的基线，优化就无靶心。

**案例三：RAG 混合检索 + 重排（2026-09）**
来源：<https://blog.csdn.net/weixin_29051245/article/details/166920334>

- 关键做法与量化：纯向量 Top-5 命中 62% → BM25 混合 **81%** → 加重排 **89%**；
  分块策略与「为什么这么做」的取舍说明；
- **映射**：本项目 hit@5 **97.2%**（词频与真实向量 RRF 同分）已超越该案例的终点，
  **说明当前知识库规模下召回不是瓶颈**；若未来语料量级跃升或出现长尾问句，重排才是候选，
  在此之前投入重排属**过度工程**——本计划因此把 AI 方向重心放在「答案质量与成本可视」。

**案例四：Playwright Flaky Tests 治理（2026-09）**
来源：<https://blog.csdn.net/gitblog_00029/article/details/137537767>

- 关键做法：**先分类再修**（时序 / 数据 / 环境 / 外部依赖四类）→ 确定性等待（禁用 sleep）+
  数据隔离（每用例独立数据）+ 外部 API 桩化 → **隔离区（quarantine）机制**兜住短期无法根治的用例
  → 预防策略（评审清单、CI 抖动看板）；
- **映射**：本项目已有「登记 + 人工隔离复跑」与桩 LLM，**缺的是 quarantine 自动化**：
  当前 flaky 判定与重跑完全依赖人，规模化后（101 spec × 双浏览器）会成为时间黑洞。

**案例五：SBOM + SLSA 供应链实践（2026-06 / 2026-09）**
来源：<https://cloud.tencent.com/developer/article/2692534>、<https://blog.csdn.net/gitblog_00190/article/details/152146323>

- 关键做法：SBOM 揭示「装了什么」（CycloneDX / syft），SLSA 验证「谁构建的」（构建溯源 + 制品签名），
  Python 侧还可用 PEP 740 解决发布者身份；三者组合把「构建可溯源 + 内容可验证 + 发布可信任」闭环；
- **映射**：本项目有 `pip-audit` / `pnpm audit`（成分**检测**）与 Renovate（依赖**更新**），
  但**发布制品无成分清单、无溯源证明**——对「分发给二开用户的内核包与镜像」这是实际缺口。

**案例六：OWASP ASVS 落地（2026-06 / 2026-08）**
来源：<https://blog.csdn.net/weixin_32428571/article/details/162085818>

- 关键做法：把「安全检查清单」结构化成分级验证项（L1 基础 / L2 标准 / L3 高级），
  逐条给出「是否满足 + 证据 + 差距」；自动化可行的条目下沉为 CI 检查，其余进入定期评审；
- **映射**：本项目安全治理走的是「自建接受项台账 + 重开条件」（`security-review.md`），
  **工程质量不低但不可对外表述**；映射到 ASVS 的主要收益是**可审计性**（可回答客户安全问卷），
  而非发现新漏洞。

**案例七：PostgreSQL 大表分区与归档（多篇，2026）**
来源：<https://active.blog.csdn.net/article/details/163939324>（分区最佳实践）、
<https://blog.csdn.net/weixin_52208686/article/details/161675619>（范围分区实战）

- 关键做法：范围分区（按月/年）+ **分区裁剪**让查询只扫热分区；冷分区 `DETACH` → 归档 → `DROP`，
  把「删数据」变成元数据操作（避免大 DELETE 的膨胀与锁）；注意 PG **不自动建分区**，需定时任务或触发器；
- **映射**：本项目已有 JSONL 归档 + 水位驱动清理（工程上更保守、更安全），**无分区**；
  分区收益出现在单表数据量跨过某个量级之后，因此本计划把它写成**带量化阈值的触发项**，
  而不是现在就做（提前做会引入迁移与默认管理器兼容成本）。

**案例八：技术债治理的分阶段与量化（2026-07 / 2026-09）**
来源：<https://codewave.163.com/info/enterprise-technical-debt-governance-legacy-system-refactoring.html>

- 关键做法：债务**盘点 → 分级（阻塞型 / 效率型 / 美观型）→ 分批清偿 + 每批带量化口径**；
  强调「债务治理不是一次性运动，而是把清理动作嵌进日常改动路径」；
- **映射**：本项目的「滚动债只减不增 + 门禁兜底」已是该模式的成熟形态，
  **可直接复用其分级口径**（本项目现存债以「效率型 / 美观型」为主，无阻塞型）。

## 三、主要优化方向清单

> 每项：**现状证据 → 借鉴依据 → 目标与手段 → 预期成果 → 验收口径**。
> 优先级：P0 = 已有量化指标未达标或存在结构性风险；P1 = 能力缺失且影响长期可维护性；
> P2 = 体验/可审计性提升；触发制 = 条件未到不立项。

### 优先级 P0

#### 方向一：API 尾延迟闭环治理（未达标项收口）

- **现状证据**：`04-metadata-fields` P95 117.62ms（目标 <60ms）；`03-list` P95 192.2ms（退化登记）；
  `04-metadata-with-meta` 218.07ms；8-worker 容量档分别为 25.74 / 105.12 / 192.51ms。
- **借鉴依据**：案例一（P95 优先、EXPLAIN、三类瓶颈归类、缓存命中率面板、P95 告警）。
- **目标与手段**：
  1. **先建闭环再优化**：为 8 个基线用例补 P95 阈值告警（Prometheus 规则）+ 端点级缓存命中率指标
     （命中/未命中计数 + 命中率面板），使「退化」不再只靠人工跑 `check_baseline.py` 才发现；
  2. 用 EXPLAIN + 追踪把 `metadata-fields` 的 117.62ms 拆到**同步段 / ORM / 序列化**，
     判定是容量膝点（worker 档位）还是可优化路径（缓存 / 预计算 / 列裁剪）；
  3. `03-list` 按案例一的「查询低效 / 串行 / 重复」三类分别取证，只改有证据的一类；
  4. 复核缓存 TTL 是否存在**同批过期**风险（抖动）、缓存故障是否**降级回源**。
- **预期成果**：`04-metadata-fields` 单 worker P95 < 60ms 或给出「容量膝点」的正式结论并下调目标；
  基线退化有自动告警；缓存命中率可观测。
- **验收口径**：`loadtest/baseline.json` 更新 + `check_baseline.py` 全绿 + 告警规则入库 +
  `docs/metrics.md` 回填定位结论。

#### 方向二：前端首屏画像与体积治理

- **现状证据**：闭包 567.5 KB gzip / code 496.3 KB / element-plus 239.3 KB / 主 chunk 142.8 KB；
  有体积门禁但**无首屏时间基线**（LCP / TTI / 请求瀑布）。
- **借鉴依据**：案例二（产物可视化定点、重型库动态化、请求并行与去重、两级懒加载、渲染范围收敛、缓存头）。
- **目标与手段**：
  1. **第一步做画像不优化**：用 `pnpm analyze:bundle` + Lighthouse（桌面与移动视口）产出
     「首屏资源瀑布 + 体积构成 + Long Task」三张表，形成 `perf-baseline.json` 的首屏维度基线；
  2. 按画像定点处理（预期集中在：element-plus 按需覆盖度、ECharts / 富文本 / Office 预览的异步化、
     首屏接口串行）；
  3. 复核静态资源缓存头（`immutable` 长缓存 + `index.html` no-cache）与 `preconnect` 是否已最优；
  4. 把「无依赖请求并行 + 请求去重」做成可复用组合式函数，避免逐页手写。
- **预期成果**：闭包 gzip **-15%**（567.5 → ≤482 KB）；主 chunk **-10%**；首屏 LCP 建立基线并改善；
  预算门禁从「单 chunk」扩到「首屏链路面」。
- **验收口径**：体积基线刷新 + 首屏基线写入 `e2e/perf-baseline.json` + perf/visual E2E 双浏览器全绿。

#### 方向三：跨仓一致性治理（工作区级校验）

- **现状证据**：根目录**无 CI、无校验脚本**；同源断言（CSP 三处、模块裁剪前端扫描、契约镜像、
  locale 对称）各自靠**单仓守卫 + 缺失即 skip**；工作区侧只靠人工同步（历史已两次踩「CI 从未跑到」）。
- **借鉴依据**：案例八（把清理与校验嵌进日常路径）+ 项目自身纪律红线第 10 条。
- **目标与手段**：
  1. 新增工作区级只读校验脚本（**不引入新 CI 平台**）：一次跑完四仓关键门禁 + 跨仓同源断言
     （CSP 三处文本同源、`menu.json` ↔ 前端 locale ↔ contract 的键集比对、版本矩阵），
     输出统一「工作区健康报告」；
  2. 把「跨仓断言在单仓检出时 skip」升级为「在本工作区必须真跑」，避免长期静默失效；
  3. 可选：以 GitHub Actions 定时（跨仓 checkout）在 server 仓跑一次跨仓校验，产出 issue 而非阻断。
- **预期成果**：跨仓漂移在提交前可发现；同源断言不再有「静默 skip 假绿」。
- **验收口径**：脚本可一键运行 + 至少覆盖 CSP / 权限种子 / locale / contract / 版本五类同源面 +
  在真实工作区跑通零告警。

### 优先级 P1

#### 方向四：测试稳定性治理机制化（quarantine + 抖动度量）

- **现状证据**：101 个 E2E spec × 双浏览器；flaky 靠登记与人工隔离复跑；已有桩 LLM 与
  `test:e2e:parallel`、`E2E_REUSE_SERVER` 等工具。
- **借鉴依据**：案例四（四类分类 → 确定性等待 / 数据隔离 / 桩化 → quarantine → 预防）。
- **目标与手段**：① CI 记录每个用例的通过/重试/失败历史，产出**抖动榜单**（按用例 × 浏览器）；
  ② 落地 quarantine 清单（自动标记 + 单独流水线跑，不阻断主线，但超过期限必须根治或删除）；
  ③ 把「已登记 flaky 家族」（webkit 负载瞬态、非确定性单例）的根因分类写入 `e2e/README.md` 教训表；
  ④ 复核是否存在 `sleep` 式等待残留。
- **预期成果**：flaky 可量化（榜单）可隔离（自动），主线 E2E 一次通过率 ≥ 99%。
- **验收口径**：抖动榜单产出 + quarantine 机制可用 + 主线 E2E 连续 2 周无「需人工判定」的失败。

#### 方向五：供应链成熟度升级（SBOM + 构建溯源）

- **现状证据**：有 `pip-audit` / `pnpm audit` / Renovate / 镜像 security-scan；无 SBOM、无 provenance、无签名。
- **借鉴依据**：案例五（SBOM 内容可验证 + SLSA 构建可溯源 + PEP 740 发布者身份）。
- **目标与手段**：① 发布流水线生成 SBOM（CycloneDX，Python 与前端两路）；
  ② 镜像与内核包附构建溯源证明（GitHub Actions 原生 attestation 即可满足 SLSA L1–L2）；
  ③ SBOM 随 Release 附件分发，并在 `docs/ops/kernel-release.md` 补「消费者如何验证」章节。
- **预期成果**：每次发布可回答「装了什么 + 谁构建的」；二开用户可自行验证内核包来源。
- **验收口径**：一次真实 release 产出 SBOM + 溯源证明 + 验证文档可复现。
- **边界**：**只在 release 流水线做**，不进 PR 门禁（避免拖慢每次提交）。

#### 方向六：可观测性深化评估（跨层追踪）

- **现状证据**：Prometheus 指标 + SLO 快照 + 告警桥 + Sentry；缺 HTTP → ORM → Celery → WS 的追踪关联。
- **借鉴依据**：案例一（Tempo 追踪定位「慢在 DB / 代码 / 外部调用」是效率关键）+ 案例五（TraceID 串联三支柱）。
- **目标与手段**：**先评估后落地**——出一份「引入 OpenTelemetry 的成本/收益/边界」评估：
  采哪儿（ASGI / ORM / Redis / Celery / WS）、采样率与开销、数据落地（本机 Tempo vs 仅导出 OTLP）、
  trace_id 注入日志的改动面；评估结论为「做 / 不做 / 什么条件下做」。
- **预期成果**：结论 + （若做）最小埋点集与开关（默认关，故障排查时开）。
- **验收口径**：评估文档入 `docs/ops/observability.md`；结论项进触发制台账。
- **边界**：单人维护 + 自建栈，**默认不做全量常开追踪**，避免运维成本反噬。

### 优先级 P2

#### 方向七：知识资产治理（大文档拆分 + ADR 生命周期）

- **验收口径**：拆分执行 + 门禁扩展 + 链接与索引门禁全绿。

#### 方向八：安全验证体系化（ASVS 轻量映射）

- **目标与手段**：把现有安全现状映射为 ASVS L1/L2 对照表（满足 / 部分 / 不适用 / 差距），

- **预期成果**：可用一页回答客户安全问卷；差距清单可驱动后续小步改进。
- **验收口径**：对照表入 `docs/security-review.md` 附录；差距项各有归属（整改 / 接受 / 触发条件）。

#### 方向九：AI 能力纵深（答案质量与成本可视）

- **现状证据**：hit@5 97.2%（词频 / 混合 RRF 同分，唯一 miss 同题）；评测集 36 问；

### 触发制新增项（带量化阈值）

#### 方向十三：大表分区（PostgreSQL 原生分区）

## 八、执行与维护约定

1. **本文件的角色**：长期方向的**唯一汇总视图**；窗口主项排期后仍以 `DEV-TASKS.md` 为执行入口，
   仓库内以 `docs/plans/` 两份台账为权威源——三处不一致时**先修正不一致再动手**。
2. **窗口纪律**：每月收口回写本文件 §四 与 KPI 表；未启动的主项注明原因。
3. **立项纪律**：结构 / 接口变更先 ADR；新功能 100% 带测试；改动后端后跑 `pnpm test:e2e:fresh`；
   只有用户明确说提交才 commit；改动完成后保留工作区待人工检查。
4. **对标纪律**：借鉴外部案例时**只取方法论与量化锚点**，落地前先在本项目复核前提条件
   （如案例二的「CDN external」在私有化部署场景明确不适用）。
5. **取舍纪律**：本项目在若干维度（RAG 命中率、门禁密度、迁移收敛）**已领先外部公开案例**，
   对标时应识别并**放弃过度工程**（重排、全量追踪、预防性分区、预防性 GIN 索引同属此类）。
