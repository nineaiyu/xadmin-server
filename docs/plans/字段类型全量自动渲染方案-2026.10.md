# 字段类型全量自动渲染方案（字段族 × 四通道补全）

> **目标**：做到「后端定义字段 → 前端四通道（搜索 / 表单 / 详情 / 列表）自动渲染」，二开者不写一行前端代码。
> 本文档是**字段类型全集盘点**——从 Django 模型字段出发的全量映射表（§3.0 表 Z：模型里写 `models.DecimalField` / `models.TextField`… 前端得到什么）+ 词表 `input_type` 逐项矩阵（§3.1）+ DRF 可达长尾（§3.2）+ 候选新增（§3.3）——以及**缺口与缺陷清单**（§四）+ **分批实施方案**（§五）。
> 状态：**已实施（2026-10-20）**。四批次代码、契约与文档已落地；公告正文的 `rich_text` 试点暂缓——
> `message` 字段受 `message_format`（html / markdown）双格式约束，静态 `input_type` 无法按实例切换，
> 待格式维度收敛后再迁移。`RichTextField` 与前端富文本四通道已就绪，并以 **demo.Book 的
> `contact_phone` / `theme_color` / `introduction`** 作为 phone / color / rich_text 的活样本。
> 机制背景见 [metadata-protocol.md](../architecture/metadata-protocol.md) §三，扩展流程见
> [framework-cookbook.md](../architecture/framework-cookbook.md) §六「新增 input_type 检查清单」，
> 完整字段矩阵见 [field-types.md](../architecture/field-types.md)。

## 一、目标与非目标

**目标**：

1. 平台可声明的每一类字段（序列化器字段 / 字段类 / `input_type` 覆写）在前端四通道都有**明确归宿**：要么有内置渲染器、要么走受控回退、要么显式不支持并报错——不允许「后端定义了、前端静默 `[object Object]` 或空白」；
2. 缺陷修复：`phone` 的默认值篡改 / 缺校验 / 缺详情列表通道，`color` 缺服务端校验（§四.1）；
3. 治理补强：`input_type` 词表闭包测试从 3 个视图集扩到**全量视图集**，把「悄悄下发未登记类型」从线上现形提前到 CI 拦截（§四.3）；
4. 新类型按价值补齐：`rich_text`（富文本）、`password`（密码遮蔽）、`url` / `decimal`（在逃长尾正式登记）（§三 / §五 批次三）;
5. 文档交付：新增「字段类型矩阵」页——**从 Django 模型字段出发的全量映射表**（模型里写什么 → 前端得到什么）× 词表逐项矩阵，二开选型不再需要读源码。

**非目标**：

- 不改四通道注册表架构（`fieldTypeRegistry.ts` 单一能力清单 + `renderers-*.tsx` 实现体 + `registry.ts` 投影的分层保持不变）；
- 不做动态表单（dform `ALLOWED_TYPES` 是独立体系，`dataset/utils/dform_constants.py`，与本方案正交）;
- 不预做无真实消费的长尾类型（`rating` / `slider` / `cron` 等进候选池，按需插槽制，见 §三.3 表 C 尾注）。

## 二、机制现状（「自动渲染」是怎么成立的）

### 2.1 链路与事实源

```
后端声明                          元数据下发                      前端分派
─────────────────────────       ─────────────────────          ────────────────────────────
字段类自带 input_type      ─┐
（PhoneField/ColorField…）   │
input_wrapper(input_type=…) ─┼→ get_field_type（isinstance）→ search-columns JSON
label_lookup 回退（DRF）    ─┤   + get_format_intput_type        │
style.base_template=textarea─┘   （prefix/suffix 修饰）           ▼
                                                        fieldTypeRegistry.ts 能力清单
                                                        （search/form/detail 三面渲染
                                                         + rule 校验 + filterKind 筛选形态）
```

| 事实源 | 位置 | 说明 |
|---|---|---|
| `input_type` 词表 | `packages/xadmin-common/common/core/modelset/input_types.py::DECLARED_INPUT_TYPES` | 封闭核心 35 项 + `api-*` 开放前缀族；**平台能下发什么以此为准** |
| 类型判定 | `common/drf/metadata.py::get_field_type` | isinstance 分支（labeled 系 / related 系 / json）+ DRF `label_lookup` 回退 |
| input_type 组装 | `common/core/modelset/metadata_columns.py` | `textarea` 覆写、关联候选截断、`step` 扩展属性透出 |
| 前端能力清单 | `xadmin-client/src/components/RePlusPage/src/utils/fieldTypeRegistry.ts` | 每个 input_type 的渲染三面 + 校验规则 + 筛选形态，一处声明 |
| 契约 Schema | `docs/schema/search-columns.schema.json`（前端镜像 `contract/schema/`） | `input_type` 枚举与词表锁步 |
| 自定义字段类 | `common/core/fields.py`（Phone/Color/StepFloat/Labeled 系列）、`fields_dict.py`（DictChoice）、`fields_related.py`（关联族） | 业务侧 `from common.core.fields import ...` 直接声明 |

### 2.2 守护体系与覆盖面缺口

现有三层守护（本方案的护栏，全部保持并加强）：

| 守护 | 位置 | 保证什么 |
|---|---|---|
| 载荷闭包 + Schema 锁步 | server `tests/unit/common/test_metadata_schema.py` | 真实响应里的 input_type ⊆ 词表；Schema 枚举 ≡ 词表 |
| 词表 ⇄ 注册表双向对账 | client `RePlusPage/__tests__/metadata-vocabulary.spec.ts` | 词表内非回退类型必有内置渲染器；前端不得发明词表外键 |
| 成对渲染守护 | client `src/utils/__tests__/renderers-pairing.spec.ts` | 详情/列表成对、详情→表单可编辑（或登记豁免）、搜索键分类登记 |

**覆盖面缺口（本方案要补的治理项）**：闭包测试的视图集参数化清单只有 3 个（`BookViewSet` / `UserViewSet` / `LoginAccessPolicyViewSet`，`test_metadata_schema.py:77-84`）。全平台几十个启用了 `search-columns` 的视图集不在闭包内——**这正是「后端定义了字段、前端没渲染」目前只能靠人肉发现的原因**。实测已有一例在逃：`settings/serializers/basic.py` 的 `SITE_URL`（`serializers.URLField`）经 DRF `label_lookup` 下发 `"url"`，而 `"url"` 不在词表（前端仅有一条词表外历史兼容登记 `url: { filterKind: "text" }`，无正式渲染与校验归属）。

## 三、字段类型全集矩阵（核心盘点）

> 通道标记：✅ 有内置渲染器；「回退」= 走注册表回退语义（`valueType = input_type` 或保持初始 `input`）；❌ 无归宿（空白 / `[object Object]` 风险）；`—` = 词表该类型本就不该出现在该通道（如搜索侧由 filterset widget 面另行产出）。
> 「值形态」= 序列化输出给前端的形状，是渲染器与校验规则的契约锚点。

### 3.0 表 Z：Django 模型字段全量映射（二开入口表——模型里写什么，前端得到什么）

二开者在模型里声明的是 Django 字段，经 **DRF `ModelSerializer.serializer_field_mapping`**（本仓锁定版本全集，26 项 + postgres 3 项）转成序列化器字段，再经 `get_field_type` 推断出 `input_type`。**这是「后端定义字段 → 前端自动渲染」的第一跳**：模型字段 → 序列化器字段 → `input_type` → 四通道。

> 用量 = 业务 13 个 app 模型字段声明统计（本仓实测），说明该类型在真实二开中的出镜率。
> 「json 化」= DRF 对 `JSONField` 自动附加 `style.base_template=textarea.html`，但元数据侧经 `get_field_type` 的 DictField/JSONField isinstance 分支产出 `json`（不落 `textarea`）。

**兜底与平台覆盖**

- 任何未映射的自定义模型字段 → DRF `ModelField` → `field` → fallback input（保底可编辑，但无类型语义——自定义模型字段应同步声明序列化器字段类或 `input_type`）；
- 平台覆盖点：`BaseModelSerializer.build_standard_field` 仅注入模型 default（不改变类型映射）；`get_field_type` 的 isinstance 分支（labeled 系 / related 系 / json）优先于 `label_lookup`——即上表 input_type 列的最终裁决者；
- **本表结论**：26 个 Django 模型字段 + 3 个 postgres 字段中，**自动渲染正确 24 个**；未登记长尾 4 个（`decimal`/`duration`/`slug`/`url`），其中 `url`（2 消费点）与 `decimal`（1 消费点）为在逃项进批次三，`duration`/`slug` 零消费由闭包兜底；`BinaryField`/`FilePathField` 自动归宿正确或未暴露。

### 3.4 扩展机制清单（二开可用的全部「声明面」，现有 6 条）

「自动渲染」的可扩展入口**不止 input_type 一种**，二开选型速查（全部已有守护，无需新机制）：

1. **字段类自带**：`PhoneField` / `ColorField` / `StepFloatField` / `LabeledChoiceField` / `DictChoiceField`（字典驱动，选项运行时可改）——业务序列化器直接 import 声明；
2. **`input_wrapper(某字段)(input_type=...)` 包装**：给任意字段（含 SerializerMethodField）指定渲染类型（demo 教学字段即此用法）；
3. **前 / 后缀修饰**：`input_type_prefix` / `input_type_suffix`（上传关联 `_file` / `_image` 合成即此机制）；
4. **`style.base_template = "textarea.html"`**：CharField 长文本 → `textarea`（DRF style 惯例）；
5. **`api-search-*` 开放前缀 + `SuggestionsAction`**：大数据量关联远程联想（`suggest_url`，ADR-043 机制）；
6. **页面级逃生舱 `*Format` 出口**：以上都不满足时，页面 `listColumnsFormat` / `addOrEditOptions` 对单列覆写（不进词表、不动框架）——这是约定兜底，不是本方案扩展对象。

**扩展属性面**（字段显式声明 → 元数据透出 → 前端消费，`step` 先例）：`min_value` / `max_value`（DRF 原生）、`step`（StepFloatField）。本方案批次四按同模式补 `predefine`（color 预设色板），并明确**不再扩张**——元数据属性面保持最小集。

## 五、实施方案（四批次，可独立交付与验收）

> 红线：全程走既有扩展流程与守护，**不加第二套机制**；词表任何变更必须三测试锁步（server Schema 锁步 / client 词表⇄注册表 / 成对守护）+ `pnpm sync:contract`。

### 批次一（P0）：phone / color 缺陷修复与通道补齐

**后端**（`xadmin-server/packages/xadmin-common`）：

1. `PhoneField`：默认捆绑 `PhoneValidator`（构造参数 `validate: bool = True` 可关，SMS 现有显式挂载保持兼容）；空值按 `allow_blank` / `allow_null` 统一收口（`{code, phone:""}` 与空串等价归 None / 空串，语义写入 docstring）；解析失败不再盲目补 `+86`——抛 `ValidationError`（补 `+86` 的历史行为由消费方显式参数 `country="CN"` 保留）；
2. `ColorField`：捆绑色值格式校验（`#rgb`/`#rrggbbaa` 十六进制、`rgb()/rgba()/hsl()/hsla()`、CSS 颜色名——口径与 `WATERMARK_COLOR_RE` 对齐并抽为共享常量，消除两处口径）；
3. 新增/扩展守护用例：`PhoneField` 空值 / 垃圾值 / 带码对象写入、`ColorField` 合法 / 非法色值（放 `tests/unit/common/`）。

**前端**（`xadmin-client/src/components/RePlusPage`）：

4. 删除 phone 渲染器对 `column.default` 的篡改；默认值由 `PhoneInput` 的 `defineModel` 缺省（`{code:"+86", phone:""}`）兜底，`change` 事件产出净化后的 `{code, phone}`（剥离 `name`）；装配侧对 phone 默认值形态按 `columnDefaultValue` 同口径处理（对象形态不包 `{value}`）；
5. `renderers-detail.tsx` 补 `phone`：详情 `render` + 列表 `cellRenderer` 成对（`${code} ${phone}` 文本 + `v-copy`，不引 libphonenumber——遵守体积门禁）；
6. `fieldTypeRegistry.ts` 补 phone 的 `detail` 面与 `rule` 工厂（对象值穿透取 `.phone` 判必填；格式校验接 `src/utils/rules/phone.ts`，**口径决策**：元数据场景校验「数字与 `+` 组成、长度 6~15」的国际宽松口径，`isPhone` 国内口径留给登录注册页——两口径在 rule 模块注释写明分工）；
7. `color` 补 `rule` 工厂（色值正则，空值放行）；
8. `renderers-pairing.spec.ts` 补反向守护（G2）+ 两类型分类登记；`metadata-vocabulary.spec` / `fieldTypeRegistry.spec` 随之对账（无词表变更，Schema 不动）。

**验证**：server `uv run pytest tests/unit/common -q` + ruff + 重启三容器实测用户/SMS 表单；client `pnpm test:run` + `typecheck` + `lint`；E2E `smoke:fresh` + 定向 `tag-center`（颜色面板）与 SMS 设置页手机号回显。

### 批次二（P1）：词表闭包全量化（治理核心）

1. `test_metadata_schema.py` 参数化改为**URLconf 递归收集**：`get_resolver(...).url_patterns` 递归 walk，收集全部具备 `search_columns` / `search_fields` 属性的 ViewSet 类（去重、排除抽象基类），内存构造请求断言闭包；对个别无法脱离请求上下文构造的视图集允许显式 skip 清单（写理由，预期为空或个位数）；
2. 全量化后跑出的存量逃逸**逐个处置**（登记或修复，不豁免）：预期至少 `url`（2 处）与 `decimal`（1 处）——批次三正式登记前可先在本批次把对应序列化器字段显式转 `input_wrapper(...)(input_type="string" / "float")` 过渡（行为零变化、语义显式化）；
3. 嵌套 Serializer（`nested object`）显式结论落地：`get_field_type` 不转 json，文档声明「嵌套序列化器不支持元数据表单」（`metadata-protocol.md` §三补一行）；
4. `generate_crud` 字段计划对齐：`system/utils/platform/codegen_fields.py` 的字段表格把专用字段类（Phone/Color/StepFloat/DictChoice）纳入可选项，生成器产出的代码自动获得全部渲染能力（「后端加模型 → 前端免写页面」覆盖专用类型）。

**验证**：`uv run pytest tests/unit/common/test_metadata_schema.py -q`（全量视图集闭包绿）；`python manage.py generate_crud` 冒烟生成一个含 color/phone 字段的演示模型并实测渲染（demo app 教学字段顺带补一列 phone/color，作为矩阵文档的活样本）。

### 批次三（P1）：新类型 `rich_text` / `password` / `url` / `decimal`

逐类型走五步清单（摘要，详见 §三.3 表 C）：

1. **词表**：`DECLARED_INPUT_TYPES` 增 `rich_text` / `password` / `url` / `decimal` 四项；Schema 枚举同步 + `pnpm sync:contract`；
2. **`rich_text`**：后端新字段类 `RichTextField`（`common/core/fields.py`，CharField 子类 + 入库 bleach 净化复用 `common/utils/sanitize.py`）；前端表单接 WangEditor（懒加载已有）、详情净化渲染（DOMPurify）、列表纯文本摘要；试点迁移**公告正文**（可消除手写表单豁免清单一项；与《公告Markdown支持开发方案》的 `message_format` 维度正交，两者可并存）；

### 批次四（P2）：体验打磨与文档矩阵

1. **color 预设色板元数据化**（`step` 先例）：`ColorField(predefine=[...])` → `metadata_columns.py` 透出 `predefine` → Schema 补键 → 前端消费替换 `renderers-form.tsx:52-62` 硬编码 9 色；
2. **`PhoneInput` 打磨**：countries 接口模块级缓存（一次会话拉一次）、国码下拉 label 修正（`flag + name + code` 文本，去除 `JSON.stringify`）、禁用态从表单上下文透传；

## 七、风险与边界

1. **闭包全量化可能暴露存量逃逸**：处置策略是「登记或修复」而非豁免（豁免会让治理退化）；实施时如遇无法构造的视图集，skip 清单逐项写理由并保持最小；
2. **`PhoneField` 校验收紧的存量兼容**：现有唯一消费点 SMS 已挂 `PhoneValidator`，收紧不引入回归；但二开库可能存在依赖「盲目补 +86」行为的存量数据——补 `+86` 行为改为显式参数保留逃生舱，并在 changelog/升级注记提示；
3. **`rich_text` 安全面**：HTML 内容入库净化（bleach）+ 展示净化（DOMPurify）双保险沿用既有口径，WangEditor 组件已有 CSP 评估先例（公告页在用）；
4. **体积门禁**：WangEditor / PhoneInput 均为懒加载 chunk，不进首屏闭包；`pnpm check:bundle-size` 每批次必跑；
5. **不动的东西**：dform 控件白名单、四通道注册表架构、词表「不预登记无消费长尾」的克制原则、`api-*` 开放前缀机制。
