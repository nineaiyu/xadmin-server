# 权限行为新旧对比（2026-09 重构落地版）

> 本文是《数据权限与字段权限重构方案-2026.09.md》的配套交付物：**同一份配置在旧实现与新实现下的结果对照**，
> 供评审权限变动。实施范围 = 方案 P0+P1+P3（后端核心）+ 前端联动清理；
> P2（缓存）、P4（字段权限收口）、P5（预设模板）为后续批次，见文末。
>
> 新实现代码：`common/core/data_scope.py`（规则编译器 + ScopeResult 代数 + 写入校验）、
> `common/core/filter.py`（薄壳入口）。旧实现的内联逻辑已移除。

## 0. 一句话总结

**表达力不变（规则引擎完整保留），组合语义简化为行业通行的「取最宽生效」**：
部门祖先链 + 个人授权汇入同一授权池，各组结果取并集；组内多规则仍按授权自身的且/或模式；
「全部数据」在任何层级正确生效；无任何适用授权仍然看不到任何数据（fail-closed 保留）。

## 1. 合并语义：旧 → 新

```
旧（三层嵌套、模式错位）：
  组内规则      → 按 DataPermission.mode_type（单规则强制或模式）
  层内多授权组  → 按【用户本部门】mode_type（错位：祖先部门自身的配置是死配置）
  部门祖先链层间→ 固定 AND（逐级收紧，缺一层即全灭）
  个人 vs 部门链→ OR

新（两层、语义归位）：
  组内规则      → 按 DataPermission.mode_type（不变；且模式下 ALL 被忽略、或模式下支配整组）
  其余一切组合  → 统一 OR（取最宽生效）
  无适用授权    → none()（不变）
```

「且/或模式」字段变化：

| 字段 | 旧 | 新 |
|---|---|---|
| `DataPermission.mode_type` | 组内组合 | **保留**，含义不变（组内且/或） |
| `DeptInfo.mode_type` | 名义上控制层内组合，实际只在「用户本部门」时被读，祖先部门配置无效 | **删除**（迁移 0014；表单/筛选器/导入导出/empower 参数同步移除） |
| `UserInfo.mode_type` | 全仓无读取（纯死字段，可写不可用） | **删除**（迁移 0014） |

### 2.2 规则引擎（表达力全部保留 + 三处缺陷修复）

| # | 规则 | 旧结果 | 新结果 | 性质 |
|---|---|---|---|---|
| M | `value.dept.ids`（指定部门及下级） | **子树从未展开**（str/UUID 比较失配，只匹配所列部门本身） | 正确展开「部门及下级」 | **bug 修复**（新测试捕获的存量缺陷） |
| N | `value.table.*.ids` + `match=exact`（历史占位） | Q(字段=[列表]) → DB 报错 500 | 运行时强制归一为 `in` | **bug 修复**（案例 5 后端防御） |
| O | `match=ip_in` + 值 `["*"]`（配「全部 IP」） | 静默变成「无 IP」（守卫要求嵌套 `[["*"]]`） | 「不限」 | **bug 修复**（D10） |
| P | `match=m2m_all` 单规则授权 | 退化为「包含任一」（多 Q 展开被外层或模式吞掉） | 单 Q 交集，「包含全部」正确表达 | **bug 修复**（D10） |
| Q | `exclude=true` + 全部数据规则 | exclude 被忽略（恒放行） | **保存时直接拒绝**（校验）；存量读取仍按忽略 | **行为变更**（D11：校验拒绝） |
| R | 跨表字段（`admin__dept`）、时间窗（`value.date`）、相对时间、正则、IP 段、JSON 条件 | 支持 | 支持（不变；验证器按 dunder 逐段校验路径） | — |
| S | **新增**：`value.leader.dept.ids`（我主管的部门及下级） | 不存在 | 主管部门子树展开（`dept_belong` 维度） | **新增** |
| T | **新增**：`value.leader.user.ids`（我主管部门的成员） | 不存在 | 主管部门成员 pk 集合（`creator`/归属人维度） | **新增** |

主管语义：`DeptInfo.leader = FK(UserInfo)`（迁移 0014）；用户不是任何部门主管时，两类规则解析为空集（恒假），不影响其其他授权。主管授权与部门/个人授权同池「或」合并——**主管权限天然是授权并集的一个来源**，无独立开关。

## 4. 数据与结构变更清单（升级影响）

- **迁移 0014**（`system/migrations/0014_remove_mode_type_add_dept_leader.py`）：
  1. 删除 `system_deptinfo.mode_type` 列（数据丢弃——该字段旧实现下从未被有效读取，属清理）；
  2. 删除 `system_userinfo.mode_type` 列（同上）；
  3. 新增 `system_deptinfo.leader` 外键（SET_NULL）。
- **种子清理**（`loadjson/`，需重跑 `load_init_json` 生效）：
  - `deptinfo.json` / `userinfo.json`：移除 `mode_type` 字段；
  - `modellabelfield.json`：移除 userinfo/deptinfo 下的 `mode_type` 注册项（4 条），`datapermission` 的 2 条原位保留；新增 `deptinfo.leader` 注册项（字段树两套，field_type 0/1），与迁移 0014 配套。
  - 存量库中的旧注册项无害：新校验器会拒绝在其上新建规则。
- **API**：部门/用户序列化器与筛选器不再含 `mode_type`；`empower` 请求体去掉 `mode_type`（旧前端多传会被忽略，不报错）；部门序列化器新增 `leader`。
- **rules JSON 存量数据完全兼容**：结构未变，无需迁移。
- **建议巡检**（升级必做，见 §4.1）：对存量 `DataPermission.rules` 跑一次 `validate_rules` 巡检，列出并修正非法规则。

### 4.1 升级操作清单（部署后必做）

| 步骤 | 命令 | 目的 |
|---|---|---|
| 1 | `python manage.py migrate` | 应用迁移 0014（删 `mode_type`、加 `deptinfo.leader`） |
| 2 | `python manage.py load_init_json` | 重导种子（`modellabelfield` 增 `deptinfo.leader` 注册项等） |
| 3 | `python manage.py compilemessages -l zh` | 新增文案生效（构建期已编译可跳过） |
| 4 | `python manage.py audit_data_permission_rules --strict` | **重点**：列出存量非法 / value 与字段类型不匹配的规则 |

> 第 4 步为何必做：新读侧对「value 与字段类型不匹配」的存量脏规则 fail-closed（编译期会抛错的规则整条判为不生效），
> 现象从「接口 500」变为「绑定用户看不到数据」，且后台无直接线索。`--strict` 使该检查可进发布流水线（发现即非零退出）。

### 6.2 复核修复（2026-09-10 第三轮：value 收口与收尾项）

| 级别 | 问题 | 修复 |
|---|---|---|
| 高 | §6.1 放行 `isnull`/`range`/`year` 等 class lookups 后 value 无类型收口：实测 `isnull` 传 `"true"` 字符串、`range` 传单元素在 `filter()` 阶段**不报错**，要到 SQL 编译期才抛（ValueError/IndexError），绑定用户仍会 500 | ①`normalize_match_value` 归一 isnull(bool)/range(2 元)/日期分量(int)，归一失败读侧拼恒假；②`_is_compilable` 以 `str(qs.query)` 做编译探测，坏规则整条 DENY_ALL + 告警（覆盖归一管不到的 `date`/JSON 等）；③写入侧同口径拒绝（新增 3 条 po 文案） |
| 中 | `validate_rules` 的 pk-list 形态校验恒真（`isinstance(_pk_list(value), list)` 永远为真），TABLE_TYPES/DEPARTMENTS 的值实际没校验 | 改为空集校验：`value` 归一后不得为空（`Rule %(index)d requires at least one value`） |
| 中 | `loadjson/modellabelfield.json` 未登记新增的 `deptinfo.leader`，字段权限/字段树里看不到「部门主管」 | 补两条注册项（field_type 0/1），见 §4 |
| 中 | 编译探测会误伤存量「运行时注入 value」的规则：`loadjson/datapermission.json` 实测 4/10 条（仅本人数据等 `value.user.id`/`value.user.dept.id`，value 为 `""` 占位）保存即报错——与 §6.1 的 P1-1 同类陷阱 | 新增 `RUNTIME_VALUE_TYPES`（OWNER / 部门类 / TABLE_*）：写入侧不做 value 形态与编译探测（读侧 resolve 后仍探测），match 校验保留 |
| 低 | `build_rules_qs` 的 ALL 短路按 `match` 字面判断，存量 ALL 规则 match 缺失/为 `"*"` 时不短路 | 改按 `type == value.all` 判定（与 resolve_rule 读侧口径一致） |
| 低 | `ip_in` 的 `hosts()` 是一次性生成器，编译探测会消费它导致真实查询条件丢失 | 显式 `list(...)` 物化 |
