# 功能模块化与裁剪（二开友好架构）

> 目标：让使用者（尤其是二次开发者）在**不改代码**的前提下，把后台裁剪成自己需要的样子，
> 而不是被动接受一整套功能。机器可读的模块清单在
> [`common/core/modules.py`](../../common/core/modules.py)，决策记录见
> [ADR-045](../adr/ADR-045-modular-trimmable-architecture.md)。

## 一、为什么"重"

| 根因 | 实测（2026-09-17） |
|------|--------------------|
| 功能没有边界 | 后端 8 个 app / ~56 模型；`system` 单 app 承载 47 模型、53 个视图文件、28k 行；前端 156 个页面 / ~33k 行 |
| 功能没有开关 | 全仓不存在模块级开关；唯一"裁剪"手段是删菜单数据（页面与接口都还在） |
| 装配点分散 | 新增/移除一个功能要动 6+ 处：`INSTALLED_APPS` → `urls.py` → `loadjson/menu.json`（49 菜单 + 493 权限点）→ 权限扫描映射 → 前端页面/组件映射 → 前端 API 与词条 |
| 扩展点只增不减 | `XADMIN_APPS` + `auto_register_app_url` 只能在导入期追加全局列表，且必须改配置文件重启 |

## 二、分层模型

```
┌─ 内核 core（不可裁剪）：身份与访问、组织与权限、配置、文件与流转、通知、审计与在线、PAT
├─ 标配 standard（默认开，可裁）：运维监控、敏感操作审批、数据脱敏、目录同步
└─ 可选 optional（按需开）：聊天室、AI、数据分析、表单采集、审批流引擎、事件订阅、开放平台、全局搜索、SCIM
```

发行预设（`MODULE_PRESET`）：

| 预设 | 含义 | 适用 |
|------|------|------|
| `full`（默认） | 全部模块开启 | 存量部署、功能体验（行为与改造前完全一致） |
| `standard` | 内核 + 标配 | **推荐二次开发起点**：去掉 9 个可选模块 |
| `core` | 仅内核 | 只做自有业务的极简底座 |

## 四、开关用法（config.yml）

```yaml
# 1) 选基线：full（默认，全功能）/ standard（去掉可选模块）/ core（仅内核）
MODULE_PRESET: standard

# 2) 在基线上按需增减（可选）
MODULE_ENABLE:
  - chat          # 单独打开聊天室
MODULE_DISABLE:
  - ops           # 关掉运维监控页与采集任务
  - datamask      # 关掉数据脱敏
```

规则与校验（启动期 fail-fast，报错信息直接可执行）：

1. 未知模块 id / 非法预设 → 启动报错并列出可用值；
2. `core` 等级模块不可关闭；
3. 依赖未满足（模块声明了 `depends` 但被依赖项关闭）→ 启动报错，不做隐式连带启用；
4. 配置变更**需重启进程**（与 `XADMIN_APPS` 同语义）；重启时会自动清理菜单路由与权限缓存。

## 五、裁剪在四层生效（软裁剪）

| 层 | 行为 | 实现位置 |
|----|------|----------|
| 请求路由 | 命中停用模块前缀的请求直接 404（`code=1001`），避免"页面没了、接口还在" | `server/middleware.py::ModuleGateMiddleware` |
| 菜单与权限点 | 停用模块的菜单子树（含其权限点）从 `/api/system/routes` 与鉴权结果中隐藏；子树被清空的目录一并隐藏 | `common/core/modules.py::filter_menu_queryset` |
| 周期任务 | 停用模块声明的周期任务不注册，已注册的 beat 条目一并清理；重新启用自动恢复 | `common/tasks.py` + 装饰器 `module=` 参数 |
| 种子导入 | **新装库即为精简形态**：`load_init_json` 按同一口径过滤种子，停用模块的菜单/权限点/字段权限/角色菜单绑定不入库 | `common/core/modules.py::ModuleSeedFilter` + `system/utils/seed.py::build_seed_fixtures` |
| 缓存 | 存在停用模块时，启动即清理菜单路由/权限缓存（TTL 24h，避免残留显示） | `common/core/modules.py::invalidate_trimmed_caches` |

**语义红线**：关闭模块只隐藏与拦截，**不删除任何业务数据**；重新开启即恢复原状。
（种子过滤只作用于「新装/重建种子」，不会清理存量库里已有的菜单数据。）

**种子导入的冲突预检**：`loaddata` 把整次导入放在单个事务里，一行冲突会回滚**全部** fixture。
因此种子装配会先做自然键预检——`code`/`name` 等唯一键已被库内对象占用（主键不同）时跳过该行，
并级联剔除引用行、从 m2m 列表移除主键；**库内数据优先、种子让位**，跳过项逐条打印。
这条对"运营已建同类对象"的存量库尤其重要（详见 `system/utils/seed.py` 模块说明）。

## 五之二、命令行与管理页

```bash
python manage.py modules                            # 当前生效的模块组合（等级/状态/页面数/路由数）
python manage.py modules --preset standard          # 预演另一套预设（不改动实际配置）
python manage.py modules --disable analysis,chat    # 预演关闭若干模块
python manage.py modules --preset core --enable chat --config   # 只输出可粘贴到 config.yml 的片段
python manage.py modules --preset standard --impact # 在当前库上评估影响面（只读）
python manage.py module remove chat                 # 物理移除计划（种子清理范围/代码引用/前端文件/i18n 词条）
python manage.py module remove chat --apply         # 执行种子清理（原文件先归档到 _delete/，可整体还原）
python manage.py generate_module my_biz --app demo --label "自有业务" --menu MyBizMenu --route "^/api/demo/"
```

配置非法（未知模块 / 关闭内核 / 依赖未满足）与真实启动一致地 fail-fast 并给出可执行的报错文案。

**切换前的"体检"**：`--impact` 在**当前库的真实数据**上按同一口径复算影响面——会隐藏多少目录/页面/权限点、
逐模块明细、哪些角色受影响（绑定数与在册用户数）、相关业务表体量。全程只读：不改配置、不写库、不重启，
授权数据无需调整（运行期过滤，开回即恢复）。上线裁剪前先跑一次，避免"预演说隐藏 A、实际隐藏 B"：

```bash
python manage.py modules --preset standard --impact
```

```
影响面（当前库实时数据，只读）：菜单行 551（目录 13 / 页面 50 / 权限点 488）
  将隐藏：目录 4 / 页面 17 / 权限点 137    仍可见：页面 33 / 权限点 351
  ...
  受影响角色（绑定菜单 / 其中被隐藏 / 在册用户；授权数据无需改动，运行期过滤）
    示例-员工                    40 /   34 /    1
```

管理界面：**系统管理 → 模块管理**（`/system/module/index`）只读展示同一份清单——当前预设、
每个模块的等级/依赖/覆盖范围/启停状态与可复制的裁剪配置片段，供不方便进容器的人查看。

## 六、已知边界

- **WebSocket 通道不拦截**：停用 `chat` 后页面与 REST 均不可达，WS 连接本身不拦截（后续批次补 WS 级拦截）；
- **存量库的菜单数据不回收**：种子过滤只作用于新装/重建种子；存量库以运行期隐藏为准（不删数据是红线）；
- **前端构建产物仍包含全部页面**：已评估不立项（见 §八 P2 说明）；
- **模块开关不替代功能开关**：如 `LDAP_AUTH_ENABLED`、`SCIM_ENABLED`、`AI_ASSISTANT_ENABLED` 等运行期功能开关保持独立。

## 七、维护约定

**新增一个可裁剪功能**：

0. 第三方 app 用脚手架生成 `{app}/modules.py`（`python manage.py generate_module ...`）——
   app 侧声明随安装自动纳入清单，不需要改本项目源码；项目内置功能按下述步骤写在
   `common/core/modules.py`；
1. 在 `common/core/modules.py` 的 `MODULES` 里加一条 `ModuleSpec`（id/等级/菜单根 name/路由前缀）；
2. 菜单 name 必须在 `loadjson/menu.json` 中存在（守护测试会校验，拼错即裁剪失效）；
3. 若带周期任务：`@register_as_period_task(..., module="<模块 id>")`；
4. 补一条裁剪用例（参照 `tests/unit/common/test_modules.py`）；种子侧无需额外登记——
   `ModuleSeedFilter` 按同一份声明过滤。

**停用/移除一个现有功能**：只需改配置，不必改代码；确实要物理移除时，见路线图 P4。

| 批次 | 内容 | 状态 |
|------|------|------|
| P0 | 模块清单与裁剪矩阵（本文档）+ ADR | ✅ 2026-09-17 |
| P1 | 模块注册表 + 预设 + 运行期四层软裁剪 + 守护测试 | ✅ 2026-09-17 |
| P2 | 种子裁剪（`load_init_json` 按启用模块过滤，新装即精简形态）+ `manage.py modules` 清单/预演 CLI | ✅ 2026-09-17 |
| P2b | 前端构建期裁剪（componentMap + 按需 glob） | ✖ **评估不立项**（见下） |
| P2c | `loadjson` 目录级拆分（`loadjson/menu/{module}.json`） | ✖ **评估不立项**（2026-09-17）：裁剪与删除已由种子过滤器 + `module remove` 覆盖；拆分只改文件组织方式，却会打断既有二开对 `loadjson/*.json` 的路径引用。触发条件：种子需要按模块独立升级分发 |
| P3 | 二开路径文档（§九）+ `generate_module` 脚手架 + app 侧 `modules.py` 声明扩展点 + 「模块管理」页面 | ✅ 2026-09-17 |
| P4a | 硬裁剪脚本 `manage.py module remove`（计划 / 种子清理 / 归档回滚） | ✅ 2026-09-17 |
| P4b | `system` 物理拆分子 app | ✖ **评估不立项**（见下） |
| P5 | 影响面预演 `manage.py modules --impact`（只读：隐藏范围 / 逐模块明细 / 角色影响 / 数据体量，与运行期同口径） | ✅ 2026-09-17 |

**P2b 不立项的理由与触发条件**：前端页面已通过 `import.meta.glob`（非 eager）按页面分块懒加载，
未访问的模块页面本就不进首屏闭包，构建裁剪的收益只剩 `dist` 体积；而把「子串匹配」改成显式
componentMap 需要新增一份「模块 → 页面目录」映射（与后端声明形成第二个事实源，需再建生成器与
CI 同步校验），并改动路由解析这一高风险路径。**触发条件**：出现"发布产物体积硬约束"（如离线
介质分发）或"页面目录与菜单组件名错配"的真实故障时，再按「生成器 + 同步校验」方案重开。

**P4b（`system` 物理拆子 app）不立项的理由与触发条件**：

- **收益边界**：可裁剪性已由声明 + 五层裁剪完整提供，拆 app **不改变任何裁剪能力**，只影响代码组织；
  当前 `system` 内 45 个模型可清晰分为 组织与权限 11 / 审计与配置 9 / 审批与表单 10 /
  数据分析 4 / AI 3 / 开放平台与集成 8——边界信息已沉淀在 `MODULES` 声明里，拆分技术上是"搬运"。
- **成本与风险**（实测）：`system` 现有 7 个迁移，`0001_initial` 48.9 KB、`0004_*` 122.6 KB
  （一次全量重建）；表名是隐式 `system_<model>`（未 pin `db_table`），跨 app 移动模型即
  表重命名，必须 `SeparateDatabaseAndState` + 表名保持 + 数据迁移；**125 个非 `system` 文件**
  import `system.models`，且 `app_label` 参与 `modellabelfield` / `datapermission` 的模型标识与种子；
  另外 `common.DbAuditModel.dept_belong` 硬编码 `system.DeptInfo`，拆组织模型前要先解耦 common。
- **触发条件**（任一成立再开独立窗口）：① 某子域需要独立发版/独立许可分发；
  ② `system` 迁移在多分支并行时频繁冲突；③ 需要把某子域（审批 / 数据分析）做成可单独安装的 app 包。
- **结论**：保留单 app + 声明式边界；将来拆分时按 `MODULES` 逐域迁移，不推翻现有裁剪体系。

## 九、二开典型路径

**路径 A：只要一个轻后台（改配置，不改代码，10 分钟）**

```bash
python manage.py modules --preset standard          # 先看一遍会关掉哪些模块
python manage.py modules --preset standard --config # 拿到 config.yml 片段
# 写入 xadmin-server/config.yml → 重启进程 → 新装环境执行 python manage.py load_init_json
```

存量库无需重灌种子：关掉的模块立即从菜单、接口（404）与周期任务中消失，数据原样保留；
以后想再加回来，改回配置重启即可。

**路径 B：彻底删掉一个模块（物理移除，可选）**

```bash
python manage.py module remove chat          # 先看计划：种子清理范围 / 后端引用 / 前端文件 / i18n 词条
python manage.py module remove chat --apply   # 执行种子清理（原文件归档到 _delete/，可整体还原）
```

命令会打印完整清单，人工按序执行：

1. **先软裁剪**（`MODULE_DISABLE: [chat]`）并重启，确认业务无依赖——这一步可随时回滚；
2. **种子清理**：用上面的 `--apply` 一次性完成（菜单/权限点/字段权限/角色绑定，原文件有归档）；
3. **后端代码**：按命令列出的引用清单删除（如 `message/` 目录、`server/urls.py` 的 include、
   `server/asgi.py` 路由、`common/core/modules.py` 里的 `chat` 声明）；
4. **前端代码**：按命令列出的文件删除（`src/views/chat/`、`src/api/chat/`）与 i18n 词条（`menus.chat`）；
5. **门禁**：`pytest -q && ruff check .`、前端 `pnpm lint && pnpm typecheck && pnpm test:run`，E2E smoke 兜底。

**路径 C：加自己的业务模块（推荐做法）**

1. 用代码生成器起骨架：`python manage.py generate_crud <app.Model>`（产出 serializer/view/urls/config
   + 前端页面 + 菜单种子，见 ADR-027）；
2. 在 `config.yml` 的 `XADMIN_APPS` 注册 app（自动注入路由与权限前缀）；
3. 把它做成「可裁剪的功能模块」——两种方式：
   - **app 内声明（推荐，第三方 app 不必改本项目源码）**：
     `python manage.py generate_module my_biz --app demo --label "自有业务" --menu MyBizMenu --route "^/api/demo/"`
     生成 `{app}/modules.py`，随 app 安装自动进入模块清单；
   - 或按 §七 在 `common/core/modules.py` 的 `MODULES` 里补一条 `ModuleSpec`；
4. 带周期任务时给装饰器加 `module="<模块 id>"`；菜单根 name 需在 `loadjson/menu.json` 登记；
5. 跑 `python manage.py modules` 确认新模块出现在清单里，并按需调整等级（core/standard/optional）。
