# 方案选型与对比（二次开发）

> 定位：同一个目标往往有多条路——本文给出**每条路的特点、适用场景、优缺点与取舍建议**，
> 让选型有依据，而不是"看谁先搜到"。
> 组件用法见 [component-handbook.md](component-handbook.md)；按任务找步骤见 [../guide/recipes.md](../guide/recipes.md)。

## 〇、结论先行（TL;DR）

| 我要做…… | 选 |
|---|---|
| 标准 CRUD 列表页 | **元数据驱动**（`BaseModelSet` + `<RePlusPage>`）——本项目默认路径 |
| 非标准形态页面（看板/画布/聊天） | **手写页面** + 复用 Re\* 组件与工具（`ReDialog` / `BaseApi` / `utils`） |
| 从零建模块 | **`generate_crud` 生成骨架** → 人工复核收口（不手抄） |
| 一次性交付轻量后台 | **模块裁剪**（`MODULE_PRESET=standard/core`），而不是删代码 |
| 临时确认交互 | `ElMessageBox`；表单/详情 → `ReDialog` / `ReDrawer` |

---

## 一、列表页开发的三种范式

### 1.1 元数据驱动（RePlusPage）—— 本项目默认

**做法**：后端声明序列化器/过滤器 → 前端一行 `<RePlusPage :api :auth>`，列/搜索/表单/详情全部由 `search-columns` / `search-fields` 元数据生成。

| 维度 | 评价 |
|---|---|
| 特点 | 页面零硬编码列定义；新增字段只改后端；权限、导入导出、回收站、变更历史开箱即用 |
| 适用 | 一切"标准 CRUD 资源"（本项目绝大多数后台页面） |
| 优点 | ① 一处声明两端生效，杜绝前后端列不一致；② 页面代码量极小（薄壳 + hook）；③ 内建能力完备（分页/搜索/导出/审计） |
| 缺点/代价 | ① 定制需要理解 `*Format` 出口与元数据协议（学习成本）；② 元数据缺失时**静默缺列**（项目已加 DEV 警示条）；③ 极端定制（复杂联动画布）不适用 |
| 何时不要用 | 页面不是"资源列表"形态；交互超出 CRUD（拖拽画布、实时看板、聊天） |

### 1.2 手写页面（el-table + 自研表单）

**做法**：完全手写表格、分页、搜索、表单。

| 维度 | 评价 |
|---|---|
| 特点 | 完全自由 |
| 适用 | 非标准形态；轻量只读展示页（几十行就够，不值得上组件） |
| 优点 | 无框架约束；一次性的简单页面开发快 |
| 缺点/代价 | ① 列定义与后端重复（字段改名忘了改前端 → 静默错列）；② 权限/导出/审计都要自己接；③ 项目红线多（类型严格、行数门禁、a11y）都要自己过 |
| 建议 | **只用于非标准形态**；表单/弹层/请求仍复用项目组件（`useBaseColumns`、`addDialog`、`BaseApi`），不要重造 |

### 1.3 后端渲染（Django Admin 式）

**做法**：后端直接出 HTML 页面。

| 维度 | 评价 |
|---|---|
| 适用 | 纯内部工具、无前端团队、页面形态完全不需要定制 |
| 本项目情况 | **不采用**：前端已是独立 SPA，后台渲染会引入第二套 UI 体系与权限口径 |

**决策建议**：默认 1.1；确属非标准形态用 1.2（并最大化复用组件）；1.3 不在本项目技术栈内。

## 二、从零建模块的三条路

| 路线 | 特点 | 优点 | 缺点/风险 | 建议 |
|---|---|---|---|---|
| **`generate_crud` 生成**（推荐） | 模型 → 后端四件套 + 前端页面 + 菜单种子，生成块幂等合并 | 机械步骤秒级完成；产物就是标准范式；尾部给出后续步骤清单 | 关联字段 `input_type`、菜单挂载位置仍需人工复核；生成物是普通代码，后续维护自理 | **默认选择**；先 `--dry-run` 预览 |
| 手写四件套 | 照 `demo/` 与 `first-module-30min` 逐层写 | 完全理解每一层的时机 | 慢；易漏 `table_fields` / 权限点 / `Meta.fields` 同步 | 学习期用一次（理解链路），生产用生成器 |
| 复制现有模块改写 | 拷一个相似模块改名 | 起步快 | 残留旧模块的权限码/菜单/种子引用，清理成本高；容易带进历史坏味道 | 不推荐 |

## 三、组件选型速查

### 3.1 弹层：ReDialog / ReDrawer / ElMessageBox

| 组件 | 适用 | 优点 | 代价 |
|---|---|---|---|
| `ReDialog` | 表单编辑、导入导出、确认类交互 | 命令式调用（不在模板挂组件）；内建 loading / beforeSure / 拖拽 / 尺寸档位 | 内容组件需按约定写（props 收参、close 经框架） |
| `ReDrawer` | 复杂详情、长表单、侧栏编辑 | 不遮挡主列表上下文；空间更大 | 与 Dialog 二选一的判断成本（经验：**预览/详情 → 抽屉，编辑/确认 → 弹窗**） |
| `ElMessageBox` | 一句确认 / 简单输入 | 零成本 | 不能承载表单；忘记 `.catch` 会出现"取消仍执行"类缺陷（项目修过） |
| 页面内嵌（inline 展开/分栏） | 主从联动（选中行在右侧编辑） | 无模态打断 | 布局复杂度高（分栏页有专门组件 `ReSplitPane`） |

### 3.2 表单的三形态

| 形态 | 适用 | 说明 |
|---|---|---|
| RePlusPage 内置新增/编辑（`addOrEditOptions`） | 标准资源表单 | 零代码起步；定制走 `columns` 解析器 + `beforeSubmit` |
| `openDialogDrawer({...})` | 独立表单弹层（复用框架校验/提交链） | 已收敛的标准写法 |
| 自定义表单组件 + `addDialog` | 形态特殊（分步、动态字段、强联动） | 参考收敛模式：`addDialog` + `XxxForm.vue`（`getPayload()` 返回 null 表示不关） |

### 3.3 选择器/数据源四选一

| 方案 | 适用 | 特点 |
|---|---|---|
| 静态 `choices`（元数据下发） | 小声量枚举 | 零成本；改动要发版（需要在线维护 → R7 数据字典） |
| `api-search-*`（表单字段组件） | 中等数据量关联字段（用户/部门/角色/菜单） | 弹层搜索选择；四款内置 + 可注册扩展 |
| `RePlusSearch`（独立选择器） | 页面内嵌"选一个业务对象" | 下拉里嵌完整表格（搜索/分页/树形） |
| `SuggestSelect`（联想） | 大表 / 远程模糊匹配 | 候选与写入校验同源（防枚举）；当前服务端需声明 `suggestion_fields` |

### 3.4 其他成对选择

| 场景 | 方案 A | 方案 B | 建议 |
|---|---|---|---|
| 共享状态 | 组件本地 state | Pinia store | 跨页共享才进 store；页面内状态留在页面 |
| 数据获取 | `BaseApi` 标准方法 | 手写 `http.request` | 标准资源用 A；一次性端点用 B（保持类型与错误链一致） |
| 图标 | 编译期（`useRenderIcon(Delete)`） | 元数据字符串名（`ep:xxx` 离线集） | 代码内用 A（类型安全）；菜单/后端下发用 B |
| 树形列表 | RePlusPage `isTree`（全量拉取） | 手写树组件 | 数据量可控用 A；超大树上自研虚拟化 |
| 二次验证 | `ReMfaConfirm`（412 协议） | 业务自己弹窗 | 用 A（http 层自动接线的共享 Promise） |

## 四、功能取舍：裁剪 vs 删除 vs 不用

| 方案 | 特点 | 适用 | 代价 |
|---|---|---|---|
| **模块裁剪**（`MODULE_PRESET` / `MODULE_*`） | 六层联动关闭（路由/WS/菜单/任务/种子/缓存），**不删数据**；可随时恢复 | 交付轻量后台、涉密环境收窄功能面 | 代码仍在仓库（体积/依赖还在）；模块需已声明（内置模块已声明齐） |
| `module remove` 硬裁剪 | 物理移除代码 + 种子清理，带归档回滚 | 确定永不需要该功能 | 移除后升级合并成本高 |
| 不改代码、菜单层面隐藏 | 最轻 | 只是"不给某些人看" | 权限点仍在接口可调（安全性靠角色授权） |

**建议**：默认树用裁剪；"交付给客户的发行版"用 preset；`module remove` 只在极端减体积场景用。

## 五、与同类方案对比（类别视角）

> 下表以**方案类别**对比（代表项目为类别举例，特征为类别共性）；本项目列按本仓库实际机制填写。

| 维度 | 后端渲染型（Django Admin / simpleui） | 代码生成型（RuoYi 系 / jeecg 系） | 前端模板型（vue-pure-admin / vue-element-admin） | 低代码平台 | **本项目（xadmin）** |
|---|---|---|---|---|---|
| 页面来源 | 框架运行时渲染 | 生成完整代码后人工维护 | 全部手写 | 拖拽配置运行 | **元数据运行时驱动 + 生成器起步** |
| 加一个字段的成本 | 改模型（前端自动） | 改模型 + 重新生成 + 合并（或手改多处） | 改模型 + 手改前端列/表单/搜索 | 平台内配置 | **改模型 + 序列化器声明（前端自动）** |
| 定制自由度的上限 | 低（页面形态固定） | 高（代码在手） | 高（代码在手） | 低（平台表达力） | **中高**（`*Format`/渲染器/自定义页面三层出口） |
| 权限模型 | 模型级为主 | RBAC 常见 | 需自建或接后端 | 平台内置 | **API/数据/字段三层 RBAC + 应用级授权** |
| 前后端一致性 | 不存在（同源） | 靠纪律/重复劳动 | 靠纪律 | 平台内一致 | **契约镜像 + 类型生成 + CI 守护** |
| 学习成本 | 低 | 中（先学生成器再学框架） | 中（前端框架） | 低（但受平台限制） | **中高**（元数据协议 + 权限码 + 组件体系三件事） |
| 最适合 | 内部工具、快速兜底 | 一次性交付、二次开发团队 | 个性化产品前端 | 简单流程/表单应用 | **长期演进的自建后台（本项目场景）** |

### 5.1 本项目的优势（相对同类）

1. **元数据驱动 + 契约治理**：列/表单/搜索一处声明两端生效，且契约用 JSON Schema 冻结 + CI 守护——同类开源后台里少见的工程化程度；
2. **权限颗粒度**：API/菜单 + 数据（16 种规则）+ 字段 + 应用级四道门，配套权限点缺口扫描与自检；
3. **可裁剪**：模块六层联动裁剪，不改代码即可得到轻量发行版；
4. **交付链路完整**：离线安装器、备份/PITR、升级回滚、门禁与 E2E 体系。

### 5.2 本项目的代价（诚实清单）

1. **学习曲线**：三件事必须先懂（元数据协议 / 权限码约定 / 渲染器注册），否则会遇到"不报错但没效果"类问题（见 [dev-pitfalls.md](../dev-pitfalls.md)）；
2. **约束更多**：文件行数、strict TS、a11y、契约同步等门禁对"只想加个页面"的人有压迫感（换来的是长期可维护性）；
3. **环境门槛**：Node ≥ 22.22.1 / pnpm ≥ 11 / Python 3.13+，Windows 有限支持（任务监控命令）；
4. **维护规模**：单人主导维护，社区生态小于头部开源后台。

### 5.3 什么项目适合 / 不适合

| 适合 | 不适合 |
|---|---|
| 需要长期演进、多人协作的内部管理平台 | 一次性黑客松页面（框架学习成本高于产出） |
| 对权限（数据行级/字段级）与审计有硬要求的系统 | 纯 C 端产品（无后台管理形态） |
| 希望"加字段/加模块"是分钟级操作的团队 | 团队完全不想接受任何工程门禁约束的项目 |
| 需要裁剪发行（客户版/轻量版）的交付场景 | 需要拖拽式全民开发的低代码场景 |
